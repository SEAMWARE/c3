Coroutines

A request that waits - a forward to another broker, an @context download, a notification to send - runs as a coroutine of the event loop that read it. Where it would block on a socket it hands the socket to the loop and yields; the loop serves every other connection meanwhile and resumes it when the socket is ready. One thread, any number of requests waiting at once, no thread switch.

The last row's waits are inside a library that knows nothing of the loop - libmongoc, libpq, the bridge's condition variable: a coroutine there would stop the loop for the length of the wait. So coraine lets a request be a coroutine with corDB and TRoE none or corDB, except for ?ddsSync.

A broker with coroutines is one with the built-in HTTP server (cmake -DCOR_HTTP_SERVER=builtin; libmicrohttpd is the default - Building) or a cor:// listener (--corPort), --database corDB, and --troe none or --troe corDB.

After the response

The post-response phase - a write's notifications above all - runs the same way: inline when the request left nothing that can wait, else as a coroutine with corDB. A pending bridge goal release waits on the bridge, and goes to a worker.

The cap

1024 coroutines per loop. Past it, or with no stack to be had, a request that can wait goes to a worker (HTTP), or moves its connection to a thread of its own (cor://, when nothing else of that connection is in flight; else it runs on the loop).

What waits, and how

Every wait of the broker's clients goes through one function, as poll() on one descriptor:

int corRestWaitFd(int fd, short events, int timeoutMs, short* reventsP);

In a coroutine it registers the descriptor with the loop's epoll (one epoll_ctl, EPOLLONESHOT), arms the timeout and yields; on a worker or a libmicrohttpd thread it is poll().

For code that runs in a coroutine. A request's state is reached through one thread-local pointer, corRestP, saved before a wait and restored after it. No lock may be held across a wait: a coroutine that yielded holding a mutex deadlocks the next coroutine of its thread that wants it - what the clients, the notification senders and the registration probe read is pinned, and they wait without a lock.

The servers

Server
built-in HTTP--httpLoopsevent loops on one port, 1-64; 0, the default, is one per core, at most 4 (the cores the process may run on - its CPU affinity and cgroup quota). The cor:// listener (--corPort) takes the same count, at most 16, on either HTTP server. Loop 0 accepts every connection and deals them out in turn, so they are spread evenly - the kernel's SO_REUSEPORT hash splits a handful unevenly. A coroutine's response goes out on its loop's thread.
cor:// server--corPorta connection is armed once and multiplexed: the loop reads every frame, starts each request inline or as a coroutine, and queues each response as it finishes
cor:// clientone connection per peer per thread, shared by that thread's requests, any number in flight - a distributed operation has every cor:// forward in flight at once (The cor format and cor://)

At a stop

The broker drains the workers, then stops the loops. A stopped loop cancels its coroutines' waits: one waiting for a socket is resumed with -1 (ECANCELED), a parked one with 0, and every later wait fails at once. A request or post-response phase still waiting - a Context Source that does not connect, a notification endpoint that does not answer - runs its failure path to its end and frees what it holds, without waiting out its timeout. Then the connections still holding a request are closed. A stop takes no longer for it; a request in flight is answered as failed, a notification in flight counted as failed.

Not coroutines today

  • mongoc requests - the driver blocks; a yielding mongoc stream would change that
  • libmicrohttpd's requests - they wait on a worker thread
  • the cap and the stack size are fixed - no option sets them
