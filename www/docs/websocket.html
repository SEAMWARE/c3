WebSocket

The broker's whole API and its notifications over one connection. A web page opens a WebSocket, sends it any request it would send over HTTP, creates subscriptions over it and receives their notifications on it - nothing to poll, and no endpoint of its own for the broker to reach.

coraine --transports ws

The WebSocket is a transport plugin, ws.so, loaded by --transports. It is in the build by default; -DCOR_FEATURE_TRANSPORTS=OFF leaves it out - no --transports, no ws.so (Building).

Everything the broker serves over HTTP is served over the connection: entities, batch operations, subscriptions, context source registrations and their subscriptions, types and attributes, @context documents, temporal, /version, and the API plugins' paths. The notifications of a subscription or context source subscription made over the connection come back on it.

Connecting

GET /ngsi-ld/v1/ws on the broker's HTTP port, with Upgrade: websocket (RFC 6455, version 13). Both HTTP servers serve it - libmicrohttpd and the built-in one. The subprotocol ngsi-ld.json may be asked for in Sec-WebSocket-Protocol, and is then confirmed; asking for none is the same.

The broker's first message names the connection:

{ "metadata": { "connection": "urn:ngsi-ld:WebSocket:4ddb4c6be94beb41-7" } }

The id is of this run of the broker - a random part, new at every start, and the connection's number. An id of another run, or of another broker instance on the same store, names no connection.

no Sec-WebSocket-Key; a version other than 13; a subprotocol other than ngsi-ld.json400

Messages

Text messages, each a JSON object with metadata and body - the envelope of the MQTT notification binding (ETSI TS 104 243 clause 5), so a notification over a WebSocket is the one MQTT carries.

A request

Its method and path in metadata, beside the headers HTTP would carry. A requestId, the client's choice, comes back in the response, so several requests may be in flight at once.

{ "metadata": { "method": "POST", "path": "/ngsi-ld/v1/subscriptions", "requestId": "r1",
                "Content-Type": "application/json" },
  "body": { "type": "Subscription", "entities": [ { "type": "Vehicle" } ],
            "notification": { "endpoint": { "uri": "urn:ngsi-ld:WebSocket:4ddb4c6be94beb41-7" } } } }

A response

The status, the requestId and the headers HTTP would return in metadata; the body in body - a JSON body as it is, any other (the text of /metrics) as a JSON string.

{ "metadata": { "status": 201, "requestId": "r1",
                "Location": "/ngsi-ld/v1/subscriptions/urn:ngsi-ld:Subscription:..." } }

A notification

Content-Type and Link in metadata; the NGSI-LD Notification (or ContextSourceNotification) in body.

Errors

A request runs through the same service routines as over HTTP, so what it is refused for, and how, is the same. Over a WebSocket besides:

RefusedStatus
a message that is not a JSON object with a metadata object400
a request without method or path400
a subscription whose endpoint names another connection403

Tenants and headers

A connection has no tenant, and no other NGSI-LD header: every message carries its own, so a message means the same on every connection. A request's tenant is the NGSILD-Tenant in its metadata; without one, the default tenant - as over HTTP.

No NGSI-LD headers on the upgrade. An upgrade request with NGSILD-Tenant, Link or NGSILD-Snapshot is a 400. Put them in each message's metadata - a browser cannot set headers on an upgrade request anyway.

Subscriptions on the connection

A subscription or context source subscription notifies the connection when its notification.endpoint.uri is the connection's id, or urn:ngsi-ld:self. urn:ngsi-ld:self is an alias: the broker stores the id in its place, so the subscription shows the id and is the same as one made with it (Server-Sent Events uses the same value for its streams). A PATCH over the connection may set it too; so may a Service Execution's notification.endpoint (POST /services).

  • A connection is the endpoint only of what is made over it. Another connection's id is refused (403), and so is a connection's id in a subscription made over HTTP or cor:// (400).
  • Periodic subscriptions (timeInterval) are notified on the connection once per interval, with the matching entities as they are then - as over HTTP.
  • Another endpoint is the client's. A subscription made over the connection may notify an http(s) or mqtt endpoint; it is then not tied to the connection.

When the connection closes

The client closes it, it breaks, or the broker stops: the subscriptions that notify it are deleted, each in its tenant - those made over it to notify it, and those changed over it (PATCH) to notify it. One changed since, over HTTP or another connection, to notify elsewhere stays.

A killed broker deletes nothing - until it starts again. A broker that is killed (not stopped), or crashes, leaves its connections' subscriptions in the store. At its next start every subscription, periodic subscription and context source subscription that notifies a connection of another run is deleted, in every tenant. Not with --high-availability: there, a connection of another run may be another instance's, alive. Each instance writes the beat of its run every 10 s in the shared database, and the subscriptions of a run with no beat for 60 s are deleted by any instance alive - 60 to 70 s after the kill (High Availability).

A client that reconnects creates its subscriptions again, and is sent nothing it missed.

How it is built

A WebSocket is a transport: it carries the broker's API, as HTTP and cor:// do. Transports are a plugin kind of their own, loaded from <plugins>/transport/ (Plugin architecture); ws.so is the first.

PartDoes
the pluginthe protocol: the handshake (Sec-WebSocket-Accept, SHA-1 from libcrypto), the frames, its connections - a thread each
the brokerthe messages: it parses a request's envelope, runs it on the connection's thread through the service routines of an HTTP request, answers in an envelope, keeps each connection's subscriptions and delivers their notifications - through the same transport hook mqtt:// goes through
the upgradecorRest finds the Upgrade request, writes the 101 and hands the socket over - libmicrohttpd's upgrade API, or the built-in server's, with the same contract

Not yet

  • a subscription notifying a connection other than its own
  • a second subprotocol, ngsi-ld.cor: binary frames carrying the envelope cor-encoded (The cor format and cor://)
  • cor:// as a transport plugin (cor.so)
