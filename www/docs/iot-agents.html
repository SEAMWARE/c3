FIWARE IoT Agents

What FIWARE's IoT Agents are and how they work - provisioning, the four attribute kinds, commands - and where each of their concepts sits in coraine's model. The background to Speaking to devices directly.

What an IoT Agent is

A translator between a device protocol and NGSI. Devices speak MQTT with UltraLight, CoAP with LWM2M, OPC-UA, LoRaWAN, Sigfox; the agent turns that into entity updates against a context broker, and broker-side writes back into device commands. Nearly all agents are built on iotagent-node-lib, a library: it supplies the provisioning API, the device and group model, the northbound NGSI interactions and the command machinery; each agent adds a southbound binding and a payload codec.

An agent is a southbound adapter, not an NGSI endpoint. It provisions devices and config groups over its own REST API, forwards measurements to a broker (updateContext), and answers broker-initiated requests as a registered Context Provider for lazy attributes and commands. It serves no subscriptions or registrations of its own, hosts no context, answers no queries, has no temporal API. It uses subscriptions and registrations; it does not serve them - without a broker behind it, it does nothing.

The specification's account: Annex G

ETSI TS 104 175, Annex G, Suggested actuation workflows (informative), calls the agent a Context Adapter and gives two models (§ G.4.1):

ModelClausesThe adapter acts asStateDelivery
Subscription / notification§ G.4.2, § G.5"a Context Source as well as a Context Consumer"none of its ownsubscriptions carry command requests to it; it writes the results back

Forwarding is what makes lazy attributes possible: an attribute read only when someone asks, because reading it costs something. Annex G describes workflows built from existing primitives, not a mechanism of the API - the gap NGSI-LD Service Execution closes.

Provisioning

Two resources, both under /iot, both outside NGSI:

ResourceEndpoints
Config groups (formerly service groups)GET / POST / PUT / DELETE /iot/groups
DevicesGET / POST /iot/devices; GET / PUT / DELETE /iot/devices/:deviceId; POST /iot/op/delete for batch removal
  • A config group is identified by an apikey + resource pair, unique. The apikey authenticates requests from devices and says which group they belong to.
  • A group supplies defaults; a device may override them.
  • Multi-tenancy is the FIWARE-Service and FIWARE-ServicePath headers.

This is a device registry - the one concept with no counterpart in a broker.

Four attribute kinds

KindProvisioning keyMeaning
Activeattributesmeasures pushed by the device; the agent sends them to the broker
Lazylazypassive measures pulled on demand - the agent is the registered Context Provider, the broker forwards the read
Staticstatic_attributesfixed values held in the broker, never updated by the device
Commandscommandsactions invoked on the device: the broker writes the attribute, the agent delivers it southbound

Active against lazy is flow against delegation in the agents' own words: active attributes flow through and the broker holds them; lazy ones live at the device and are fetched - the battery level, where polling drains what is measured.

Writing a command attribute triggers its delivery. The agent keeps two attributes per command, named after it:

PUSH or PULL is whether the agent can reach the device or waits for the device to call in. A sleeping, battery-powered or NAT'd device polls: the command is stored until it asks, and expires if it never does. With cmdMode: notification the entity is created at provisioning with its command attributes null - not yet triggered.

Seven, plus iotagent-node-lib itself. The same FIWARE catalogue chapter (Interface with IoT, Robots and Third-Party Systems) holds components that are not IoT Agents: Fast DDS and Micro XRCE-DDS (DDS middleware - coraine's DDS bridge runs on a DDS stack), Oliot (an EPCIS mediation gateway), Kurento and OpenVidu (media streams). There is no CSV or CKAN agent; the CKAN extensions publish a broker's data in CKAN - the opposite direction.

The agents are mostly combinations of two axes - the library configures device communications "regardless of the payload, syntax or transport protocol used": transports (HTTP, MQTT, AMQP, CoAP) and payload codecs (JSON, UltraLight 2.0, LWM2M objects, ISOXML/ADAPT). UltraLight over MQTT and over HTTP are one codec, two transports. LoRaWAN and Sigfox carry network semantics, join procedures and operator back-ends, and do not decompose.

Each agent as a bridge plugin

For each of the seven agents there is a coraine bridge plugin that does the job inside the broker. The six corIota* bridges are prototypes, not released: measures arrive as DataChannel records, written attributes go back to the device, commands are Service Executions where the agent has commands, and each takes what its agent takes, the same way, with the same answers. None of them has the provisioning API yet (/iot/groups, /iot/devices) - a device's DataChannel comes from the --bridgeConfig file. For OPC-UA, the OPC UA bridge plays the part.

In coraine's model

A foreign endpoint tied to an attribute is a channel on a bridge (a transport instance); a device's measures are DataChannel records; a command is a Service Execution; a value fetched on read is an ordinary registration whose endpoint names a bridge scheme. The rows marked design are designs, not built:

Agent conceptcoraine
Active attribute (a measure)a DataChannel record (design - IoT Agent measures)
Commanda service of the device's entity; running it is a Service Execution, the bridge plugin its executor (design - IoT Agents as Service Executors)
Lazy attributea registration with a bridge-scheme endpoint - the broker holds nothing and fetches on read
Static attributean ordinary attribute; a DataChannel mapping's constant
Config group + devicea DataChannel per group and per device (measures), a Service Registration per command; the provisioning API that creates them is a change of its own
<cmd>_status / <cmd>_infonone: the execution's executionStatus and executionOutput

Not verified

  • The library's own transport bindings: HTTP and MQTT are documented on the agents; AMQP appears in the ecosystem, not confirmed from primary documentation.
  • NGSI-LD support: the library is described as working with NGSI-v2 and NGSI-LD; how that is selected is not confirmed.
  • Whether every agent above is maintained, and at what NGSI version - the list is the FIWARE catalogue's.
  • Provisioning payload details beyond the attribute kinds (entity_name, entity_type, timezone, expressionLanguage, transformation expressions), and the southbound details of any one agent.
