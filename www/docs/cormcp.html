corMcp - an MCP server for NGSI-LD brokers

corMcp gives an AI model read access to an NGSI-LD context broker through the Model Context Protocol: the model asks in tools - "the vehicles faster than 90 km/h near Sol" - and corMcp makes the NGSI-LD requests, GET /entities?type=Vehicle&q=speed>90&georel=.... It works with any NGSI-LD broker over HTTP.

How it fits

The model never runs in corMcp: it runs at its provider, and an MCP host - the application the user talks to, Claude Code for example - starts corMcp and passes it the model's tool calls. corMcp turns each call into one NGSI-LD request to the broker and gives the answer back, shaped for a model.

  • Transport: stdio. One JSON-RPC message a line on stdin, the answers on stdout, the log on stderr.
  • One session, one broker. A session is bound to one broker, one tenant, one @context and one token, all chosen when corMcp is started. No tool takes a tenant or an @context: the model cannot reach a tenant the user did not choose. Another tenant is another corMcp, which only the user starts.
  • Read-only. Every tool is a GET; each is announced with readOnlyHint: true and openWorldHint: false. Nothing a model asks for changes the broker.
  • Any broker. Only the NGSI-LD API (ETSI TS 104 175) at <broker>/ngsi-ld/v1; a tool whose API the broker lacks (a broker with no temporal API) answers the broker's error.

Building and installing

corMcp is built on the Cor-Libs, as coraine is - sibling checkouts (../corRest, ../corJson, ...), each built with make in it. It links corRest, corJson, corTree, corArgs, corLog, corAlloc and corBase, and OpenSSL and zlib.

for r in corBase corLog corAlloc corArgs corTree corJson corRest corMcp; do
  git clone https://github.com/SEAMWARE/$r
done
for r in corBase corLog corAlloc corArgs corTree corJson corRest; do make -C $r; done
cd corMcp
make                  # ./corMcp
make install          # /usr/local/bin/corMcp (PREFIX=..., DESTDIR=...)

COR_LIBS=<dir> for Cor-Libs checked out elsewhere; BUILD=debug for -g -O0.

Options

corMcp --broker http://localhost:1026 [--tenant T] [--context URL] [--token-env VAR] [--limit-max N]
OptionWhat it does
--broker, -b <url>CORMCP_BROKERthe broker's base URL, http:// or https://, without /ngsi-ld/v1 - required
--tenant, -t <tenant>CORMCP_TENANTthe tenant every request goes to (NGSILD-Tenant) - default: the broker's default tenant
--context, -ctx <url>CORMCP_CONTEXTthe @context the short names (Vehicle, speed) expand with, sent as Link - default: the core context
--token-env, -te <var>CORMCP_TOKEN_ENVthe environment variable that holds a bearer token, sent as Authorization: Bearer. The token itself is never a command-line argument; a variable that is not set stops the start
--limit-max, -lm <n>CORMCP_LIMIT_MAXthe largest limit a tool call may ask for, 1 - 1000 (default 100); a larger one is lowered to it

Each option can also be set in the environment, by the name beside it; the command line wins.

The tools

ToolNGSI-LD requestFor
list_typesGET /types?details=truethe entity types and their attribute names - where a model starts
list_attributesGET /attributes?details=true, or with type GET /types/{type}the attribute names, their kinds (Property, Relationship, GeoProperty, ...) and the types that have each
query_entitiesGET /entitiesthe entities that match: type, ids, idPattern, q, scopeQ, geoQ, csf; pick, omit, datasetId, lang, format; limit, offset
get_entityGET /entities/{id}one entity by its id - also how a Relationship is followed
count_entitiesGET /entities?count=true&limit=0how many match the same filters - no entities returned
temporalGET /temporal/entities[/{id}]history: timerel and timeAt (required), endTimeAt, timeproperty, lastN, attrs; aggregation with aggrMethods and aggrPeriodDuration; one entity by id, or the filters
list_subscriptionsGET /subscriptionswhat each subscription watches, where it notifies, its status
query_registrationsGET /csourceRegistrationswhich context sources hold which entities - NGSI-LD wants at least one filter (§ 5.10.2.4)

geoQ is an object - { "georel": "near;maxDistance==2000", "geometry": "Point", "coordinates": [2.2945, 48.8584] }, with an optional geoproperty - sent as the four URL parameters. A list argument (type, ids, pick, attrs, ...) is a string or an array of strings, joined with commas. Each tool's description - what the model reads - says what it is for and shows the NGSI-LD syntax it must write (q's operators, ranges, regular expressions, sub-attributes); the server's instructions at initialize say what an NGSI-LD broker holds and name the session's broker and tenant.

What a tool returns

  • Concise by default for the entity tools - lossless: sub-attributes, unitCode, observedAt, datasetId, Property and Relationship all kept. format: simplified (options=keyValues, the values alone) or normalized when the model asks. temporal is normalized by default (or temporalValues, concise); with aggrMethods, options=aggregatedValues.
  • pick always keeps id and type.
  • A list is { count, returned, more, <items> }, limit 20 by default; the count is always asked for (count=true), and more says whether to page with offset.
  • A string longer than 1000 characters and an array longer than 100 items are cut, with a marker: …[+513 characters cut], …[+51 items cut].
  • The result is structuredContent, and the same JSON, compact, as the text content.
  • A broker error is a tool error (isError) with the broker's status, type, title and detail - text a model can act on. A bad argument too: 'limit' must be an integer, 1 or more. A broker that does not answer: the broker at <url> did not answer: ....

Configuring a model client

An MCP host starts corMcp as a command with arguments. Claude Code:

claude mcp add ngsild -- corMcp --broker http://localhost:1026

A host configured with a JSON file of servers takes the same command, arguments and environment - with a tenant and a token, for example:

{
  "mcpServers": {
    "ngsild": {
      "command": "corMcp",
      "args": [ "--broker", "https://broker.example.org", "--tenant", "city", "--token-env", "BROKER_TOKEN" ],
      "env": { "BROKER_TOKEN": "..." }
    }
  }
}

The token reaches corMcp through the variable that --token-env names, so it is in no process list. The broker decides what the token allows; corMcp only reads.

The protocol

MCP revisions 2025-11-25, 2025-06-18, 2025-03-26 and 2024-11-05: initialize answers with the client's revision when corMcp speaks it, else the newest. Methods: initialize, ping, tools/list, tools/call; notifications (notifications/initialized, ...) are accepted and not answered. No batches - one JSON-RPC object a message, as MCP has it since 2025-06-18. The JSON-RPC errors: -32700 (parse), -32600 (invalid request), -32601 (an unknown method), -32602 (an unknown tool, a tools/call without a name).

Every request to the broker carries Accept: application/json, and the session's NGSILD-Tenant, Link and Authorization when set; the timeout is 30 s. The log has one line per tool call: the tool, its arguments, ok or error, the milliseconds.

An example session

By hand, as a host would - each line one message on corMcp's stdin:

corMcp --broker http://localhost:1026
# stderr: corMcp 0.1.0 - broker http://localhost:1026, tenant (default), http backend, stdio
{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2025-06-18","capabilities":{},"clientInfo":{"name":"me","version":"0"}}}
{"jsonrpc":"2.0","method":"notifications/initialized"}
{"jsonrpc":"2.0","id":2,"method":"tools/list"}
{"jsonrpc":"2.0","id":3,"method":"tools/call","params":{"name":"list_types","arguments":{}}}
{"jsonrpc":"2.0","id":4,"method":"tools/call","params":{"name":"query_entities","arguments":{"type":"Store","q":"stock<10","pick":["stock"],"limit":5}}}

The answer to initialize carries serverInfo (corMcp, 0.1.0), the tools capability and the instructions; tools/list the eight tools with their input schemas. Call 4 becomes

GET /ngsi-ld/v1/entities?type=Store&q=stock%3C10&pick=stock,id,type&options=concise&limit=5&count=true

and its result is { "count": ..., "returned": ..., "more": ..., "entities": [ ... ] }, as structuredContent and as text. In a host, the same happens behind a question in plain language: the model reads the instructions and the descriptions, calls list_types, then the tool that answers.

Tests and evaluation

BROKER_URL=http://localhost:1026 make test

The tests make entities of their own (a type with a per-run suffix), check every tool and the protocol errors, and delete the entities. A check the broker cannot pass (a broker with no temporal API) is reported as skipped, with the broker's answer.

eval/ measures how well a model answers with corMcp's tools - what the descriptions teach it. Two sets of fixed data, each in a tenant of its own, and questions in plain language, each asked in a fresh conversation: fleet (Madrid: vehicles, depots, parking spots, air-quality stations with a day of history, a subscription - 32 questions) and building (Berlin: offices, rooms, HVAC units, energy meters with a day of history - 21 questions). No example in the tools' descriptions comes from either set.

ANTHROPIC_API_KEY=... python3 eval/run.py --broker http://localhost:1026 [--set fleet,building] [--model M]

Each answer is scored right or wrong against answers computed from the data, with the tools a good answer uses and the tool calls against a budget; tokens and seconds are recorded, in eval/results/<time>-<provider>-<model>[-label].json. --rescore <file> scores a run again without calling the model.
