corLibs - the umbrella

corLibs holds no library. It holds what assembling the stack takes: which repositories make it up and in which order they build (bootstrap.sh, the makefile), and the environment that build needs (the CI image every cor repository's CI runs in).

Siblings, not subdirectories

Every library is a repository of its own, and they sit side by side under one parent directory - by default ~/git. The include paths and the link lines resolve each other as ../<name> (-I.., ../corTree/libcorTree.a), so the layout is part of the build contract. corLibs drives the siblings; it does not vendor them.

~/git/
├── corLibs        the umbrella: bootstrap.sh, makefile, iter.sh; collects into bin/ and lib/
├── corBase  corLog  corAlloc  corArgs  corHash  corTree  corJson  corProm
├── corHttp  corBridge  corRest  corJsonld  corPlugin  corNgsild
├── corDB                                  the in-process database plugin
├── corTools  corTest                      the tools and the test runner
├── corDdsBridge  corModbusBridge  corMqttBridge  corCkanBridge  corOpcuaBridge
└── coraine                                the broker

bootstrap.sh

Clones every repository of the stack beside corLibs - or, for one already there, fetches, checks out its ref and fast-forwards (pull --ff-only, never a merge) - then builds and installs the whole stack with make di in the umbrella. The base directory is the parent of the script's own checkout, so a clone anywhere works.

git clone https://github.com/SEAMWARE/corLibs.git
./corLibs/bootstrap.sh                 # clone or update, then build
cd coraine && make di                  # the broker - coraine itself is not cloned by it

Building the stack

The umbrella's COR_DIRS is the build order, and make <target> runs the target in each directory in that order, stopping at the first failure:

corBase corLog corAlloc corArgs corHash corTree corJson corProm corHttp corBridge corRest corJsonld corPlugin
corNgsild corDB corTools corDdsBridge corModbusBridge corMqttBridge
  • corBase first - it needs nothing; then the log, the allocator, the command line, the hash tables, the tree, JSON and the metrics.
  • corHttp before corRest, which links it on a COR_HTTP_SERVER=builtin build.
  • corDB is built against coraine's plugin interface: without a coraine checkout beside it, it skips itself and says why - coraine's own make di builds it then.
  • corTools after the libraries: its tools link the whole stack.
  • corDdsBridge gates itself: built where the DDS Enabler is installed, skipped with the reason where it is not; COR_BRIDGE_DDS=ON makes a missing dependency an error. corModbusBridge needs nothing beyond libc, corMqttBridge libmosquitto - both always built.
  • corCkanBridge and corOpcuaBridge are cloned and not built here: coraine-build --bridges builds them. corTest is cloned and not built - its runner and helpers are scripts, copied by install.

./iter.sh '<command>' runs a command in each library directory - ./iter.sh 'git log --oneline -1'. It reads the list from the makefile's COR_DIRS.

What install collects

lib/every lib*.a and lib*.so of every directory in COR_DIRS (a bridge's .so is a plugin, not a lib*, and is not collected)
bin/from corTest: corTest, corTestFunctions.sh, corDiff, corDiffGui, corRegenExpect; from corJson: corJson (corTest sorts every JSON response with it and refuses to run without it - a warning when it is not built); from corTools: corRequest, corTestClient, and corMongoDrop where it was built

coraine's test target runs ~/git/corLibs/bin/corTest (Testing); the tools in bin/ are described in corTools.

Versions: what is pinned, and where

The cor repositories are not pinned against each other. Every one tracks main: they move together, and a pin between them would only be stale. The umbrella builds whatever each sibling has checked out (make branch shows it). What a release contains is recorded the other way round: cutting a coraine release tags every Cor-Lib, and corDB, corTools, corTest, corLibs and the DDS, Modbus and MQTT bridges, v<version> at the exact commit the release was built from: the linked libraries at the commits GET /version reports, the others at the commits the release build checked out.

The external dependencies are pinned, in the CI image (docker/Dockerfile.ci, published as quay.io/seamware/coraine-ci):

DependencyPin
the baseubuntu:26.04 by digest, not by tag - the broker's runtime image is ubuntu:26.04 too
the mongo-c driverMONGOC_VERSION=2.2.2, built from source (pkg-config mongoc2)
libmicrohttpdMHD_VERSION=1.0.10, built by tools/mhd/mhdBuild.sh (below)
the eProsima DDS stacknot named in the image: fetched from corDdsBridge's ddsenabler-pinned.repos, which pins releases, not branches, and built with colcon
the image itselfeach repository's CI names a dated tag (coraine-ci:<date>-<commit>), never a moving one: a red run is then a change in that repository, not in the image

The image also carries what the test harness shells out to - python3, jq, psql, mongosh, mosquitto (the daemon: the MQTT tests start their own), procps and psmisc (pkill, killall), socat - and checks at build time that every one is there. Dockerfile.ci-nightly is built FROM it and adds what only the nightly jobs need: valgrind, gcovr (pinned, 8.6), wrk. Dockerfile.mongo-rs is mongo:8.2 started as a one-member replica set, for the cache-sync tests that need a change stream. The baseimage.yml workflow builds them on a pull request that touches them, and publishes on a push to main.

tools/mhd - libmicrohttpd, checked and patched

MHD_VERSION=1.0.10 tools/mhd/mhdBuild.sh --sudo           # a workstation: /usr/local, sudo make install
tools/mhd/mhdBuild.sh --prefix /opt/mhd -- --disable-https

The one place the stack builds libmicrohttpd from - the CI image, coraine's published image and a bare CI runner run it. It downloads the release tarball from ftp.gnu.org and accepts it only with the SHA-256 recorded in the script for that version (1.0.2 and 1.0.10 today), then applies every patch in patches/<version>/ in name order. 1.0.10 carries one, 0001-header-value-fastpath.patch: a header value's plain characters skipped in one loop; a patched library behaves as the release does, and coraine works unchanged on an unpatched one. Options: --prefix (default /usr/local), --sudo, --keep (leave the build directory), and after -- options for ./configure.

The lists a repository is in

A repository added to the stack, or renamed, is a change in each list that names the repositories - one left out fails a build far from the change:
