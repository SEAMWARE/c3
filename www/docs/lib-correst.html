corRest - the REST layer

corRest turns HTTP requests into calls of service routines and their trees back into responses: a flat service table, a per-request state, a pipeline of hooks the application fills, a worker pool and coroutines for the requests that wait. It also carries the broker's clients - HTTP and HTTPS, a parallel multi-client, and cor://. Its HTTP server is libmicrohttpd or the built-in one of corHttp, chosen at build time. It is the transport layer under coraine and has no NGSI-LD dependency of its own.

Services and routes

An application hands corRest a flat array of CorRestServiceSimplified - a verb, a URL pattern, a routine, the URL parameters it accepts, and optionally a body validator and option bits. corRestInit() splits it into one vector per verb and prepares each pattern for matching.

#include "corRest/corRest.h"
#include "corTree/corTreeBuilder.h"

#define P_TYPE   (1ULL << 0)
#define P_LIMIT  (1ULL << 1)

static CorRestParam paramV[] = { { "type", P_TYPE }, { "limit", P_LIMIT }, { NULL, 0 } };

static bool thingGet(void)
{
  const char* id    = corRest.in.wildcard[0];                // the '*' of the pattern
  const char* limit = NULL;

  for (int i = 0; i < corRest.in.uriParamCount; i++)
    if (corRest.in.uriParamV[i].bit == P_LIMIT)
      limit = corRest.in.uriParamV[i].value;

  if (strcmp(id, "urn:none") == 0)
  {
    corRestProblem(404, COR_REST_ERROR_NOT_FOUND, "Not Found", "no thing '%s'", id);
    return false;
  }

  corRest.out.responseTree = corTreeObject(corRest.kallocP, NULL);   // rendered to JSON by corRest
  corTreeChildAdd(corRest.out.responseTree, corTreeString(corRest.kallocP, "id", id));
  if (limit != NULL)
    corTreeChildAdd(corRest.out.responseTree, corTreeString(corRest.kallocP, "limit", limit));
  corRestOutHeaderAdd("Cache-Control", "no-store");
  return true;
}

static CorRestServiceSimplified serviceV[] =
{
  { CorVerbGet, "/things/*", thingGet, P_TYPE | P_LIMIT },
  { CorVerbGet, "/files/**", fileGet,  0                },
};

int main(void)
{
  corRestParamInit(paramV);                                   // before corRestInit
  if (corRestInit(serviceV, sizeof(serviceV) / sizeof(serviceV[0]), 1026, 4) != 0)
    return 1;
  pause();                                                    // the servers run on threads of their own
  corRestStop();
}
Rule
wildcards* is one path segment - an id in URL form (https://...) included; a last ** is greedy, the rest of the path. At most three, read in corRest.in.wildcard[]. Patterns are matched by character sums and pre-computed offsets, not strcmp on every route.
HEAD, OPTIONSevery GET also serves HEAD (the body suppressed); every path gets an OPTIONS with its Allow
404, 405a path no route matches is a 404; a path registered for other verbs a 405 with Allow; an empty segment (//) a 400; a method that is no HTTP method a 400
URL parametersregistered with corRestParamInit / corRestParamAdd, each a name and a bit. A parameter not in the route's supportedParams is a 400 InvalidRequest; ~0 accepts any. Each parameter carries its bit, and corRest.in.uriParamMask is their OR. ?pretty=N is taken out before the check and indents the JSON.
a second listenercorRestListen(host, port, serviceV, n): plain HTTP, routes of its own, corRest.listener 1 - libmicrohttpd only

corRestPrepare() + corRestStart() are corRestInit() in two steps: between them, corRestRunJson() runs requests through the services and no client can - start-up work clients must not see half done goes there.

The request - corRest

A service routine takes no argument: it reads and writes corRest, the CorRestState of the request bound to the running thread. corRest is a macro over a thread-local pointer, corRestP, which the backend binds to the request's state - so a request handed to a worker, or a coroutine that yields and resumes, keeps its own state.

Member
corRest.inverb, urlPath, the raw query, wildcard[], uriParamV, httpHeaderV (corRestInHeader(name), without case), the payload and its parsed requestTree, contentMime, accept
corRest.outhttpStatusCode (200 by default), responseTree or a ready payload, headerV (corRestOutHeaderAdd), the problem details
corRest.kallocPthe request's allocator - an 8 KiB inline buffer, then chunks - bulk-freed when the request is over. Every tree of the request is built in it.
corRest.userDatathe application's state per request, made and freed by corRestSetUserDataHooks

Errors are RFC 9457 problem details: corRestProblem(status, type, title, fmt, ...) sets them and logs the error with the caller's file and line; corRest builds the body - type, title, status, detail, and out.problemExtras' members. A routine that sets a problem and no status is answered 500. A problem found under the routine after it has its answer - a store that cannot keep a write, found as its lock is released - is raised with corRestProblemLate(status, type, title, fmt, ...): after the routine returns it replaces the answer - the status and the problem - and drops the body, a stream and the headers the routine added. The first late problem of a request is the one answered; each is logged.

The pipeline and its hooks

corRestProcessRequest() runs a request in this order. Each step is the library's, or a hook the application sets; an unset hook does nothing.

  1. pre-dispatch hook - reset the application's per-request state.
  2. the answers decided before the body: 411 (a POST, PUT or PATCH without Content-Length), 413 (a Content-Length over corRestSetMaxRequestSize, 2 MiB by default), an upgrade refused.
  3. the route, looked up in the verb's vector.
  4. admit hook (corRestSetAdmitHook) - is the request let in at all, before any 404, 405 or 415: an auth plugin's place. Not asked for an in-process forward.
  5. 415 - a POST, PUT or PATCH body that is not application/json or application/ld+json (PATCH also application/merge-patch+json).
  6. pre-parse hook, the JSON parse (corJson) into in.requestTree, parse hook. A body that arrived as a tree (cor://) is not parsed; the key hook the pre-parse hook set is replayed over it.
  7. 404, 405 - here, so that an unknown path costs no more.
  8. the URL parameters, each checked and passed to the param hook.
  9. pre-service hook - tenant resolution and the like; false skips the routine.
  10. a POST, PUT or PATCH under /ngsi-ld/ (or with an ldOp) without a valid JSON body: 400.
  11. the route's payloadCheck, then the service routine.
  12. render hook - always, so that an Accept that cannot be met answers 406 over an earlier error; then the problem body and the JSON render (?pretty indents).
  13. the response is sent; then the post-response hook - a write's notifications - and the arena is released.

Hooks that decide where a request runs: corRestSetInlineHook, corRestSetCoroutineHook, corRestSetFinishInlineHook, corRestSetFinishCoroutineHook (below). Others: corRestSetServiceInitHook (once per route at init - corNgsild caches per-route checks of the wildcards), corRestSetUpgradeHook, corRestCorsConfig, corRestSetPrettySpaces. corRestPreDispatchHookGet() and corRestPayloadRenderHookGet() return the hook in place, for a second one to chain on.

In coraine, corNgsild sets the pre-dispatch, parse, render and param hooks and the user-data hooks; the broker sets the pre-service, post-response, service-init and the four placement hooks, and chains its own on the pre-dispatch and render hooks; an auth plugin's authenticate runs in the admit hook.

Where a request runs - workers, async, coroutines

The application says what can wait; corRest decides where that runs. corRestInit(..., poolSize) starts poolSize workers - one queue per event loop of the backend, so a request stays on one loop's threads end to end - before the HTTP server, so no connection is accepted while the pool is down.

No hook keeps the safe choice: every request to a worker, no coroutines. corRestDispatchCounts() counts the requests run inline and handed off. coraine's pool size, with --connectionPoolSize 0 (the default): one per CPU for a store that never waits (corDB, ramDB) and no distributed operations, else 32.

A coroutine yields only where corRest waits. Every wait of corRest's clients is corRestWaitFd(fd, events, timeoutMs, &revents) - poll() on a worker, a yield to the loop's epoll in a coroutine - and a host name is resolved by corRestResolve() on a thread of its own while the coroutine waits. A wait inside another library (a database driver's, a condition variable) stops the whole loop: that is why the coroutine hook is the application's. And no lock may be held across a wait - another coroutine of the same thread that wants it would wait for ever. Coroutines.

The HTTP client

A client of its own, on sockets and OpenSSL: keep-alive pooling per host, TLS, redirects, timeouts, an HTTP proxy. One corRestClientInit(maxIdleConns, idleTimeoutSec, userAgent) per process.

CorRestClientRequest  req;
CorRestClientResponse resp;

corRestClientRequestInit(&req, CorVerbGet, "https://cs.example.org/ngsi-ld/v1/entities/urn:E1", corRest.kallocP);
corRestClientRequestHeader(&req, "Accept", "application/json");
corRestClientRequestTimeout(&req, 1000, 3000);              // connect, whole request - ms

if (corRestClientSend(&req, &resp) != CORR_OK)
  COR_W("%s: %s", req.url, resp.errorDetail);                // CORR_ERR_CONNECT, _TIMEOUT, _TLS, ...
else
  use(resp.statusCode, resp.body, corRestClientResponseHeader(&resp, "Content-Type"));

corRestClientResponseCleanup(&resp);
  • The response is its own copy - status text, headers, body (zero-terminated) - in the request's allocator, valid after the connection went back to the pool. Without an allocator it is malloc'd and freed by corRestClientResponseCleanup.
  • Defaults: connect 5000 ms; the request corRestClientDefaultRequestTimeoutMs (5000; coraine's --distOpTimeout - its notifications and @context downloads set 10 s of their own); up to 5 redirects (301, 302, 307, 308).
  • Addresses: every address the name resolves to is tried in turn - localhost often resolves ::1 first while a listener is IPv4 only.
  • TLS: corRestClientTlsInsecureSet(true) accepts a certificate that does not verify (coraine's --insecureNotif).
  • Proxy (COR_WITH_CLIENT_PROXY, on by default): none until corRestClientProxyFromEnv() (https_proxy, http_proxy, no_proxy, lower case first) or corRestClientProxySet(). https goes through a CONNECT tunnel, http to the proxy with the absolute URI; a user and password are sent as Proxy-Authorization: Basic.

Many requests at once

The multi engine sends N requests on non-blocking sockets and collects them together - one epoll, one deadline - for a fan-out: corNgsild's distributed operations use it.

CorRestClientMulti* mP = corRestClientMultiCreate(n);
corRestClientMultiMaxResponse(mP, 16 * 1024 * 1024);          // a body past it: CORR_ERR_TOO_LARGE, not read

for (int i = 0; i < n; i++)
  corRestClientMultiAdd(mP, CorVerbGet, urlV[i], headerV, headers, NULL, 0, corRest.kallocP, NULL);

corRestClientMultiPerform(mP, 5000);                          // returns how many are done

for (int i = 0; i < n; i++)
{
  CorRestClientResponse* rP = corRestClientMultiResponse(mP, i);
  if (rP->error == CORR_OK)
    merge(rP->statusCode, rP->body);
}

corRestClientMultiDestroy(mP);

cor://

The broker's API over the cor binary format (The cor format and cor://): the same requests and the same service routines, but a request's body arrives as the tree the routine works on and the response leaves as the tree it built - no JSON parse or render on either side (corRest.out.noRender). A frame is a 16-byte header (magic, type, a correlation id, the length) and one tree; a connection opens with HELLO / HELLO_ACK, which compare the two ends' core-term tables - corRestCorInit(codecP, namespaceV, namespaces, termCount) sets them.

Side
corRestCorListen(port, loops)the server: event loops, a listener dealing connections out in turn. A connection is armed once and multiplexed - the loop decodes every request frame as it comes, runs it inline or as a coroutine, and queues each response as it finishes. A request that can wait and does not run as a coroutine (the hook says no, or the loop is at its cap) moves its connection to a thread of its own.
corRestCorSend(...)one request, blocking (yielding in a coroutine); false on a transport failure - an HTTP error status is a response
corRestCorStart / corRestCorWaita fan-out: every request started, then each waited for - in flight at once on the thread's connection to each peer. Every call started is waited for, once, on the thread that started it.
CorRestCorResponse resp;
const char*        error = NULL;

if (corRestCorSend("cor://broker2:1027", CorVerbGet, "/ngsi-ld/v1/entities/urn:E1?options=keyValues",
                   NULL, 0, NULL, NULL, 3000, corRest.kallocP, &resp, &error) == false)
  COR_W("cor://broker2:1027: %s", error);
else
  use(resp.status, resp.bodyTree);                            // the peer's tree, in corRest.kallocP

The HTTP backends

Two, exactly one in a build: make COR_HTTP_SERVER=mhd (libmicrohttpd, the default) or COR_HTTP_SERVER=builtin (corHttp). The service table, the pipeline, the worker pool and the response headers - their set and their order - are one implementation for both. What differs: TLS and a second listener are libmicrohttpd's only; event loops (corRestHttpLoopsSet, coraine's --httpLoops), coroutines and the inline post-response phase are corHttp's only; libmicrohttpd's memory per connection is corRestConnectionMemorySet. A build asked for TLS without it refuses to start.

  • libmicrohttpd runs its own pool of epoll threads and finishes a request (the post-response phase) on its I/O thread.
  • corHttp runs corRestHttpLoopsSet(n) loops - called before corRestInit, 1 by default, clamped to 1-64. Each loop has its own epoll, its own share of the connection slots and its own resume queue; the first loop alone listens and deals the connections out in turn, and a connection stays with its loop for its whole life. A stop wakes every loop at once. Measured 2026-09-15 on 8 cores with 319-byte responses: one loop used 4.4 of the cores and libmicrohttpd 7.9, at 70.7 us per request against 89.0.

Building

make                              # libcorRest.a and .so, and the test server corRestTest
make COR_HTTP_SERVER=builtin      # corHttp instead of libmicrohttpd
make di                           # debug + install
make clientLifetimeTest           # a client response's lifetime, under AddressSanitizer
make COR_WITH_CLIENT_PROXY=0      # without the client's proxy
make COR_WITH_COR_PROTOCOL=0      # without cor://
make COR_WITH_STREAM=0            # without streamed responses

Sibling repositories, linked as ../<lib>/lib<lib>.a; the system libraries are OpenSSL (ssl, crypto), pthread, libm, and libmicrohttpd in an mhd build. With COR_HTTP_SERVER=builtin a consumer links ../corHttp/libcorHttp.a as well - an archive cannot hold another one. test/funcTests/ runs a handful of cases against corRestTest; the rest is tested through coraine's functional suite.
