Testing

How to run coraine's functional tests, how the harness reads a test, and how to write one - plus the sanitizer, soak and pre-release runs a release is checked with.

Everything here assumes a build - Building from source. The functional tests are under test/funcTests/cases/, and run through corTest, which the corLibs umbrella installs as ~/git/corLibs/bin/corTest.

Running the suite

# the whole suite, from the coraine checkout - on MongoDB (mongoc)
make test

# on corDB, the in-process store
~/git/corLibs/bin/corTest -db corDB

# a part of it
corTest cases/create_entity.test       # one file
corTest --match subscription           # the tests whose --NAME-- matches
corTest --tags geo,temporal            # the tests with one of these tags
corTest --fromIx 120                   # from index 120 on

A test prints one line: index/total/failures-so-far, its name, and OK or FAIL: <reason> with its time. corTest exits 0 when every selected test passed, 1 otherwise. Each test starts the broker (or several) it needs and stops it at the end, so a broker that dies costs one test, and --fromIx resumes a run where it stopped.

How long it takes

The whole suite - 732 tests - takes 14.5 minutes on mongoc (868 s, 2026-10-02, on the machine of doc/performance.md). The fixed cost of a test:

stopping the broker~0.15 s with mongoc (its own close), ~0.01 s with corDB
waiting for its port at start-upup to 0.02 s - polled every 20 ms
dropping the database~0.008 s with corMongoDrop (corTools: one libmongoc connection)

Where corMongoDrop is not built (no libmongoc on the machine) the drop falls back to mongosh: ~0.3 s a drop, and the suite drops 1 466 times.

Over cor://

COR_TRANSPORT=cor ~/git/corLibs/bin/corTest -db mongoc

Every test it can runs on the broker's binary API instead of HTTP: each broker also listens on cor:// (its HTTP port + 1000), and corCurl sends the request with corRequest --curl, which prints what it prints for an HTTP request - every expectation holds unchanged. What only HTTP carries stays on curl: a body that is not JSON, a text answer, HEAD, a POST without a body (411), a method the broker does not have, a body over 1 MiB (413). COR_TRANSPORT_TRACE=<file> logs which transport each request took. The whole suite passes this way; it saves no measurable time - a request is a process start either way. The cor format and cor:// has the protocol.

corDB in the suite is persistent

With -db corDB every broker has --dbDir: a directory per role under COR_DB_PERSIST_DIR (default /tmp/corTest-dbDir). As with MongoDB, a (re)start keeps what is there and corDbDrop empties it, so every write of the suite goes through corDB's log. A test that gives its broker a --dbDir of its own keeps it.

How corTest reads a test

corTest is a generic harness for any program that writes to stdout - it knows nothing about HTTP or brokers. For each .test file it:

  1. splits the file into its sections and writes --INIT--, --RUN-- and --TEARDOWN-- out as scripts of their own (run with bash);
  2. runs --INIT--, then --RUN--, capturing its stdout into <test>.out;
  3. compares the .out with --EXPECT-- using corDiff;
  4. runs --TEARDOWN--.

Each section is a separate process. A shell variable set in --INIT-- is not there in --RUN--; what a later section needs is written to a file, or set up again.

The repository plugs in its own verbs: test/funcTests/corTestFunctions.sh (sourced before each section - coraineStart, corCurl, corDbDrop, ...) and test/funcTests/corTestParams.sh (the options above).

After a failure

A passing test leaves nothing behind. A failing one keeps its files next to the .test:

<test>.outthe captured stdout of --RUN--
<test>.diffa unified diff of expected against actual, numbered by the expected lines, each hunk headed by its step; a line its REGEX(...) matches is not a difference
<test>.run.stderrstderr of --RUN--
<test>.init.stderr, .teardown.stderrstderr of setup and cleanup

Writing a test

The first step of cases/create_entity.test:

--NAME--
Create entity and retrieve it

--TAGS--
create entity

--INIT--
corDbDrop
coraineStart

--RUN--
echo "01. Create entity with id, type, and two properties"
echo "==================================================="
payload='{
  "id": "urn:ngsi-ld:Vehicle:A001",
  "type": "Vehicle",
  "speed": { "type": "Property", "value": 120 },
  "color": { "type": "Property", "value": "red" }
}'
corCurl --url /ngsi-ld/v1/entities --payload "$payload"
echo
echo

--EXPECT--
01. Create entity with id, type, and two properties
===================================================
HTTP/1.1 201 Created
Date: REGEX(.*)
Location: /ngsi-ld/v1/entities/urn:ngsi-ld:Vehicle:A001
Content-Length: REGEX(\d+)




--TEARDOWN--
coraineStop
corDbDrop
Section
--NAME--the test's name - required
--INIT--setup - optional
--RUN--the commands whose stdout is compared - required
--EXPECT--the expected stdout - required
--TEARDOWN--cleanup - the marker is required, its content is not
--TAGS--tags for --tags / --skip-tags - optional

A test without a --TEARDOWN-- marker is refused before it runs. State left behind - a server, a database - surfaces as another test's failure, so "nothing to tear down" is an empty section, never a missing one.

Matching what varies

--EXPECT-- is not compared byte for byte:

  • REGEX(pattern) matches dynamic content - a date, a generated id, a length - alone on a line or inside one: "id": "REGEX(urn:ngsi-ld:.+)".
  • #SORT_START ... #SORT_END compares the lines between them in any order, for output whose order is not guaranteed. The two combine.

No top-level | in a REGEX. The pattern is spliced into the line's pattern unbracketed, so x: REGEX(true|false) becomes x:\ true|false: it accepts one branch and rejects the other. Write REGEX([a-z]+).

corTest --regen cases/new.test fills an empty --EXPECT-- from the captured output; coraine's regenerator (test/funcTests/tools/corRegenExpect) turns the process- and run-volatile tokens into REGEX(...). Read what it wrote before committing it.

When a test applies

A comment anywhere in the file decides whether a test is in the run:

MarkerWhat it does
# REQUIRE_<TAG>: a bthe test applies only when that option holds one of the values - REQUIRE_DB: corDB mongoc is either. Otherwise it leaves the run list, and is not counted as skipped
# SKIP_<TAG>: a bthe test applies, and is skipped - and reported so - for these values
# SKIP_VALGRIND: onskipped in a -vt run: a test that kills its broker with a signal on purpose, or reads its threads in /proc
# REQUIRE_FEATURE: A Bapplies only if the build has all of them
# SKIP_FEATURE: A Bapplies only if the build has none of them - a test of the 501 of an endpoint compiled out

The features come from COR_TEST_FEATURES, which corTestParams.sh sets by asking the binary what it was built with. Unset, both feature markers are inert and every test runs.

A test never reads the broker's log

A test waits on, and asserts on, what the API says. A trace line is there only when the trace levels include it and the code was built with its traces - a test waiting on one times out against a build without them while the broker works. No test sets COR_TRACE_LEVELS, and the suite passes with -traceLevels "". A warning (COR_W) is different: no trace level or build switch turns it off, and a test may check one was given.

For what happens after the response, corTestFunctions.sh has helpers that poll the API - for an attribute member a bridge writes (attrMemberAwait), a bridge's counters and dropped samples (bridgeChannelAtLeast, bridgeAtLeast), a DDS endpoint discovered (ddsServiceAwait), a goal ended (bridgeGoalEndedAwait) or its temporal history (bridgeGoalHistoryAwait).

Tests that need what a machine may not have

corTest detects these, and the tests apply or not - nobody has to remember a flag:

NeedsDetected asWhere it is not
a mongo replica set - the HA cache sync rides a change stream-ha yesa standalone mongod
the DDS bridge and a real ROS 2 publisher-dds yesa GitHub runner

bridge_dds_ros2_roundtrip is the one test with a real DDS system on the other side of the bridge, and it stays local. It needs:

make -C ~/git/corDdsBridge COR_BRIDGE_DDS=ON install   # needs the eProsima stack
docker pull eprosima/vulcanexus:jazzy-desktop          # 6.5 GiB, never pulled by a test

The ROS 2 demo talker in that image publishes std_msgs/String on /chatter (DDS topic rt/chatter); the demo listener observes what the broker publishes. In GitHub Actions COR_DDS_ROS2_IMAGE names the image's mirror. DDS and ROS 2 has the bridge.

The containers run with --ipc=host, not --net=host. Fast DDS reaches a participant on the same machine over shared memory: without --ipc=host the broker discovers nothing, and nothing is logged; with both, the topics never surface either.

CI images: the Docker Hub mirrors

The workflows pull nothing from Docker Hub - its anonymous pull limit is per IP, and GitHub's runners share theirs. Each image comes from a copy in quay.io/seamware/coraine-ci, tagged mirror-<name>-<tag> (every architecture, the same digests), made by .github/workflows/mirror-images.yml weekly and on dispatch. A build outside CI needs nothing from quay: docker/Dockerfile, the compose files and the test helpers keep the upstream names. To add an image:

  1. a line in IMAGES in mirror-images.yml;
  2. gh workflow run mirror-images.yml;
  3. quay.io/seamware/coraine-ci:mirror-<name>-<tag> in the workflow.

Sanitizers

The functional suite with every library and the broker built with -fsanitize=address,undefined -fno-omit-frame-pointer -O1 -g - AddressSanitizer, LeakSanitizer and UndefinedBehaviorSanitizer. The tools are in test/sanitizer/:

sanSetup.sh <dir> [<bin dir>]writes gcc-san (the compiler), sanPreload.so (dlclose() a no-op, so a leak inside a plugin names its frames) and the wrappers coraine / coraine-import
sanReport.py <report dir>the reports, deduplicated by kind and first frames, with the tests that hit each; exit 1 if there is one
lsan.suppLeakSanitizer suppressions - third-party stacks only

In a throwaway environment (it installs into /usr/local and /opt/seamware), from the coraine checkout, the libraries already built by bootstrap.sh:

test/sanitizer/sanSetup.sh /opt/san
make libs-rebuild CC=/opt/san/gcc-san COR_HTTP_SERVER=mhd
CC=/opt/san/gcc-san make di CC=/opt/san/gcc-san COR_HTTP_SERVER=mhd
COR_BROKER=/opt/san/coraine COR_IMPORT=/opt/san/coraine-import corTest -db mongoc
test/sanitizer/sanReport.py /tmp/san-reports

CC on the make command line reaches every library's make; CC in the environment is what cmake reads for the broker and its plugins. The reports go to $SAN_REPORT_DIR (default /tmp/san-reports): asan.<pid>, ubsan.<pid>, and pids mapping each pid to its test.

Soak

test/soak/soak.py --db mongoc|corDB [--minutes 120] [--rate 40]

A release broker under mixed load at a fixed, moderate rate: creates, PATCHes, retrieves, queries, batch operations, deletes, a subscription created and deleted, and three subscriptions notifying a receiver the script runs. Each worker caps its entities (--maxEntities), so the store reaches a steady size. corDB runs with --dbDir; both with --troe none. It fails on:

  • the broker exiting or not answering, or a status other than the one expected;
  • a retrieve not returning the value last written;
  • RssAnon growing after the warm-up (the first 15 %, at least 5 minutes) by more than max(--rssMaxGrowthPct %, --rssMaxGrowthMiB);
  • an E or X line in the broker's log, or a notification count other than the one expected;
  • a final read - every live entity, its value, the count, the subscriptions - that differs from what was written.

It measures no throughput.

The pre-release campaign

gh workflow run prerelease.yml -f ref=release/0.5.0              # soakMinutes=120, only=all
gh workflow run prerelease.yml -f ref=release/0.5.0 -f only=soak -f soakMinutes=30
