corHttp - the built-in HTTP server

corHttp is an HTTP/1.1 server and nothing else: it accepts connections, parses requests in place and writes responses. A request reaches one callback with its method, path, query, headers and body; routing, JSON and everything else belong to the caller. It is the HTTP server of a coraine built with COR_HTTP_SERVER=builtin, and depends on corAlloc, corBase and libc only.

The model

  • A server is one loop on one thread. corHttpServe() runs an edge-triggered epoll loop until corHttpStop(): every accept and every read loops until EAGAIN. One thread per server means no lock on its connection pool, and no two writers on one socket.
  • Several loops on one port. More cores take more servers. corHttpAcceptShare() makes the first of a group accept every connection and deal them out in turn - itself included - through a queue and an eventfd of each loop's own; the others are initialised with noListener and need no SO_REUSEPORT. A connection belongs to one loop for its whole life.
  • A port in use is an error. corHttpInit() listens on every IPv4 interface without SO_REUSEPORT: a second server on a taken port fails (EADDRINUSE). corHttpInitOptions() takes a CorHttpListenOptions - bindAddress (one numeric IPv4 or IPv6 address, not a host name), reusePort, noListener.
  • Connections are pooled, allocated at corHttpInit() - each with an 8 KiB read buffer and an 8 KiB inline per-request allocator (connP->alloc) - and reused. A read buffer grows by doubling when a request needs it, up to maxRequestSize, and is never shrunk. With the pool exhausted a new connection is closed at once. TCP_NODELAY is set on every accepted socket.

The request

Zero copy. method, path, query, version, every header key and value and the body are CorHttpSlices - a pointer and a length - into the connection's read buffer, NUL-terminated in place by the parser. Nothing survives the callback: a caller that needs a value after it copies it. The one copy the library makes is of the query, split into uriParam[] on a copy from the per-request pool, so the raw query stays whole for a caller that forwards it as it arrived. Neither the path nor the parameters are percent-decoded - that is the caller's.

Completeness first. A read-only scan decides whether the request is whole; the destructive parse runs once, on a request known to be complete. (Terminating a header value in place overwrites the byte after it - for a sender using a bare LF, the line's terminator - so a parse that ran on half a request could not run again.)

  • An HTTP/1.0 request, or Connection: close, ends the connection after its response.

The response

The callback answers with corHttpResponseStatus(), corHttpResponseHeader() and corHttpResponseBody(), which borrow what they are given: it must outlive the callback, and connP->alloc - reset in bulk when the response is out - lives exactly that long. The engine adds Content-Length (not on a 1xx or a 204) and Connection: close when the connection ends. A callback that sets no status is answered 500.

#include <signal.h>
#include <stdio.h>
#include <string.h>

#include "corAlloc/corAlloc.h"
#include "corHttp/CorHttp.h"

static CorHttpServer server;

static void onSignal(int sigNo) { (void) sigNo; corHttpStop(&server); }

static void request(CorHttpConn* connP)
{
  if (strcmp(connP->path.s, "/ping") != 0)
  {
    corHttpResponseStatus(connP, 404);
    return;
  }

  const char* name = corHttpUriParam(connP, "name");             // NULL: not given
  char*       body = corAlloc(&connP->alloc, 128);               // lives until the bytes are out
  int         len  = snprintf(body, 128, "{\"pong\":\"%s\"}", (name != NULL) ? name : "");

  corHttpResponseStatus(connP, 200);
  corHttpResponseHeader(connP, "Content-Type", "application/json");
  corHttpResponseBody(connP, body, len);
}

int main(void)
{
  signal(SIGINT,  onSignal);
  signal(SIGPIPE, SIG_IGN);                    // a peer that vanishes mid-write is not fatal

  if (corHttpInit(&server, 8080, 64, request) != CorHttpOk)   // 64 connections
    return 1;

  corHttpServe(&server);                       // until corHttpStop
  corHttpServeEnd(&server);
  corHttpRelease(&server);
  return 0;
}

The request is over when its bytes are out, not when the callback returns. A caller that hangs state on connP->userData - the state the response borrows from - sets server.doneCb: it is called once per request that reached the callback, on the loop's thread, after the last byte is written or when the connection dies with the request on it.

Answering later - suspend and resume

A request that waits - a database round trip, a forward to another server - cannot wait on the loop without stopping every other connection of it.

Call
corHttpSuspend(connP)from inside the callback: "not now". The connection leaves the loop's care - no epoll interest, no idle timeout, not reused - until it comes back.
corHttpResume(connP)the only function that may be called from another thread: it queues the connection and wakes its loop through an eventfd, and the loop writes the response. Two threads never write one socket.
corHttpResumeHere(connP)for code that runs on the loop's own thread - a coroutine of the loop: the response goes out at once, no queue.

The loop runs corBase's corCoLoop: a coroutine that waits for a socket or a time hands its descriptor to the loop's epoll (the event pointer tagged, so the loop tells it from its connections) and yields; the loop resumes it when it is ready - Coroutines.

corHttpServeEnd(), after corHttpServe() has returned, closes every connection but the suspended ones - each with a request on it gets its doneCb first; call it when the application holds no request any more, then corHttpRelease().

static void events(CorHttpConn* connP)
{
  corHttpResponseStatus(connP, 200);
  corHttpResponseHeader(connP, "Content-Type", "text/event-stream");

  CorHttpStream* streamP = corHttpResponseStream(connP);
  handToWriter(streamP);                       // the application's: a thread that writes events
}

// on any thread
if (corHttpStreamWrite(streamP, "data: 42\n\n", 10) == false)   // the client is gone
  corHttpStreamEnd(streamP);                   // exactly once - also after a write said false
  • A write copies the bytes into the stream and wakes the loop through the same eventfd as corHttpResume; the loop writes them as one chunk. The writer never waits for the socket.
  • A client that falls COR_HTTP_STREAM_PENDING_MAX (16 MiB) behind is disconnected, and the writes say false.
  • The idle sweep skips a stream: a writer with nothing to say for long sends something small now and then, or the client cannot tell a quiet stream from a dead one.
  • While a file or a stream is on its way, what the client sends is read and dropped; its hang-up closes the connection, which is how a writer learns it is gone.

Upgrading the connection

A callback that accepts an upgrade (a WebSocket handshake) sets the 101 and the protocol's headers, then calls corHttpUpgrade(connP, cb, cls). Once the 101 is written, the socket leaves the loop, the connection goes back to the pool without being closed, and cb(fd, extra, extraLen, cls) is called on the loop's thread with the socket and the bytes the client sent behind the request (valid during the call only). The socket is the caller's from then on, to read, write and close.

Not implemented

  • Pipelining. A second request arriving behind the first, before its response, is not served.
  • TLS. No HTTPS listener: a proxy in front terminates TLS.
  • Chunked request bodies - above.

In coraine

corHttp is one of corRest's two HTTP backends; exactly one is in a build, chosen at compile time, and everything above the backend - the service table, the dispatch, the worker pool, the response headers - is the same either way (corRest, Choosing the HTTP server).

cmake -DCOR_HTTP_SERVER=builtin ..           # coraine with corHttp
make -C ../corRest COR_HTTP_SERVER=builtin   # corRest's own make takes the same variable; mhd is the default
coraine -V                                   # httpServer: builtin

Building and testing

make              # libcorHttp.a and libcorHttp.so, staged to the repository's root
make di           # ... and install
make corHttpTest  # a server that echoes what it parsed
make listenTest   # bind address and SO_REUSEPORT
make streamTest   # a file body and a streamed body: chunked, from another thread, a client gone or behind
$ ./corHttpTest 1041 &
$ curl "localhost:1041/ngsi-ld/v1/entities?type=T&limit=5&local"
{"method":"GET","path":"/ngsi-ld/v1/entities","query":"type=T&limit=5&local","headers":3,"uriParams":3,"accept":"*/*","limit":"5","bodyLen":0}

The repositories are siblings: sources compile with -I.. and link ../corAlloc/libcorAlloc.a and ../corBase/libcorBase.a. Through the broker, coraine's functional suite runs on both servers - its corDB shards on a builtin build in every pull request, both servers in the nightly run. A test tied to one server says so (REQUIRE_HTTPSERVER): five need libmicrohttpd - among them the one whose notification receiver serves HTTPS, which this server cannot - and two need this one.
