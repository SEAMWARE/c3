Authorization in the broker

coraine decides who sent a request, and whether it may do what it asks, in the broker itself - through an auth plugin, one at most, chosen with --auth. Two come with it: OpenID Connect tokens with a read and a write role, and the FIWARE Data Space Connector's tokens and ODRL policies.

The modes

Started withA request is
no --authlet in. None of the code runs; built with -DCOR_FEATURE_AUTH=OFF it is not in the broker at all
--auth oidcan OpenID provider's access token (Keycloak, Auth0, Entra ID, ...) and two roles in it: one reads, one reads and writes; and the tenants the token may use - below
--auth fdscthe Data Space Connector's provider-side security: VCVerifier's access token, the ODRL-PAP's policies - decided as the connector decides them - below
--auth fdsc --fdscNgsildthe same policies, decided on the entity as NGSI-LD has it: its stored, expanded types, entity by entity, attribute by attribute - below
--auth <name|path>a plugin of your own - below

Inside the broker the request is already parsed, its @context applied, every type and attribute name expanded, a batch split into its entities. A decision there is a lookup, not a second parse, and it can do what a proxy in front cannot: decide per entity in a batch, decide on the stored type of an entity whose request does not carry one, make "may only read type X" a condition of the query itself.

How a request is decided

  • Every request is asked - HTTP, cor://, and each message of a WebSocket connection (the connection carries no credentials; each message has its own Authorization in its metadata). Not asked: an in-process forward (its request was asked when it arrived), the broker's own requests, and the health port (--healthPort), a server of its own.
  • The answers are ProblemDetails of type about:blank (RFC 9457 § 4.2.1), with the plugin's title and detail.
  • A query decided entity by entity may return a page with fewer entities than its limit; its position links name only entities the request may read; its count counts the ones left out.
  • Not decided entity by entity, so refused where entities are decided: join=inline, and the EntityMaps themselves (a map names its entities by id).

Notifications

A subscription notifies long after the request that made it, so the broker keeps its owner - who created it, or last updated it - in the store's collection subscriptionOwners, beside the subscription and never in it (nothing that renders a subscription can show it). Each notification is decided on the owner: the entities the owner may not read are left out, and a notification left with none is not sent. An owner not known leaves out every entity - fail closed. A PATCH of the subscription makes its sender the owner. A restored owner is cached for 30 s, so an owner one broker of a high-availability set stores is seen by the others within that.

Fail closed

--auth asks for security; the broker never starts without it. A plugin that cannot be loaded, or whose init refuses its options, stops the broker (exit 1). A plugin that cannot decide answers 503. A plugin's own options exist only when it is loaded: coraine --auth oidc -u lists them.

How a client finds where to log in

The broker serves the plugin's OAuth 2.0 Protected Resource Metadata (RFC 9728), without authentication, at GET /.well-known/oauth-protected-resource - the issuers in authorization_servers, and the plugin's own members. Every 401 names it:

WWW-Authenticate: Bearer error="invalid_token", error_description="wrong issuer", resource_metadata="http://broker:1026/.well-known/oauth-protected-resource"

c³ reads it on the first 401. Without --auth the route is a 404. It is COR_FEATURE_AUTH_METADATA, on by default, about 1 KB of the broker.

--auth oidc: an OpenID provider's tokens and roles

No policies, nothing decided per entity: each request is decided at its admission, on its method and its NGSI-LD operation, before the broker fetches a @context for it. Built with COR_FEATURE_AUTH_OIDC (on by default).

  • The token - Authorization: Bearer, a JWT signed with RS256 or ES256, checked against the provider's JWK Set; iss must be --oidcIssuer, exp and nbf hold within --oidcLeeway, aud holds --oidcAudience when given. No token, or one that does not hold: 401. A token is checked once; a request that sends it again finds it in a cache and only its exp and nbf are checked again.
  • The keys - from the discovery document (<issuer>/.well-known/openid-configuration, or --oidcDiscovery), whose issuer must be --oidcIssuer; or --oidcJwks. Fetched every --oidcRefresh seconds, every second until there are some, and at once (at most once a second) when a token names a key the set lacks. Until there are keys, every request is a 503.
  • The tenants - the claim --oidcTenantsClaim (default tenants), an array or a space-separated string: default is the default tenant, * every tenant. A token without the claim may use the default tenant only. Another tenant: 403, decided before the tenant is resolved - a create in a tenant the token may not use creates no tenant.
  • Subscriptions - creating or updating one is a write. Its owner (the roles and tenants of that token) holds for --oidcOwnerMaxAge seconds: roles or tenants taken away at the provider stop its notifications within that. After it, none are sent until a request with a valid token updates the subscription.
RoleDefault nameMay
readngsild-readGET, HEAD, OPTIONS, and the queries that are POSTs: POST /entityOperations/query, POST /temporal/entityOperations/query, POST /temporal/timepoint/entityOperations/query

A token without the role a request needs: 403, its detail naming the role.

With Keycloak

coraine --auth oidc --oidcIssuer https://keycloak.example.org/realms/city --oidcAudience coraine
  1. Realm roles ngsild-read and ngsild-write, given to the users and service accounts that need them.
  2. The tenants: a user attribute tenants (several values: default, t1, ...), and on the client a "User Attribute" mapper - user attribute tenants, token claim name tenants, multivalued, added to the access token. Keycloak 26 keeps only the attributes its user profile declares: declare tenants there, or let the realm keep unmanaged attributes.
  3. An audience mapper on the client the applications log in with, adding coraine to the access token's aud - Keycloak's access tokens do not carry it otherwise.
  4. A broker that reaches Keycloak by an internal name while the tokens carry the public one adds --oidcDiscovery http://keycloak:8080/realms/city/.well-known/openid-configuration; the jwks_uri in it must be one the broker can reach.

--auth fdsc: the Data Space Connector's security

fdsc.so takes what the connector's provider side has, unchanged: the access token VCVerifier issues for a Verifiable Presentation, checked as APISIX's openid-connect checks it, and the ODRL policies of the ODRL-PAP, evaluated as OPA evaluates the Rego the PAP generates from them. A deployment's tokens and policies need no change: for every request, the same 401, 403 or pass.

Target: FIWARE Data Space Connector 10.87.0 (2026-10-09) - VCVerifier 6.23.1, odrl-authorization 2.4.3 (APISIX 3.17.0, OPA 1.11.0) - and odrl-pap 1.7.3 (SEAMWARE/odrl-pap, 2026-10-14; the connector's chart pins 1.7.1). test/fdscDiff/fdscDiff.sh runs that chain in docker beside coraine, both given the same verifier and PAP, and compares the answers by class (401, 403, 503, let through): 67 cases, 0 differences (the nightly, 2026-10-27), apart from one decided on purpose.

A source of keys and a source of policies are required; without either the broker does not start.

The token

  • Authorization: Bearer <JWT>, as APISIX takes it with bearer_only: a compact JWS, alg RS256 or ES256, verified with the key of its kid. alg: none, or an alg that is not its key's, is refused.
  • iss is always checked. aud is checked with --fdscAudience - recommended: VCVerifier sets it to the service id, and without it a token issued for another service is accepted.
  • A bad token: 401 with error="invalid_token"; no token: 401 with WWW-Authenticate: Bearer. The credential is the token's verifiableCredential (else vc).
  • A token whose signature has been checked is kept (1024 of them) - a client sends the same token for its 30 minutes - and its claims are checked on every request. The kept tokens are dropped when the key set changes.
  • The token's size is a cost of every request: a 696-byte token takes 0.86 µs of a PATCH with libmicrohttpd 1.0.10, 0.31 µs with the header patch every build of the stack applies (PATCH, 50 connections, the broker on one core, corDB, 2026-10-13 - Performance). With --auth the broker says once in its log when requests carry an Authorization header over 512 bytes.

Keys and policies

A thread of the plugin fetches the keys and the policies (the PAP's GET /policy, page by page) every --fdscRefresh seconds, and every second while either is missing. Each is replaced whole, once read completely; a failed fetch keeps what is in use.

WhenThen

How a policy decides

  • A request is allowed when one policy allows it; no policy allows nothing. The policies are evaluated in the PAP's order, and the first that allows decides.
  • A policy allows when all its rules hold - the rules of all its permissions together, as the PAP puts them in one rule set: two permissions are an AND. Prohibitions, obligations and duties are ignored, as the PAP ignores them.
  • A rule on a value the request or the credential does not have is not true - nor its negation (neq, isNoneOf).
  • A token with two or more credentials satisfies no vc: word and no issuer assignee.

Two words of coraine's own, read with --fdscNgsild only (without it a policy that uses one is skipped, and the log says why): ngsi-ld:tenant - the request's NGSILD-Tenant, "" for the default tenant; and ngsi-ld:attribute - one attribute at a time, expanded. With ngsi-ld:attribute a read leaves out the attributes no policy allows (id, type stay), a write of an attribute not allowed is a 403, and a write of the entity whole (a delete, a replace) needs a policy that holds whatever the attribute.

A kept owner credential is personal data at rest. It goes with its subscription (a DELETE of it), and it is never checked again for revocation - VCVerifier checks that when it issues a token. --fdscOwnerMaxAge bounds how long a revoked credential still receives notifications.

The broker as its own PAP

With --policyApiPort <port> the broker serves the ODRL-PAP's /policy API (odrl-pap 1.7.3) on a port of its own, and fdsc.so reads from it as from the PAP: --fdscPap http://127.0.0.1:<port>. The policies are documents of the default tenant's collection odrlPolicies: they outlive the broker. Built with COR_FEATURE_POLICY_API (on by default).

RequestDoes

POST /policya policy: 200, Location: its id (ten letters)

The policy port has no authentication, as the PAP has none: whoever reaches it can change every policy. --policyApiHost (default 127.0.0.1) keeps it to the machine; in Kubernetes, give the port a Service of its own and a NetworkPolicy that lets in only what writes policies (contract-management). The port needs libmicrohttpd - a broker built with the built-in HTTP server refuses --policyApiPort at start-up.

A plugin of your own

--auth <name> loads <plugins>/auth/<name>.so (or a path) and calls its authRegister(AuthDriver*). The contract is src/lib/plugin/AuthDriver.h, at AUTH_ABI_VERSION 6, append-only. Only plain data crosses it - strings, integers, function pointers - so a plugin can be written in any language that exports a C function:

#include "plugin/AuthDriver.h"

static AuthVerdict authenticate(const AuthRequest* reqP, void** identityP, AuthAnswer* answerP)
{
  const char* key = reqP->header("X-Api-Key");

  if ((key == NULL) || (strcmp(key, "secret") != 0))
  {
    answerP->detail = "no API key";
    return AuthUnauthenticated;
  }

  return AuthAllow;
}

void authRegister(AuthDriver* driverP)
{
  driverP->abiVersion   = AUTH_ABI_VERSION;
  driverP->name         = "apikey";
  driverP->authenticate = authenticate;     // authorize NULL: an authenticated request may do anything
}

Built as a shared object, put in <plugins>/auth/apikey.so, run with --auth apikey.

Any of them may answer AuthUnavailable - 503. A plugin is called on the broker's request threads, concurrently, possibly on a coroutine's stack: it is thread-safe and never blocks - keys and policies are fetched by threads of its own. AuthRequest gives the method, path, URL parameters, the NGSI-LD operation, the tenant, and accessors for a header, the body as the client sent it, and a term expanded with the request's @context or with the broker's default one.

Open point. With --fdscNgsild, a request whose decision depends on the entity has its @context fetched before entity decides it: a client with a right to some entity can have the broker fetch a URL of its choice.
