Migrating a database to coraine

What another broker holds - entities, subscriptions, context source registrations and the temporal history - moved into coraine's stores, with the identities and the system timestamps it had there. For an operator moving a deployment, today from Orion-LD.

How it works

Two programs meet in one file, the migration stream. A reader knows its source and nothing of coraine's storage. The writer, coraine-import, knows no source: it is linked against the broker's libraries, loads the broker's store plugins, and stores what the current broker stores. The broker itself carries no import code.

The importer and a broker never share a store. The import runs before the broker starts on the same stores - and into empty ones: an import never overwrites.

1Stop the writes to the source

What is written after the export is not in the stream. A deployment that cannot stop can export and import once, then export and import again what changed - but a record already imported is refused the second time, so a second pass carries new entities, not changed ones.

2Export

From a checkout of the coraine repository, with the source's MongoDB - and its TRoE PostgreSQL, for the history - reachable:

pip install pymongo psycopg            # psycopg only for the history
tools/migrate/orionldExport.py --mongo mongodb://orion-mongo:27017 --db orion \
                               --troe 'host=orion-pg user=postgres password=...' \
                               --out stream.ndjson
OptionWhat it does
--mongothe MongoDB URI of the current state. Default mongodb://localhost:27017
--dbthe database-name prefix the deployment ran with (its -db). Default orion
--troethe libpq connection string of the TRoE server, without dbname; none (the default): no history
--troeDbthe TRoE database-name prefix. Default: the --db prefix
--tenantscomma-separated tenants (default or '' for the default tenant). Default: all
--noCurrentleave the current state out - history only
--outthe stream file. Default: stdout

What the exporter leaves out, it says on stderr - below.

3Import

Into the stores the broker will run on, with the broker not running on them:

coraine-import --database mongoc --dbHost mongo --troe timescale --troeHost pg --file stream.ndjson
coraine-import --database corDB  --dbDir /var/lib/coraine --troe corDB      --file stream.ndjson

coraine-import takes the broker's store options by the broker's names - --database, --troe, and each plugin's own (--dbDir, --dbName, --dbHost, --troeName, ...) - and --file (-: stdin). Its log is stdout; the report is on stderr:

import of stream.ndjson:
  entities                        3 imported,      0 refused
  subscriptions                   3 imported,      0 refused
  registrations                   1 imported,      0 refused
  temporal entity events          4 imported,      0 refused
  temporal instances              8 imported,      0 refused
  created rows (history)          1 written,       0 failed

Exit code 0: every record imported. 1: some were refused, each named above the report by its line in the stream and the reason:

stream.ndjson:3: entity: entity type 'Room' is not expanded - the stream must hold expanded NGSI-LD (full IRIs, core terms short)

4Start the broker, and compare

Start the broker on the same stores, the usual way. Compare with the source: the number of entities per type (GET /ngsi-ld/v1/types?details=true), the subscriptions, the registrations, and a few entities' temporal evolution.

5Deal with what was refused

A refused record is not written, and the others are - the import does not stop at the first one. Fix those lines of the stream (or the reader), and import a stream of just them.

Do not import the whole stream again. A record already in the target store is refused, never overwritten - a second import of the same stream refuses everything that went in the first time, and exits 1.

In a container, on Kubernetes

coraine-import is in the image beside coraine:

docker run --rm -v $PWD:/migrate --network <the stores' network> --entrypoint coraine-import \
       quay.io/seamware/coraine:<tag> --database mongoc --dbHost mongo --file /migrate/stream.ndjson

On Kubernetes it is a one-off Job before the broker starts, on the broker's stores. For a persistent corDB that is the volume the broker's StatefulSet mounts - ReadWriteOnce: run the Job with the StatefulSet at zero replicas, then scale it up (Kubernetes).

Not an initContainer. It would run again at every restart of the pod - and a second import refuses everything and exits 1.

The stream

One JSON object per line (NDJSON), version 1:

{"kind":"header","format":"coraine-migration","version":1,"source":"orion-ld"}
{"kind":"registration","tenant":"","data":{ ...a ContextSourceRegistration... }}
{"kind":"subscription","tenant":"","data":{ ...a Subscription... }}
{"kind":"entity","tenant":"t1","data":{ ...an Entity... }}
{"kind":"temporalEntity","tenant":"","data":{"id":"urn:E1","type":"https://ex.org/T","op":"created","at":"2024-01-02T03:04:05.123Z"}}
{"kind":"temporalInstance","tenant":"","data":{"id":"urn:E1","type":"https://ex.org/T","attr":"https://ex.org/speed","op":"modified","instance":{ ... }}}

tenant "" or absent is the default tenant. The data is NGSI-LD as the API represents it, with every name expanded - nothing of any broker's storage, whatever the source, so the stream is readable without coraine.

kindThe record
headeroptional, the first line
entityan Entity, normalized, with createdAt / modifiedAt on the entity, every attribute instance and every Sub-Attribute. A multi-instance attribute is an array, each instance with its datasetId
subscriptiona Subscription with id, createdAt, modifiedAt, and in notification the counters a GET shows - timesSent, timesFailed, lastNotification, lastSuccess, lastFailure. A q names attributes by IRI, the IRI's dots written %2E
registrationa ContextSourceRegistration with id, createdAt, modifiedAt
temporalEntityan entity-level history event: op created | replaced | deleted, at at
temporalInstanceone attribute instance of the history: the entity's id and type, attr, op created | modified | replaced | deleted, and the instance with its instanceId, createdAt, modifiedAt (a deletion: deletedAt) and datasetId

The records are imported in the order they come; the history in batches of 500 events, one transaction each. A reader therefore writes the registrations first (an exclusive or redirect registration is refused over local entities that hold what it claims), and an entity's temporalEntity records before its temporalInstance records.

Names: expanded, always

The importer expands nothing and takes no @context. Every name NGSI-LD expands - an entity type, an attribute or Sub-Attribute name, a VocabProperty's vocab, the names in a subscription's entities, watchedAttributes and notification.attributes, in a registration's information, a history record's type and attr - is an absolute IRI (http://, https://, urn:) or an NGSI-LD core term. Room, temperature or a compact IRI such as ex:humidity means the stream is not expanded, and the record is refused. The member names inside a compound value are the application's own JSON and are not checked.

How the writer writes

coraine-import writes every record through the code a live write goes through - the conversion and checks of a create, the service routines of POST /subscriptions and POST /csourceRegistrations - and puts the source's system timestamps, counters and instance ids back where the broker would set its own. Every storage format is written only by the plugin that owns it. Nothing else a live write does happens: no notification, no forwarding, no history from the current state - the history is what the stream's temporal* records say.

An entity the stream gives no history, with a history store: it gets the history a create writes - its created event at its createdAt, and an instance of each attribute as it is now. The report counts them as created rows. An entity with history in the stream - even a refused history record - gets what the stream holds and nothing more.

Why not
the APIa create through it cannot keep createdAt, modifiedAt, a subscription's counters or an instanceId - the broker sets them, as it must
the fileswriting mongoc documents or corDB log records from outside is a second copy of each format, kept in step with the broker for ever
an import route on a serving brokera route that lets a client set system timestamps is a hole in what a broker guarantees about them

Reading an Orion-LD database

tools/migrate/orionldExport.py - Python 3; pymongo for the current state, psycopg 3 or psycopg2 for the history. Per tenant:

Orion-LDRead fromBecomes
current stateMongoDB <db> (default tenant) and <db>-<tenant>: collections entities, csubs, registrationsentity, subscription, registration
history (TRoE)PostgreSQL <db> and <db>_<tenant>: tables entities, attributes, subAttributestemporalEntity, temporalInstance

Orion-LD stores names expanded (core terms short), so the reader writes them as they are. Not exported, each said on stderr: NGSIv2 subscriptions in csubs (an ObjectId _id), the casubs collection, and history rows of an entity whose type neither the history nor the current state knows. A history value is what the history table kept: an integral number comes back as an integer, and the attribute types the table does not record come back as Properties.

Other sources

A reader is any program that writes the stream. Planned: Orion (NGSIv2) - the current state, every name expanded with the user's @context, a term it does not define an error; history kept outside the broker (CrateDB or PostgreSQL tables of an NGSIv2 deployment's history service); and an ETSI neutral export format, once ETSI TC DATA defines one - the stream already holds the same content.
