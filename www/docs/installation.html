Installation

How to install coraine - from the apt repository, as a Docker image or from source - start it, choose its database, check that it works, and upgrade it. The options of a running broker, its admin API and its health probes are in Administration.

coraine is one binary plus the plugins it loads at start. With the corDB store it needs no other service. The MongoDB store needs a MongoDB server; the TimescaleDB history needs PostgreSQL with the TimescaleDB extension.

  • aptUbuntu 26.04, Ubuntu 24.04 LTS, Debian 13 - amd64 and arm64. A systemd service included.
  • DockerOne immutable image tag per merge to main, release and debug flavours.
  • From sourceThe Cor-Libs and coraine cloned and built at their pinned versions.

Install with apt

Two packages, from the signed repository https://seamware.github.io/apt:

curl -fsSL https://seamware.github.io/apt/coraine.gpg | sudo tee /usr/share/keyrings/coraine.gpg > /dev/null
echo "deb [signed-by=/usr/share/keyrings/coraine.gpg] https://seamware.github.io/apt $(. /etc/os-release; echo $VERSION_CODENAME) main" \
  | sudo tee /etc/apt/sources.list.d/coraine.list
sudo apt update && sudo apt install coraine        # or coraine-dev
PackageWhat it holds
corainethe broker (/usr/bin/coraine), coraine-import, every plugin but the DDS bridge (/opt/seamware/plugins), /opt/seamware/etc/contextSourceExtras.json, the systemd unit coraine.service with its options file /etc/default/coraine, and c³, the control center (/usr/bin/c3)
coraine-devcoraine-build, and the exact source of the same version - coraine and every Cor-Lib at the commits built - in /usr/share/coraine/src/coraine-src.tar.xz, with the toolchain and libraries to build it as dependencies. No installed headers, no libraries
  • Components. main holds the releases; testing holds builds of a commit between releases - put testing in place of main on the deb line.
  • Versions. 0.6.0+<dist> for a release, 0.6.0~git<YYYYMMDD>.<sha8>+<dist> for any other commit (it sorts before 0.6.0); <dist> is ubuntu26.04, ubuntu24.04 or debian13.
  • Without the repository. Each run of the Packages workflow keeps its .deb files as artifacts (debs-<dist>-<arch>): sudo apt install ./coraine_0.6.0+ubuntu24.04_amd64.deb - apt resolves the dependencies.
  • Dependencies come from the distribution: OpenSSL, GEOS, libmicrohttpd, libmosquitto, libpq, zstd, and on Ubuntu 26.04 the MongoDB C driver v2. Ubuntu 24.04 and Debian 13 package only v1 of that driver, so there the package carries v2 privately, in /opt/seamware/lib; the system's libmongoc-1.0 is not touched.

The service

The service is installed not enabled and not started: the broker listens on every interface and has no authentication of its own (Authorization). Configure it first.

sudoedit /etc/default/coraine
sudo systemctl enable --now coraine
journalctl -u coraine -f
  • It runs /usr/bin/coraine in the foreground (Type=simple, the log on stdout - in the journal) as the system user coraine, with the options of /etc/default/coraine as CORAINE_* environment variables (every option has one).
  • Out of the box: corDB on disk in /var/lib/coraine/db, no temporal history, port 1026.
  • systemctl stop is a clean stop (SIGTERM): requests in flight finish, corDB syncs its log and writes a snapshot per tenant. An upgrade of the package restarts a running broker.
  • Removing the package stops the broker. Purging it removes /etc/default/coraine and keeps the data in /var/lib/coraine and the user coraine.

coraine-dev - a broker of your own

coraine-build --list-features
coraine-build --features REGISTRATIONS=OFF,SERVICE_EXECUTION=OFF ~/coraine-small
. ~/coraine-small/install/env
coraine --database corDB

coraine-build [options] <dir> unpacks the source into <dir> and builds there, as any user; nothing is written outside it. The result is in <dir>/install - bin/, plugins/, etc/ and env, which points PATH, SEAMWARE_PLUGIN_DIR, SEAMWARE_ETC_DIR and CORAINE_CONTEXTSOURCEEXTRAS at it.

OptionThe build
--releasethe default: optimised, traces compiled out
--debugtraces compiled in (--traceLevels)
--pgoprofile-guided, trained on the measured request shapes - as the packages and the image
--tune <workload>profile-guided on your workload - Extreme performance
--features NAME=ON|OFF,...the COR_FEATURE_* switches; --list-features lists them (--json as JSON)
--http-server builtincorHttp, the built-in HTTP server, instead of libmicrohttpd; the switches that need libmicrohttpd off (POLICY_API). Not with --pgo or --tune
--name <exe>the broker is install/bin/<exe>: 1-64 of A-Z a-z 0-9 . _ -, not coraine-import. It reads the same CORAINE_* variables
--source <clones>a directory of git clones (coraine and every Cor-Lib side by side) instead of the tarball - committed trees only

A plugin of your own - a bridge, say - is compiled against the headers in the unpacked tarball and links none of the broker's libraries; a plugin built from the tarball of version X matches the coraine package of version X. How: Building a plugin against it and Plugin architecture.

Install with Docker

# in memory, nothing else needed
docker run --rm -p 1026:1026 quay.io/seamware/coraine:<tag> --database corDB --apiPlugins admin

# against MongoDB
docker run --rm -p 1026:1026 quay.io/seamware/coraine:<tag> --database mongoc --dbHost mongo
  • Tags. quay.io/seamware/coraine:<version>-<date>-<sha> - one immutable tag per merge to main, never latest - and the same with -debug, the debug flavour of that build.
  • Two flavours. release: traces compiled out, for deploying. debug: traces compiled in, for --traceLevels and for replaying a crash report from a release image of the same tag.
  • Options are the arguments after the image name, or -e CORAINE_* variables. The port is not fixed: pass --port and publish the one you chose.
  • Building one: make docker in the coraine repository (DOCKER_BUILD=debug for the debug flavour). It stages each Cor-Lib's committed state - uncommitted work in a sibling repository is not in the image. docker/docker-compose.yml is a broker with MongoDB.

The image's own page: docker/README.md. On a cluster: Kubernetes.

Install from source

The broker is built against the Cor-Libs, its libraries; corLibs clones and builds them, and coraine is the broker's own repository.

git clone git@github.com:SEAMWARE/corLibs.git
./corLibs/bootstrap.sh          # clones and builds every Cor-Lib at its pinned version
cd coraine
make i                          # release build + install

make install writes the broker to /usr/local/bin/coraine, the plugins to /opt/seamware/plugins/{db/currentState,troe/temporal,api}/ and the provenance file to /opt/seamware/etc/contextSourceExtras.json - run it with the privileges for that, or create those directories first.

The MongoDB C driver v2 (mongoc2.pc) is the usual build snag: few distributions package it. cmake -DCOR_FEATURE_MONGOC=OFF builds without MongoDB; run with --database corDB.

The system packages (Debian / Ubuntu): libmicrohttpd-dev, libssl-dev, libmosquitto-dev (MQTT), libgeos-dev (geo-queries), libicu-dev (orderBy collation), libpq-dev (TimescaleDB), cmake build-essential, and the MongoDB C driver v2. Every package and make target: Building.

First start

The defaults: port 1026, the mongoc store (MongoDB on localhost:27017), no temporal history, no API plugins.

# in memory, pretty JSON, the admin API on - no other service
coraine --database corDB --troe none --apiPlugins admin -pp 2

# MongoDB, the broker on another port
coraine --port 1027 --database mongoc --dbHost localhost

# every option, the selected plugins' own included
coraine --apiPlugins admin --database mongoc -u

The broker runs in the foreground and logs to its standard output; --daemon (-bg) runs it in the background with the log in a file (Foreground or daemon). The first requests to try: API walkthrough.

The databases

Two choices: the current state (--database) and the temporal history, TRoE (--troe). Each is a plugin with options of its own, listed by coraine --database X --troe Y -u.

--databaseThe store
mongoc (default)MongoDB. A database per tenant; needed for --high-availability mongo (with a replica set)
corDBin the broker's memory; on disk too with --dbDir
ramDBcorDB built without the disk - nothing written anywhere
--troeThe history
none (default)no history; the Temporal API has nothing to answer
corDBinside corDB's own store - it needs --database corDB

MongoDB

MongoDB 8.2 (mongo:8.2): the functional suite, CI and the performance figures run on it.

MongoDB 8.0 does not start on a Linux kernel 6.19 or newer - mongod exits at once (SERVER-121912). In a container the kernel is the host's, so mongo:8.0 fails the same way on such a host. 8.2 starts.

--globalDbCORAINE_GLOBALDBcoraine - the database for state that belongs to no tenant (the JSON-LD contexts)
--dbUser / --dbPwdCORAINE_DBUSER, CORAINE_DBPWDnone - the user and password

--dbPwd and --dbURI are secrets: GET /admin/config shows ***. A --dbUser / --dbPwd the server refuses fails the start at once (mongoc: ping failed: Authentication failed.).

corDB on disk

With --dbDir <directory> corDB survives a restart: every write appends its effect to a log, synced every 100 ms, with a snapshot as the log grows. A clean stop (SIGTERM) loses nothing, and neither does kill -9, a crash or an OOM kill - the log is memory-mapped, so a record is in the kernel's page cache before the response. A power cut loses at most the last unsynced interval.

OptionDefault - what it does
--dbDirCORAINE_DBDIRnone: in RAM only. The directory - a subdirectory per tenant (snap-N.cor, log-N.cor)
--dbSyncCORAINE_DBSYNCinterval: synced every --dbSyncInterval ms. request: a write answers once its record is on the disk. none: written, never synced
--dbSyncIntervalCORAINE_DBSYNCINTERVAL100 - ms between two syncs
--dbSnapshotEveryCORAINE_DBSNAPSHOTEVERY64 - MiB of log after which a tenant is snapshotted (and at least as much as its last snapshot)
--dbCompressCORAINE_DBCOMPRESSoff - snapshots and finished log segments compressed (zstd); the open segment never. A store written with it is read with or without it
--dbLockPreferCORAINE_DBLOCKPREFERreads - reads or writes: whom a tenant's store lock lets in first when both wait (also ramDB)
--dbValueIndexesCORAINE_DBVALUEINDEXESnone - the declared indexes, as for MongoDB (also ramDB)

--dbSync, --dbSyncInterval, --dbSnapshotEvery and --dbCompress act on the disk: given without --dbDir - on the command line or in the environment - the broker does not start, and the error names the option: corDB: --dbSync without --dbDir - the store is in RAM only, there is no disk for it to act on.

A log that cannot be written - a full disk, a file-size limit, an I/O error - pauses the store: writes are refused with 503 PersistenceUnavailable and reads are served, until a snapshot of each such tenant succeeds - a history log that failed (--troe corDB) is written anew from memory the same way, and the pause ends by itself (A store that cannot write its log).

What it costs: Performance. How it works: corDB's persistence.

ramDB

--database ramDB is the same store and the same API as corDB, with nothing written anywhere - for a broker whose content is only ever the latest value (pub/sub, a cache in front of another system).

A restart starts empty, by design, and nothing warns about it at runtime. --dbDir is an unknown option with ramDB, and --troe corDB is refused; none, timescale and ramDB work.

TimescaleDB history (--troe timescale)

OptionDefault - what it does
--troeHost / --troePortCORAINE_TROEHOST, CORAINE_TROEPORTlocalhost / 5432 - the PostgreSQL server
--troeUser / --troePwdCORAINE_TROEUSER, CORAINE_TROEPWDpostgres / none (libpq then takes PGPASSWORD or ~/.pgpass). --troePwd is a secret (*** in /admin/config). The user, the password and --troeName are quoted in the connection string - a space, a ' or a \ in them is passed as it is
--troeNameCORAINE_TROENAMEcorh - the default tenant's database, and the prefix of the others
--troePoolSizeCORAINE_TROEPOOLSIZE10 - connections per tenant for the temporal reads and the Temporal API's writes
--troeWritersCORAINE_TROEWRITERS8 - writer threads per tenant, each on its own connection, writing the history of many requests in one transaction. 0: every request writes its own
--troeConnectTimeoutCORAINE_TROECONNECTTIMEOUT30 - seconds a start waits for the database, a try a second; 0: one try
--troeDownExitCORAINE_TROEDOWNEXIT0 (never) - seconds the database may be down before the broker exits with 1 (below)
--troeSqlIndexesCORAINE_TROESQLINDEXESnone - extra indexes for SQL sent to PostgreSQL directly: attrObserved, geo, time
--troeValueIndexesCORAINE_TROEVALUEINDEXESnone - the declared indexes of the history (Database indexes)
--troeInstanceCap / -troeCapCORAINE_TROEINSTANCECAP1000000 - instances per attribute a temporal query returns without firstN / lastN (also --troe corDB)

A request's history rows are queued for its tenant's writers and written after its response. With --troeSync they are queued before the response, so a temporal read that follows it sees them; no response waits for the commit. Measured against the default (eight cores, ABBA): writes 1-3 % fewer a second with 50 connections, 2-6 % with one. The queue holds at most 8 MiB. A stop (SIGTERM, SIGINT) writes what is queued; kill -9, a crash or an OOM kill loses it - up to 8 MiB, the rows of the last few milliseconds while the database keeps up. Every broker writing to the same PostgreSQL should run with the same --troeSqlIndexes.

When PostgreSQL is down

The current state and its subscriptions are served as before. The history is held in memory, retried, and written when the database is back - nothing is lost while what is held stays under 8 MiB.

During the outageAnswer
a write or read of the current stateas always; its subscriptions notify; its history is held
a temporal read, a Temporal API write500 InternalError, at once - the history it would read is in the database
GET /ready, GET /live200 - the health report says "status": "degraded", "recording": false
  • Retries: 100 ms after the first failure, then twice as late each time, up to every 5 s. The outage ends at most 5 s after the database takes connections again. Every row keeps the times of its write - the history is as if there had been no outage.
  • Past 8 MiB the history is lost, counted (lostRows) and logged, at most every 10 s. 8 MiB is some 5 660 creates of an entity of five attributes (~550 bytes of JSON), or some 34 200 attribute PATCHes.
  • --troeDownExit <s>: the broker exits (code 1) after <s> seconds of the database down while history is held, or at the first row that would be lost - whichever comes first. What is held is lost at the exit, and a restarted broker waits for the database: with it, an outage of the history is an outage of the broker.
  • A start during an outage waits --troeConnectTimeout seconds, then exits with 1. A database that answers and refuses (a schema version newer than this build, a permission, the password of --troeUser / --troePwd) fails the start at once, with the server's message: timescale: connection to db 'postgres' refused (--troeUser, --troePwd): ... password authentication failed for user "postgres". A refused password is told from an absent server by that message, in English: a PostgreSQL whose lc_messages is another language is waited for.

Every case, the log lines, the connection timeouts and the indexes of the history, measured: doc/installation.md.

Tenants

A request names its tenant in the NGSILD-Tenant header. With mongoc each tenant is a database of its own, with corDB a store of its own (with --dbDir, a directory of its own). Nothing is configured: a write naming an unknown tenant creates it; a read of one that does not exist is 404 NonexistentTenant.

Check an installation

With the admin API plugin loaded, on port 1026:

# 1. the broker answers, and says which build it is  -> 200, "coraine version" and each library's
curl -s localhost:1026/admin/version

# 2. create an entity  -> 201 Created, with a Location header
curl -si localhost:1026/ngsi-ld/v1/entities -H 'Content-Type: application/json' \
     -d '{"id": "urn:ngsi-ld:SanityCheck:1", "type": "SanityCheck",
          "temperature": {"type": "Property", "value": 21.5}}'

# 3. read it back  -> 200, "temperature" with value 21.5
curl -s localhost:1026/ngsi-ld/v1/entities/urn:ngsi-ld:SanityCheck:1

# 4. delete it  -> 204; a second GET is then 404
curl -si -X DELETE localhost:1026/ngsi-ld/v1/entities/urn:ngsi-ld:SanityCheck:1

Upgrading

Every store records the version of the format its data is written in, and a broker checks it at start - in every store it opens, coraine-import too:

StoreWhere0.6.0 writes
mongocmetadata, { _id: "storageFormat" }, in every tenant's database2 (1 without COR_FEATURE_Q_PREFILTER)
corDB with --dbDir<dbDir>/_storageFormat1
timescalemax(version) of troe_schema_version, in every tenant's database3
  • A lower version is upgraded at start, and this build's is written. No version and no data: a new store.
  • A higher version - written by a newer release - and the broker does not start (exit 1, the error names the store and both versions). Run that release, or a newer one.

0.5.x to 0.6.0 on MongoDB: stop every broker on the database first. 0.6.0 marks the attributes that have an instance with a datasetId (format 2); 0.5.x writes them without the mark, and q on 0.6.0 then misses them. A rolling upgrade with both versions serving the same database is not supported across this version, and 0.5.x refuses a format-2 database.

No downgrade to 0.4.x once 0.5.0 has written to a database: 0.4.x reads that format wrong and predates the check. Going back from 0.6.0 to 0.5.x: the script in doc/installation.md.
