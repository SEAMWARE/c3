Writing a bridge

A bridge is a plugin, <alias>.so, that carries values between the broker and a transport that is not NGSI-LD - an MQTT server, a Modbus device, a DDS network, a CKAN portal. The contract it satisfies is corBridge; a new bridge starts from corBridgeTemplate, which builds, loads into a broker and moves a value both ways before a line of the new protocol is written.

What a bridge carries

Endpointthe transport's own name for a value - an MQTT topic, a Modbus register, a CKAN resource id. Exact, as the wire spells it: a sample finds its Channel by (alias, endpoint).
Channelthis endpoint ↔ this attribute of this entity, this direction. Made by the broker from the ngsild section of the plugin's member of the --bridgeConfig file, shown on GET /ngsi-ld/v1/channels. A Channel the plugin refuses stays, dormant, with the reason.
DataChannelone endpoint whose samples are records (a row: one JSON object, one member per column), each made into entities by the broker's mapping - inbound, GET /ngsi-ld/v1/dataChannels. The plugin's side is the same sampleIn, one record a call. The CKAN bridge is one.
Bridgeone transport instance - one connection, one server - on GET /ngsi-ld/v1/bridges. --bridges <alias> loads the plugin; nothing loads one at runtime or from the configuration.

The broker does the NGSI-LD work: a sample becomes an attribute write (observedAt = the sample's time), with its notifications and its temporal event. A value that came in from a transport is never published back out of it; keeping its own writes from coming back in as samples is the plugin's job. The concepts and the configuration file: Plugin architecture - what crosses a bridge.

The entry points, in the order they are called

corBridge/BridgeDriver.h is what the plugin fills in (broker → plugin), corBridge/BridgeBroker.h what the broker hands it (plugin → broker). Every slot is documented in the header; the corBridge API page lists them.

Entry pointThreadWhat the plugin does
bridgeRegister(BridgeDriver*)broker, at loadthe one function the broker looks up: fills in the alias, the version and the entry points it has
init(configFile, brokerP)broker, last in start-upkeeps brokerP (valid until close returns), reads its own member of the configuration file, brings the transport up. configFile is the --bridgeConfig file, else bridges.json in /opt/seamware/etc ($SEAMWARE_ETC_DIR) when it exists, else NULL
channelTypedAdd / channelAddInfo / channelAddbroker, after initonce per channel: checks the endpoint and its channelInfo, subscribes. The broker calls the newest the plugin has: channelTypedAdd (ABI 15), else channelAddInfo (ABI 9), else channelAdd

channelDel is in the contract and is not called: channels come from the configuration file (and from endpoints a transport discovers) and none is removed while the broker runs. A plugin may leave it NULL.

bridgeRegister and the ABI handshake

BRIDGE_ABI_VERSION is 16. The structs are append-only - never reordered, resized or repurposed - and the broker owns them: it zeroes the BridgeDriver, writes its BRIDGE_ABI_VERSION into abiVersion, and calls bridgeRegister. The struct has the size of the broker's header, so the plugin fills in no slot the broker is too old to have, then writes its own version back. A mismatch is logged (INFO), not refused, and an older plugin's unfilled slots are NULL - which is how "not supported" is spelled. From the template:

__attribute__((visibility("default"))) void bridgeRegister(BridgeDriver* driverP)
{
  if (driverP->abiVersion < 1)
    driverP->abiVersion = 1;                          // a host from before the handshake

  driverP->alias       = "tmpl";                      // --bridges tmpl, and its member of --bridgeConfig
  driverP->version     = "0.1.0";
  driverP->args        = NULL;
  driverP->init        = tmplInit;
  driverP->close       = tmplClose;
  driverP->versionInfo = tmplVersionInfo;
  driverP->channelAdd  = tmplChannelAdd;
  driverP->channelDel  = tmplChannelDel;
  driverP->publish     = tmplPublish;

  if (driverP->abiVersion >= 9)
    driverP->channelAddInfo = tmplChannelAddInfo;

  driverP->abiVersion  = BRIDGE_ABI_VERSION;
}

The other direction is the same rule: an upcall added after ABI 1 is called only after checking brokerP->abiVersion and that the pointer is not NULL - a host that is not the broker (the test client) fills in only what it needs, and a broker built without a feature leaves its slot NULL:

#if BRIDGE_ABI_VERSION >= 12
  if ((brokerP != NULL) && (brokerP->abiVersion >= 12) && (brokerP->channelStatusIn != NULL))
    brokerP->channelStatusIn("tmpl", endpoint, BridgeChannelDormant, why);
#endif

A plugin written in C++ declares bridgeRegister extern "C", or the broker's dlsym does not find it.

The optional slots

A slot left NULL means "not supported": the broker checks every slot before calling it, and treats a NULL as BRIDGE_UNSUPPORTED. A plugin fills in what its transport does - the template fills in the ABI 1 slots and channelAddInfo; a bridge that only reads (inbound channels) has no publish.

Return codes and the rules of the seam

CodeValueMeaning
BRIDGE_OK0done
BRIDGE_ERR-1the transport, or the plugin, failed
BRIDGE_NOT_FOUND-2no such endpoint / channel
BRIDGE_UNSUPPORTED-3the plugin does not implement this
BRIDGE_BAD_INPUT-4malformed endpoint or payload
  • Plain data. Every parameter is const char*, an integer or a bool: no tree node, no allocator, no NGSI-LD type. A plugin need not be C - the DDS bridge is C++.
  • Borrowed. The json handed to publish (and every other text the broker passes) is the broker's for the duration of the call: copy what is needed after it. The broker parses what the plugin hands to sampleIn into its own buffer before returning.
  • Threads. publish, serviceInvoke, actionGoalSend and payloadCheck run on a broker thread inside a client's request and must not block. sampleIn and the other upcalls come from the plugin's own threads; the broker sets up its per-request state and takes its locks inside the call, and the plugin prepares nothing. Call it without a lock of the plugin's own held that a broker thread inside publish or the add call may be waiting for - the template's poller releases its mutex first.
  • Refusing a channel. Say why through channelStatusIn before the add call returns BRIDGE_BAD_INPUT or BRIDGE_UNSUPPORTED: GET /ngsi-ld/v1/channels then shows the plugin's reason; without it, the broker's own words. The reason is shown over the API - never a credential in it.

Broker symbols - built against the broker

The broker is linked -rdynamic with the Cor-Libs whole-archived, and a plugin is dlopened with RTLD_NOW. A plugin therefore calls corLog (COR_E, COR_W, COR_V, COR_I, COR_T), corAlloc, corJson and corTree without linking them - the template parses its configuration with corJsonParse and corTreeLookup in a CorAlloc buffer of its own. The way into the broker's NGSI-LD side is BridgeBroker and nothing else.

BRIDGE_ABI_VERSION covers the three structs and nothing else. A plugin that calls Cor-Lib functions must be built against the same Cor-Lib sources as the broker that loads it - for a packaged broker, the coraine-dev source of the same version. A function the broker lacks fails the dlopen; a changed signature is not detected. The tree node's layout is: BridgeDriver.h includes corTree/CorNode.h, so the plugin carries corNodeLayout, and a plugin built against another layout is refused at load (Built for this broker).

An export, not a copy: cp -r takes the template's .git along, with an origin that pushes to corBridgeTemplate - rename.sh warns when it sees that. rename.sh <name> takes the bridge's alias (lowercase letters and digits, starting with a letter; not tmpl), replaces every tmpl / Tmpl / TMPL with <name> / <Name> / <NAME> and corBridgeTemplate with cor<Name>Bridge, renames the files named tmpl*, removes the README's "from this template" section, and deletes itself.

The transport interface a real protocol fills in:

typedef void (*TmplReceiveFunc)(const char* endpoint, const char* json, int64_t timeNs);

extern int  tmplTransportOpen(CorNode* serverP, TmplReceiveFunc receiveF);
extern void tmplTransportClose(void);
extern int  tmplTransportEndpointAdd(const char* endpoint, BridgeDirection direction, bool text, const char** whyP);
extern int  tmplTransportEndpointDel(const char* endpoint);
extern int  tmplTransportSend(const char* endpoint, const char* json);

Connect in tmplTransportOpen without waiting for the peer where the protocol allows it - the broker's start should not hang or fail on a device that is not up yet; subscribe in tmplTransportEndpointAdd; send in tmplTransportSend; call receiveF from the thread the protocol library delivers on. A transport with a slow round trip queues in tmplTransportSend and sends from a thread of its own, as the Modbus bridge does.

The example transport

A directory of files stands in for a device. An endpoint is a relative file path under server.dir (letters, digits, _ - . /, no ..); one thread polls every inbound endpoint's file each pollMs and reports a changed content once, with the file's modification time as the sample's time. A published value is written to a temporary file and renamed over the endpoint's file, and remembered as its last content, so it does not come back in as a sample. At most 64 endpoints.

Configuration

One --bridgeConfig file serves every bridge, one member per alias. The ngsild section is the broker's - it makes the channels; the rest of the member is the plugin's, read in init:

{ "tmpl": { "server": { "dir": "/var/lib/tmpl", "pollMs": 1000 },
            "ngsild": { "topics": {
              "tank1/level": { "entityId": "urn:ngsi-ld:Tank:T1", "entityType": "Tank", "attribute": "level" },
              "tank1/state": { "entityId": "urn:ngsi-ld:Tank:T1", "entityType": "Tank", "attribute": "state",
                               "channelInfo": [ { "key": "format", "value": "text" } ] } } } } }
server.diran absolute path - mandatory; init fails without it
server.pollMsan integer, 10-3600000, default 1000
channelInfo formatjson (the default: the content is JSON) or text (the content becomes a JSON string); any other key is refused

A channel's direction is both unless the file says otherwise, and every configured attribute exists from start-up with the value "uninitialized" until the first sample. A sample on an endpoint no channel claims goes to the catch-all entity urn:ngsi-ld:tmpl:default, unless the section says "defaultEntity": false.

coraine --bridges tmpl --bridgeConfig bridges.json            # installed in <plugin dir>/bridge
coraine --bridges $PWD/tmpl.so --bridgeConfig bridges.json    # a name with a '/': a path, used as it is

Building

make                  # tmpl.so, debug (traces compiled in: -DCOR_T_ON)
make BUILD=release
make contract         # does src/tmplRegister.c still satisfy BridgeDriver.h?
make install          # to /opt/seamware/plugins/bridge (PLUGIN_DIR=...)

The Cor-Lib headers are found in COR_LIBS, default .. - the sibling repositories corLibs' bootstrap.sh clones. Without them and with the coraine-dev package installed, the installed broker's source (/usr/share/coraine/src/coraine-src.tar.xz) is unpacked into .coraine-src/ and used. For a broker built with coraine-build <dir>: make COR_LIBS=<dir> and make install PLUGIN_DIR=<dir>/install/plugins/bridge. The .so is compiled -fvisibility=hidden, so of the plugin's own functions only bridgeRegister is exported. make contract compiles src/tmplRegister.c alone - it includes no transport header, so the check runs where the transport library is not installed.

The functional test

make test

Starts coraine from PATH (the package, or . <dir>/install/env after coraine-build) on port 19026 with --database ramDB - no database server - loading ./tmpl.so by path, and runs test/funcTests/cases/*.test with corTest (Testing). COR_TEST_NO_REAP=on is set: corTest's start-up reaping kills every coraine on the host, and these tests stop their broker by its pid. TMPL_BROKER, TMPL_PORT, TMPL_PLUGIN and TMPL_TEST_DIR override; the broker's log is /tmp/tmpl-bridge-test/broker.log.

bridge_tmpl.test writes a value on the device (deviceWrite tank1/level 42.5 2026-10-01T12:00:00Z) and waits for the attribute (entityAwait), checks a text channel, PATCHes an attribute and waits for the device to receive it (deviceAwait), and lists the channels:

../escape dormant samplesIn=0 samplesOut=0 - not an endpoint of this transport - a relative file path, no '..'
tank1/level available samplesIn=1 samplesOut=0
tank1/setpoint available samplesIn=0 samplesOut=1
tank1/state available samplesIn=1 samplesOut=0

The refused endpoint shows the plugin's reason, and samplesIn=0 on tank1/setpoint is the no-echo check. A test asserts on what the API says, never on the broker's log. In a real bridge the device is the protocol's peer, started in the test's --INIT-- section - corMqttBridge's tests start mosquitto.

CI

.github/workflows/ci.yml runs on pull requests in the cor stack's CI image (quay.io/seamware/coraine-ci, a pinned tag - a TODO says to move it with coraine's). The repositories are siblings, as on a workstation: the bridge in stack/bridge, corLibs and coraine beside it. The steps: ./bootstrap.sh in corLibs, make contract (first, so a broken contract is named as such), make BUILD=release then a debug build, make di in coraine, then make test with CORTEST=../corLibs/bin/corTest. A failing run keeps the tests' .out, .diff and .stderr files and the broker's log.
