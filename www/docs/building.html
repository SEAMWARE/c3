Building from source

The published image runs the broker with no compiler involved. Build from source to change coraine, to run it where no image suits, or to compile out the features a deployment does not use.

1Install the system packages

Debian / Ubuntu:

TLSlibssl-dev

The mongo-c v2 driver is the most common build snag. Without MongoDB, build without it - cmake -DCOR_FEATURE_MONGOC=OFF - and run the broker with --database corDB.

2Clone and build the libraries

coraine links the Cor-Libs - corBase corLog corAlloc corArgs corHash corTree corJson corProm corRest corNgsild corJsonld corPlugin - and they must sit as siblings of coraine under one parent directory (by default ~/git): the build references ../<lib>/lib<lib>.a. The corLibs umbrella's bootstrap clones every one of them, and corTest, beside itself, and builds them:

git clone git@github.com:SEAMWARE/corLibs.git
./corLibs/bootstrap.sh

It works wherever it is cloned - the layout comes from the umbrella's own location. Later, make in coraine rebuilds corRest, corNgsild and corJsonld by itself; the other libraries must already be built.

3Build and install the broker

cd ~/git/coraine
make i             # release build + install
make di            # debug build + install

Install writes the broker to /usr/local/bin, the plugins to /opt/seamware/plugins and the configuration to /opt/seamware/etc - run it with the permissions for that, or create the directories first.

Installing while brokers run is safe. Each file is copied beside the installed one and renamed over it, never written in place: a running broker keeps the files it started with and loads the new ones at its next start. A plain copy onto a plugin a broker has loaded changes its code under it, and it dies of SIGSEGV within seconds.

4Check what the binary carries

coraine --version            # without starting it
coraine 0.6.0-dev
features: SUBSCRIPTIONS=1 REGISTRATIONS=1 GEOQ=1 CONTEXT_HOSTING=1 MONGOC=1 ...
httpServer: mhd
curl localhost:1026/build    # a running broker

GET /build answers with three kinds of fact, fixed at three different moments: the features compiled in (at the build), the plugins built against the ones loaded (at start-up, from a directory the binary does not own), and the runtime settings that change what a client gets (at a restart) - a broker with REGISTRATIONS compiled in and --distributed off accepts registrations and forwards nothing, and this is the one place both show. It is not under /admin: the admin API is itself a feature a build can leave out. GET /version is product, version and the linked libraries' commits.

coraine-build - a build from the installed packages

coraine-build builds a broker of your own from the exact source of the installed packages - the tarball coraine-dev installs (/usr/share/coraine/src/coraine-src.tar.xz), or a directory of git clones. Nothing is written outside the directory it is given, and root is not needed.

coraine-build --features REGISTRATIONS=OFF,SERVICE_EXECUTION=OFF,MONGOC=OFF ~/coraine-edge
. ~/coraine-edge/install/env           # bin/ on PATH, the broker pointed at plugins/ and etc/
coraine -fg --database corDB
OptionWhat it does
<dir>where the source is unpacked and built: a new or empty directory, or one an earlier coraine-build unpacked into (the source is then reused). The result is in <dir>/install: bin/coraine, bin/coraine-import, plugins/, etc/, env
--releaseoptimised, traces compiled out (--traceLevels is not there), no training - the default
--pgoprofile-guided: built instrumented, trained on the measured request shapes, rebuilt with the profile - what the coraine package and the image hold. A few minutes more; needs curl, wrk and python3; libmicrohttpd only
--tune <workload>profile-guided, trained on your workload, and the knobs measured on it; the best are kept in <dir>/install/etc/tune.env
--debug-g, not optimised, traces compiled in (--traceLevels works) - for reproducing a problem report, not for production
--features <list>comma-separated NAME=ON|OFF, the name without COR_FEATURE_ - the switches
--http-server <s>mhd (libmicrohttpd, the default) or builtin (corHttp) - below; builtin not with --pgo / --tune yet
--bridges <list>the bridge plugins to build: mqtt, modbus, dds, ckan, opcua, or none (default mqtt,modbus). One whose libraries are not installed stops the build and says so
--list-bridgesevery bridge, whether it can be built here and why not (--json: a JSON array)
--list-featuresevery feature switch, its default and what it is; with --json also its group and what it requires
--name <exe>the broker's executable name (default coraine) - a broker built for one role named after it. 1-64 of A-Z a-z 0-9 . _ -, starting with a letter or a digit; not coraine-import
--source <file>the source tarball (default: the one coraine-dev installs)
--source <dir>a directory of git clones, side by side as bootstrap.sh clones them: coraine at its checked-out commit, each library at origin/main (LIBS_REF=HEAD: the branch each clone has checked out). Committed trees only; coraine-dev is not needed

Compiling features out

Every feature that can be left out is a COR_FEATURE_* switch: cmake -DCOR_FEATURE_<X>=OFF, or coraine-build --features <X>=OFF. All are on by default except ICU_COLLATION. A route whose feature is compiled out keeps its place and answers 501, NotAvailableInThisDeployment - not 404: the resource is not missing, this deployment declined the feature, and the client's move is a different deployment.

Size is what turning the switch from its default changes in what a build installs - the stripped programs and plugins, and the libraries they load that a bare ubuntu:26.04 does not have. Measured 2026-10-13 on main c44d4b4e, release builds, one switch at a time against the default build (GEOQ: 2026-10-14). A stripped file grows in 4 KiB pages, so a small switch reads 0 or 4 KiB.

Tenants, entity scope, datasetId and multi-type entities have no switch - they are always in the broker. coraine-build --list-features --json gives every switch with its group and what it requires - each one of them - or requiresAny - one of them is enough. Every switch builds turned from its default alone: the nightly builds each one and checks that --version says so.

A reduced tree beside the ordinary one

make di CMAKE_FEATURES=-DCOR_FEATURE_REGISTRATIONS=OFF BUILD_DEBUG=BUILD_DEBUG_MINIMAL

CMake caches what it is given, per build directory. The same command again with a different feature keeps the previous one off as well, and the build still succeeds. Give each combination a directory of its own, and check coraine --version or GET /build after any reduced build.

A reduced build is at your own risk: the combinations nobody has tried are the ones most worth reporting. Open an issue at github.com/SEAMWARE/coraine/issues with the switches set and the GET /build output.

The HTTP server

cmake -DCOR_HTTP_SERVER=mhd        # libmicrohttpd - the default
cmake -DCOR_HTTP_SERVER=builtin    # corHttp - no external HTTP library
libmicrohttpd (mhd)corHttp (builtin)
Modela thread per connectionedge-triggered epoll loops sharing one port; loop 0 accepts and deals connections out in turn
Dependencieslibmicrohttpd 1.0.10 and GnuTLS behind it: nine libraries, 7.29 MiBcorAlloc and libc - 12 KiB of corHttp, -7.3 MiB against libmicrohttpd
--httpLoopsaccepted, ignoredthe number of loops; 0 (the default): one per core, at most four
POLICY_APIyesno - its port is a second listener, and corHttp has one
Profile-guided, tunedyesnot yet

The value reaches CMake and corRest's own make, and decides whether libmicrohttpd is on the link line at all: ldd coraine shows it took, and a running broker reports it as build.httpServer on GET /build. The wire format of both is the same, byte for byte.

The four-loop cap: on 8 cores, eight loops bought 16 % over four and made p99 seven times worse. One per core: four loops on a single core compete for it, and measure slower than one.

corHttp serves no TLS (the broker is put behind a proxy that does) and no HTTP pipelining - a second request in the same packet as the first is dropped; curl, browsers and the ETSI suite's HTTP library do not pipeline.

Which libmicrohttpd. The images and CI build 1.0.10 with corLibs' tools/mhd/mhdBuild.sh, which accepts a release tarball only with its pinned SHA-256. On a workstation: ~/git/corLibs/tools/mhd/mhdBuild.sh --sudo (to /usr/local, with TLS). A distribution's libmicrohttpd-dev works as well - but 1.0.4 and 1.0.5 fixed HTTP request smuggling (CWE-444): a release before 1.0.5 is not one to put behind a gateway.

Profile-guided and tuned builds

make pgo (coraine-build --pgo) builds the broker and its libraries instrumented, trains them on test/perf/pgoTrain.sh - perfRun's request shapes on corDB in RAM and on disk with history, a write that notifies, the three-broker forwarding chain over HTTP and cor:// - and rebuilds them with the profile: +1-10 % per core against Release, about 6 minutes, with wrk. The image is built this way.

make tune WORKLOAD=my-workload.json (coraine-build --tune) trains on your workload instead, and measures two more knobs on it - the memory allocator (glibc's malloc, jemalloc, tcmalloc) and --dbLockPrefer reads|writes. About 15 minutes; it writes tune-result.json, and the best settings to etc/tune.env in the install; make install_pgo installs the result. What it gains, the workload file, and how to run it: Extreme performance.

Measure on a quiet machine. A browser, a build or a video call running beside the training is measured too (make tune warns when a browser is up). Run it where the broker will run, or on the same kind of machine.
