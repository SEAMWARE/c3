corAlloc

An arena allocator: memory is handed out from a buffer by moving a pointer, nothing is freed one allocation at a time, and everything an arena gave out goes at once. A request's parse tree, its rendered response, a downloaded document - all of it lives in a CorAlloc and is dropped with it. Repository: SEAMWARE/corAlloc.

The model

A CorAlloc starts on a buffer the caller gives it - usually a char array on the stack or inside a struct. When that is used up it mallocs blocks of allocSize bytes and goes on from them; every block is kept in a list, and a reset frees the list.

Setting one up

void corAllocBufferInit(CorAlloc* kaP, char* buf, unsigned long long bufSize,
                        unsigned long long allocSize, CorAllocErrorHook errorHook, const char* name);
Argument
buf, bufSizethe initial buffer. The first allocation starts at its first 8-aligned byte
allocSizethe size of each block malloced when the buffer is used up. It must be well above the block header (CorAllocBuffer, 16 bytes on a 64-bit machine): 0 breaks the arena the moment the initial buffer is full
errorHookcalled on an allocation failure, or NULL
namekept as a pointer, not copied - for traces and debugging

Nothing is allocated by the call. Sizes coraine uses: a request's arena is an 8 KiB buffer inside corRest's request state with 256 KiB blocks (corRestStateInit.c); a cor:// request's a 64 KiB block size; small one-off arenas - an OIDC discovery document, a JWK Set - a stack buffer with 8-16 KiB blocks.

Allocating

FunctionWhat it returns
corAlloc(kaP, size)size bytes, zeroed, 8-aligned; NULL on failure or when kaP is NULL
corAllocStrdup(kaP, s)a copy of s in the arena; NULL when s is
corAllocRealloc(kaP, p, oldSize, newSize)a new allocation of newSize with the first min(oldSize, newSize) bytes of p copied in. The old one stays where it is, until the arena goes

What a call does, in order:

  1. the size is rounded up to a multiple of 8, so every pointer handed out is 8-aligned;
  2. a size of allocSize - sizeof(CorAllocBuffer) or more gets a block of its own (calloc), linked into the list; the current block is left as it is, and the next small allocation goes on from it;
  3. a size that fits in what is left of the current block is taken from it, and that part memset to 0;
  4. else a new block is malloced and the allocation is its first; what was left of the previous block is not used again.

A failed malloc is retried every 100 µs, up to 100 times; then corAlloc logs an error (COR_LIB_E), calls the error hook with CorAllocAllocError and returns NULL.

#include "corAlloc/corAlloc.h"

typedef struct Item { char* name; struct Item* next; } Item;

static int itemsCount(const char** nameV, int names)
{
  CorAlloc ka;
  char     buf[4096];
  Item*    first = NULL;
  int      n     = 0;

  corAllocBufferInit(&ka, buf, sizeof(buf), 16 * 1024, NULL, "items");

  for (int ix = 0; ix < names; ix++)
  {
    Item* itemP = (Item*) corAlloc(&ka, sizeof(Item));   // zeroed: next is NULL

    if (itemP == NULL)
      break;

    itemP->name = corAllocStrdup(&ka, nameV[ix]);
    itemP->next = first;
    first       = itemP;
    ++n;
  }

  corAllocBufferReset(&ka, false);                     // every Item and name, every block - gone
  return n;
}

coraine's one-off arenas have this shape - an OIDC discovery document, for one, is fetched, parsed by corJson into a tree in a 4 KiB stack arena with 16 KiB blocks, read, and dropped (src/plugins/auth/oidc/oidc.c).

Reset and teardown

void corAllocBufferReset(CorAlloc* kaP, bool reuse);

Both forms free every block of the list - the malloced ones and the oversized ones. What they do after that differs, and the difference matters:

reuse = true - resetreuse = false - teardown
the blocksfreedfreed
the initial buffermemset to 0, all of it (bufSize bytes)untouched
the CorAllocinitialised again (corAllocBufferInit with its own arguments): an empty arena, ready for the next cycleleft as it was: allocList still points at the freed blocks, the allocation pointer into the last one
after itallocate againdo not use the CorAlloc again - neither allocate nor reset it - until it has been through corAllocBufferInit

In a loop, reset with true. A corAllocBufferReset(kaP, false) followed by another reset of the same arena frees the same blocks twice - a double free that shows only once a cycle has outgrown the initial buffer. Teardown is for the end of an arena's life: a function's local arena on its way out, a thread's at its end. coraine's per-thread arenas that serve one cycle after another (the periodic notifications, the bridge samples, the high-availability events) reset with true; its one-off arenas end with false.

A reset with true also turns thread safety off: corAllocBufferInit sets threadSafe to false, so an arena made thread-safe has to call corAllocThreadSafe again after it.

Zeroing

Every allocation comes back zeroed - a struct needs no memset. The blocks themselves are malloced, not calloced: each allocation is zeroed as it is handed out, so the part of a block no allocation reaches is never written. The oversized blocks are calloced. A reset with true zeroes the whole initial buffer, whatever was used of it.

Threads

An arena is not thread-safe, and nearly every one is one request's or one function's, used by one thread. For an arena shared between threads:

void corAllocThreadSafe(CorAlloc* kaP);

Called once, after corAllocBufferInit and before a second thread can reach the arena: from then on every allocation takes the arena's mutex. An arena that is not thread-safe pays one branch. It protects the arena only - what the allocations hold is the caller's to protect. coraine has one such arena: the JSON-LD context store, into which every thread that downloads or parses an @context allocates (src/app/coraine/coraine.c, a 64 KiB static buffer and 256 KiB blocks).
