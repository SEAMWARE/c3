Performance and footprint

How small coraine is - on disk, in RAM, at start-up - how fast it answers per operation and per database, how it holds up with more entities and more cores, and what the durable configuration costs. Every number comes with the conditions it was measured under.

Two other guides cover what makes a deployment faster than these numbers: Extreme performance (indexes on the attributes you query, and a broker trained on your workload) and Database indexes (what each store indexes).

Where the numbers come from

One machine, a laptop, and release builds. Nothing here is an estimate.

DatabasesMongoDB 8.2 and PostgreSQL 16 + TimescaleDB as containers on the host network, unless a table says otherwise

Four builds are measured - the two axes that change what a coraine process is made of:

  • The HTTP server - corHttp, the built-in epoll server, with no external dependency; or libmicrohttpd (the default of the image and the packages).
  • The current-state database - --database corDB, the entities in the broker's own RAM (on disk too with --dbDir); or --database mongoc, the entities in a MongoDB server.

Every rate is per core unless it says otherwise: the broker is pinned to a stated number of physical cores (the SMT siblings left out, the topology read from /sys), and the load generator runs on other cores. A figure is the median of three 5-second wrk -t8 -c50 runs, each started on a quiet machine (load average below 2); a run stops at the first non-2xx answer. The fixture is 100 five-attribute entities of ~550 bytes each, so a limit=20 query returns about 11 KB. TRoE is none unless a row says otherwise.

Latency depends on how deep the CPU sleeps. With one client, most of a request's time is a core waking up: the three-broker cor:// chain gave 11 000 requests/s with the idle states as the machine ships them, 14 200 with the deep ones disabled - the same build, minutes apart. Every latency here is taken with the deep states on, the machine's own setting. Many clients keep the cores awake, so throughput barely moves.

The stored trees

What corDB keeps of an entity is a tree of nodes, allocated in the tree heap: a node, its name and a string value in one block, carved from 16 KiB pages, with no allocator header per block. A node that is not an object or an array is 32 bytes, not 40.

Threads building trees at once

Every thread writing the store builds and frees tree nodes - a batch update of 20 entities clones and frees thousands, in a few sizes. Each thread keeps a cache of free blocks per size class, taken and freed with no lock; the class's mutex is taken once for a batch of blocks (4 KiB worth, 32 at most), and once to give a batch back when a thread holds two. A thread that ends gives its cache back. The cost is up to 8 KiB a class a thread; with 300 000 entities stored the broker's RSS did not move (641 MB both).

What the durable configuration costs

--dbDir makes corDB survive a restart. Every write appends its effect to a memory-mapped log, so the record is in the kernel before the response; the log is synced to the disk every 100 ms (--dbSync interval, the default) and snapshotted as it grows. A broker that dies loses nothing it acknowledged; a machine that dies, at most the last 100 ms. The tables marked --dbDir use this configuration.

  • Reads cost nothing - they never touch the log.
  • A write that changes the store costs 4-21 %: encoding its record and copying it into the log. An attribute update logs the attributes, not the entity.
  • Creates cost more, because a growing store needs snapshots: batch create's p99 is 23.6 ms against 2.06 ms in RAM.
  • --dbSync request runs at the disk's speed: ~1 800 writes/s on one connection, ~21 000-24 000 with fifty sharing each sync.
  • --dbCompress: on eight cores every scenario within -2.3 to +2.9 %; batch create with history, the scenario that snapshots most, -7.4 %.
  • A store that pauses when its log cannot be written (the pause) costs a write one atomic load: every single-entity scenario within ±2.5 % of the same broker without it (2026-10-27, the conditions of Threads building trees at once).
  • Recovery: 100 000 entities (38 MB of log or snapshot) are back in 0.19 s after kill -9 or a clean stop (2026-10-04).

The history in TimescaleDB

The timescale plugin's writer threads (--troeWriters, 8 in these runs) put the history rows of many requests in one transaction. Counted until the last history row is in the database, on the eight shared cores: create 24 025/s, create on one connection 7 601/s, batch create (20) 2 321/s; 120 000 history rows/s on a create at 50 connections. A create costs the broker 82 µs without history, 97 µs with.

--troeSync hands a request's history to the writers before the response, so a temporal read sees it at once; the response does not wait for the commit. It costs -0.0 to -6.4 % (create on one connection, about 6 µs a create); reads -0.4 %.

2026-10-21, PGO build, mongod 8.2 and PostgreSQL 16 + TimescaleDB on the eight shared cores, synchronous_commit on, 5 s after a 2 s warm-up, ABBA.

Pin both sides when measuring a container. Unpinned, the load generator and the containerised broker compete for the same CPUs, and the container loses: large query responses looked 40 % slower than natively. Pinned, the difference is gone.

Measuring it yourself

test/perf/reproduce.sh produces the core figures from a published image, Docker and wrk. It pins the broker to 1 and then 4 physical cores, runs wrk on others, and prints a figure only if every response was a 2xx and, for writes, the broker's entity count matches what wrk saw acknowledged. The report names the image by digest, the CPU and the kernel. Linux only.

curl -fsSLO https://raw.githubusercontent.com/SEAMWARE/coraine/main/test/perf/reproduce.sh
less reproduce.sh                                   # the load scripts are inside it
bash reproduce.sh quay.io/seamware/coraine:<version>   # CORES="1 2 4 8", DURATION, REPEATS change the sweep

From source, test/perf/perfRun.sh runs every request shape and prints one JSON object per run (PERF_BROKER_CORES pins the broker, PERF_ENTITIES sizes the store), test/perf/coreScale.sh sweeps cores, and test/perf/corChain.sh measures forwarding through three brokers.

The full measurements - the PGO tables of both HTTP servers, forwarding over HTTP and cor://, the request arena's and the HTTP server's sizes, the subscription matching, the costs of authorization, and every scenario on mongoc: doc/performance.md.
