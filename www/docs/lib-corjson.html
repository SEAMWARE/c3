corJson - JSON in and out of a tree

The JSON parser that turns text into a corTree, the renderers that turn a tree back into text, and the corJson command-line tool built on them. Every request body coraine reads over HTTP and every JSON response it sends goes through it.

Parsing

CorJson* corJsonCreate(CorJson* corJsonP, CorAlloc* kaP);
CorNode* corJsonParse(CorJson* corJsonP, char* json);

A CorJson is the parser's state and its rendering settings, over an allocator (corAlloc). corJsonCreate zeroes the struct it is given (or callocs one for NULL) and sets the defaults; with no allocator it makes one of its own, an 8 KiB malloc. One CorJson per thread: it holds the parse in progress. This is how coraine reads a bridge configuration file:

char      kallocBuffer[8192];
CorAlloc  kalloc;
CorJson   corJson;

corAllocBufferInit(&kalloc, kallocBuffer, sizeof(kallocBuffer), 8 * 1024, NULL, "bridge config");

CorJson* corJsonP = corJsonCreate(&corJson, &kalloc);
CorNode* treeP    = corJsonParse(corJsonP, buf);

if (treeP == NULL)
  printf("line %d, position %d: %s\n", corJsonP->lineNo, corJsonP->errorPos, corJsonP->errorString);
...
corAllocBufferReset(&kalloc, false);      // the tree goes with the allocator

In place

The text is parsed in place, and the tree points into it. A string is unescaped where it is and terminated there; a node's name and a string's value.s are pointers into json. The buffer is changed, must be writable (not a string literal), and must live as long as the tree. Parse a copy when the text is needed again - coraine passes corAllocStrdup(&corRest.kalloc, text).

The nodes come from the CorJson's allocator, 40 bytes each, zeroed - flags, kind and termId included. Such a tree is never freed node by node: it goes when the allocator is reset. A tree that must live on is cloned into the tree heap, which copies the strings out of the buffer as well:

CorNode* parsed = corJsonParse(corRest.corJsonP, buf);
if (parsed == NULL)
  COR_X(1, "contextSourceExtras: '%s' is not valid JSON", path);

ldContextSourceExtras = corTreeClone(NULL, parsed);   // buf and the allocator may go now

The returned node is the document's top level - an object, an array, or a scalar - named "toplevel object", "toplevel array" or "toplevel value".

What it accepts

InputResult
a number with no fraction and no exponentCorInt, a long long
a number with a fractionCorFloat; the first 12 decimals are kept, the rest read and dropped
a positive exponent whose result fits a long long (5e3)CorInt (5000)
any other exponent (5e-3, 5e30, 1.5e3)CorFloat, by strtod_l in the C locale - correctly rounded, whatever the process's locale
\", \\, \/, \b, \f, \n, \r, \t, \uXXXX and surrogate pairsunescaped to UTF-8
a leading + (+5), a fraction with no digits (1.)accepted: 5, 1

Refused, with an error: a leading zero (01), a hex number, an exponent with no digits, a raw tab or newline inside a string or a name, an unknown escape, a lone surrogate, a trailing comma ([1,], {"a":1,}), a double comma, a missing colon, an unterminated string, anything after the document.

Limits that are not checked. An integer of more than 19 digits overflows silently - 12345678901234567890123 is read as 4807115922877859019. A float beyond the range of a double (1e400) is infinity, and is rendered as inf.

Nesting is limited to 100 levels of objects and arrays: the parser recurses once per level, and so does every walk of a tree after it. A deeper document is refused - JSON Parse Error: nested deeper than 100 levels, status CorJsonMaxDepthExceeded - even when it is valid JSON.

Errors

On an error corJsonParse returns NULL and the CorJson says why: errorString (JSON Parse Error: expecting comma or end of array), errorPos (the offset in the buffer), lineNo and status - the kind of failure: CorJsonMaxDepthExceeded, CorJsonAllocError, else CorJsonParseError (CorJsonOk after a parse that succeeded). An errorF callback, if set (corJsonConfig(corJsonP, CorJsonConfigErrorFunction, (char*) fn)), is called once, with the line, the position, the text and the rest of the buffer. The parse stops at the first error.

Hooks

FieldCalled
keyFfor each object member, the moment its name is final - unescaped, terminated, the node linked into its container - and before its value is parsed: bool keyF(CorJson*, CorNode* containerP, CorNode* nodeP, int depth). It may stamp the node (flags, termId) or point nodeP->name elsewhere; false refuses the name and fails the parse. depth counts the enclosing containers: a top-level object's members are at 1, those of the objects in a top-level array at 2. keyDataP is the hook's own state. corNgsild sets it to classify the NGSI-LD core terms of a request body as it is parsed - no second walk of the tree.
addFto add a member to its object - NULL appends; corJsonConfig(..., CorJsonConfigSorted, NULL) sets corTreeChildAddSorted (CorJsonConfigSortedReverse: descending). Array items are always appended.
saxFfor each event of the parse - start, end, object and array start and end, each value - with the name, the value and whether it is in an array (CorJsonConfigSaxFunction)

corJsonReset(corJsonP) clears the state of the last parse, the hooks and the rendering settings, for a CorJson that is used again.

Rendering

int  corJsonFastRenderSize(CorNode* nodeP);
void corJsonFastRender(CorNode* nodeP, char* buf);

int  corJsonRenderSize(CorJson* corJsonP, CorNode* nodeP);
void corJsonRender(CorJson* corJsonP, CorNode* nodeP, char* buf);
RendererOutput
corJsonFastRendercompact - no whitespace at all - and needs no CorJson
corJsonRenderlaid out by the CorJson's settings - two spaces per level, a newline after each member, a space after the colon by default - and ends with a newline

The renderers take no buffer size. They write as much as the tree needs: size the buffer first with the matching ...RenderSize function, plus one for the terminating zero, as coraine does:

char* text = (char*) malloc(corJsonFastRenderSize(treeP) + 1);
corJsonFastRender(treeP, text);
  • A string is escaped: ", \, the control characters (\n, \t, ..., the rest as \u00XX); every other byte, UTF-8 included, is written as it is.
  • An integer is written in full, up to 19 digits and a sign.
  • A float is written with at most 9 decimals, trailing zeros removed (1.50 is 1.5, 2.0 is 2, 0.1234567890123 is 0.123456789); one whose integer part is 1e21 or more, or one too small for 9 decimals, as the shortest %g form that reads back exactly (1e+30).
  • A scalar on its own renders without its next: the value alone.
  • The order is the tree's - insertion order. A sorted rendering is a sorted tree: corTreeSort, or a parse with CorJsonConfigSorted.

corJsonConfig(corJsonP, item, value), before corJsonRender:

ItemEffect

CorJsonConfigNewlineStringthe newline string ("": one line)
CorJsonConfigSpaceBeforeColon, CorJsonConfigNoSpaceAfterColonaround the colon
CorJsonConfigObjectStartOnNewLine, CorJsonConfigArrayStartOnNewLinethe opening bracket on a line of its own

The indentation strings are allocated in the CorJson's allocator at the first indented render.

The corJson tool

corJson reads one JSON document - a file, or stdin - and prints it, parsed and rendered again:

corJson file.json              # two spaces per level
corJson -sort file.json        # object members in alphabetical order
corJson -min < file.json       # compact, from stdin
corJson -i 4 -saol file.json   # four spaces, short arrays on one line
corJson -bin file.json         # through the cor binary format and back - the output must be the same
corJson -u                     # every option
Option
-sort, -rsortobject members in alphabetical order, or the reverse - array items keep their order
-min, -olno whitespace at all; one line
-i <n>spaces per level
-sbc, -nsaca space before the colon; none after it
-onl, -anlan object's, an array's opening bracket on a new line
-aol, -ool, -saol, -soolarrays, objects, short arrays, short objects on one line; -saml <len>, -soml <len> what is short (80)
-o <file>, -srthe output to a file; to stderr
-bin, -binStatsa round trip through the cor format (cor://) - -binStats also prints the compact JSON's size and the cor size to stderr
-saxTesta log line per SAX event, and no output
-t, -T, -v, -Vtrace levels and verbose mode, of the tool and of the libraries

A document that does not parse is said on stderr with its source (pipe for stdin), line, reason and position, and the exit code is 10:

$ echo '[1,2' | corJson
kjson: pipe[1]: JSON Parse Error: expecting comma or end of array (offending buffer position: 6)

The tool's input is at most 64 MiB. A second file name is refused. -u exits 1.

coraine's functional tests need it. corTest pipes every response body through corJson -sort before comparing it with the expected one - member order is insertion order and none of a test's business - so the tool must be on PATH, or CORJSON must point at it (Testing).

Trace levels

With corLog: 50-54 parsing (values, objects, arrays, allocation) and 56-63 rendering - corTree has 55 and 64-66.
