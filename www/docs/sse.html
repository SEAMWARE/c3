Server-Sent Events

A subscription made on its own event stream: one POST creates it, and the response stays open with its notifications as events. For a client the broker cannot connect to, that wants neither a WebSocket nor a server of its own - nothing but plain HTTP.

curl -N -H 'Content-Type: application/json' -d '{
  "type": "Subscription", "entities": [ { "type": "Vehicle" } ],
  "notification": { "endpoint": { "uri": "urn:ngsi-ld:self" } } }' \
  http://localhost:1026/ngsi-ld/v1/subscriptions
: stream

event: notification
data: {"id":"urn:ngsi-ld:Notification:...","type":"Notification","subscriptionId":"urn:ngsi-ld:Subscription:...","data":[...]}

The 201 is a text/event-stream that does not end - the WHATWG HTML standard's Server-Sent Events (HTML § 9.2): events made of event: and data: lines with a blank line after each, and comments, lines that start with :. A change-driven subscription's events come as the entities change, a periodic one's once per interval. The broker never connects to the client; the client's other requests are ordinary HTTP requests.

In the build by default; -DCOR_FEATURE_SSE=OFF leaves it out, and so does SUBSCRIPTIONS=OFF (Building). No plugin to load.

Creating it

POST /ngsi-ld/v1/subscriptions or POST /ngsi-ld/v1/csourceSubscriptions on the broker's HTTP port, with notification.endpoint.uri urn:ngsi-ld:self. The endpoint alone decides - no header is needed.

HTTP/1.1 201 Created
Location: /ngsi-ld/v1/subscriptions/urn:ngsi-ld:Subscription:...
Content-Type: text/event-stream
Cache-Control: no-cache
X-Accel-Buffering: no
Transfer-Encoding: chunked

an Accept without text/event-stream, text/* or */* (no Accept is fine)406

Anything else a subscription is refused for is refused here too, before the stream: the 201 is the stream, an error is an ordinary response. Accept: text/event-stream on a subscription with another endpoint is an ordinary create whose 201 is JSON - an Accept naming only text/event-stream is then a 406.

On the subscriptionWhat it does
endpoint.acceptapplication/ld+json (the default with this endpoint) puts the @context in each notification's body - an event has no Link header to carry it; the core context when the subscription names none. application/json leaves it out.
endpoint.urishown as urn:ngsi-ld:self by GET /subscriptions/{id}
timesSent, lastNotification, lastSuccessmove when an event is written on the stream

A subscription stays on its stream for its whole life. A PATCH that changes the endpoint to or from urn:ngsi-ld:self is a 400. Everything else is patched as on any subscription, but a periodic one stays periodic and a change-driven one change-driven: adding or removing timeInterval is a 400. The interval itself may change.

The stream

WhenOn the stream
at oncethe comment : stream. A notification made before the stream is open waits for it (up to 1000 of them).
per notificationevent: notification, one data: line with the Notification (or ContextSourceNotification) as JSON on one line, a blank line. No id: - there is nothing to resume.
15 s with nothing sentthe comment : keep-alive, so that a proxy does not close an idle stream

How it ends

  • The client leaves - it closes the connection, or is killed: the broker sees it within a second and deletes the subscription.
  • The broker ends it when the subscription is deleted (DELETE), when the client falls 16 MiB behind (the connection is cut, the subscription deleted), and when the broker stops (every stream ended, every subscription on one deleted).
  • A killed broker deletes nothing. At its next start every subscription and context source subscription on urn:ngsi-ld:self is deleted, in every tenant - no stream outlives the broker that served it. Not with --high-availability: there, a stream may be another instance's, open.

Periodic subscriptions

A subscription with timeInterval (seconds) is made on its stream the same way, for entities and for context sources:

  • the first event within a second of the 201, then one per interval - the matching entities as they are then. Two events are never closer than the interval.
  • Entities: an interval in which no entity matches sends no event (the keep-alives still come). Context sources: an event every interval, its data empty when no registration matches (§ 12.4.7).
  • an entity subscription's counters move when the event is handed to the stream; a context source subscription's when it is written.

In a browser

EventSource sends a GET, so a page reads the stream with fetch():

const r = await fetch('/ngsi-ld/v1/subscriptions', { method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ type: 'Subscription', entities: [ { type: 'Vehicle' } ],
                         notification: { endpoint: { uri: 'urn:ngsi-ld:self' } } }) });
const reader = r.body.pipeThrough(new TextDecoderStream()).getReader();
let text = '';
for (;;) {
  const { value, done } = await reader.read();
  if (done) break;                                 // the stream ended: the subscription is gone
  text += value;
  let end;
  while ((end = text.indexOf('\n\n')) >= 0) {
    const block = text.slice(0, end); text = text.slice(end + 2);
    const data = block.split('\n').find(l => l.startsWith('data: '));
    if (data) console.log(JSON.parse(data.slice(6)));
  }
}

With --auth the request carries its token (Authorization) as every request does; the stream is the response to the create, so it is authorized as the create is (Authorization).

The same in both: a client that reconnects creates its subscriptions again and is sent nothing it missed; a subscription ends with its connection; a killed broker's are deleted at its next start. c³ uses the WebSocket.

Server-Sent Events is not a transport - a transport carries the API; this carries one subscription's notifications. Nor is it a notification binding: there is no address the broker sends to, the notification is written on a response that is already open.

Deployment

A buffering proxy holds events back. nginx buffers unless told not to; the broker's X-Accel-Buffering: no tells it, per response. APISIX is nginx.

  • A browser over HTTP/1.1 opens about 6 connections per host, and each open stream is one. A page reading many subscriptions wants HTTP/2 in front, or one subscription for them all.
  • --sseStreams caps the streams open at a time - default 1000; one more is a 503.

NGSI-LD

Not in the specification: its bindings are HTTP and MQTT. Server-Sent Events solves what MQTT solves - a broker that cannot reach the client - with no second server and no WebSocket. Not yet: Service Executions' notifications (POST /services) on a stream.

How it is built - corRest's response stream, corNgsild's urn:ngsi-ld:self hook, the broker's stream table: doc/sse.md.
