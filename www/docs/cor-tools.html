corTools

corTools holds three command-line programs built on the Cor-Libs: a cor:// client and load generator, the other end of a functional test, and a fast MongoDB drop. coraine's functional tests use all three; nothing in them is specific to the tests.

ToolWhat it is
corRequesta cor:// client - one request, like curl -i; several at once; or load, like wrk, also at a fixed rate and over http://
corTestClienta notification receiver (HTTP, HTTPS, MQTT), a mock context source with programmed replies, and a host for the broker's bridge plugins - the peer a bridge talks to
corMongoDropdrops MongoDB databases or collections over one libmongoc connection; built only where libmongoc is

corRequest

A client for the broker's binary API, cor://. It encodes the request with corNgsild's codec and sends it with corRest's cor:// client.

corRequest --url cor://localhost:2026 --path /ngsi-ld/v1/entities/urn:E1
corRequest --url cor://localhost:2026 -X POST --path /ngsi-ld/v1/entities \
           --payload '{"id": "urn:E1", "type": "T", "p": {"value": 1}}'

One request prints STATUS <code>, the headers, an empty line and the body as JSON.

ModeSelected byWhat it does
one requestthe defaultprints the response as above
as corCurl--curl --bodyFile <f> --pretty <n>the header block exactly as curl -D shows the HTTP server's - status line with its reason phrase, Date, the broker's headers, Content-Length - and the body in <f>. Content-Length is the size the broker would render at --pretty spaces per indent. This is how the functests' corCurl runs a test over cor:// with every expectation unchanged
parallel--paths 'p1|p2|...'each path sent at once, the answers printed as they come; --sockets 1 puts every path on one connection (multiplexed), 0 a thread and a connection each
load-c <n> --duration <s>n connections, each a thread sending one request after the other for s seconds; prints requests per second and the p50 / p90 / p99 / max latency
load at a rate-c <n> --rate <r>each connection sends its share of r requests per second on a schedule; a latency counts from when the request was due, so a slow answer delays the requests behind it and they count that delay (as wrk2)

An http:// URL loads an HTTP server - load mode only, GET only (keep-alive, Content-Length bodies):

corRequest --url http://localhost:1026 --path /ngsi-ld/v1/entities/urn:E1 -c 16 --rate 20000 --duration 8
OptionWhat it is

--pathpath and query, default /ngsi-ld/v1/entities

--payload / --payloadFilethe request body, JSON - on the command line, or from a file
--header, -H'Name: value', several separated by |
--conns, -cload mode: connections, 0-1024 (0: one request)
--durationload mode: seconds, 1-3600, default 8

Exit codes: 0 a response came back (whatever its status), 1 none did, 2 bad arguments, an unreadable --payloadFile or an http:// URL outside load mode or not GET, 3 the payload is not JSON - a request only HTTP can carry. In coraine's functests each broker also listens on cor:// at its HTTP port + 1000, and COR_TRANSPORT=cor sends every request it can through corRequest --curl (Running the suite).

corTestClient

The far end of a test: whatever the broker sends - a notification, a forwarded request - lands here and is kept until a test reads it. It is a corRest server, one thread per connection.

corTestClient --port 7701                       # a notification receiver
corTestClient --port 7702 --status 500          # a receiver that fails every POST
corTestClient --port 7703 --mqttPort 1883 --mqttTopic 'plant/#'
curl localhost:7701/dump                         # what arrived since the last dump - and consumed
RequestWhat it does
GET /dumpthe requests received since the last dump, as a JSON array (verb, url, payload, ...), and consumes them
GET /counthow many are kept, as a bare integer - no JSON parser needed
GET /probeCounthow many /info/sourceIdentity probes arrived (kept out of the dump)
GET /mqttReady1 once the MQTT subscription is acknowledged (or none was asked for), 0 not yet, -1 given up - the log says why
GET /dieexits the process
POST /mock/replyprograms a reply: { "verb": "POST", "path": "/attrs/", "status": 207, "body": {...} } - matched on the verb and a substring of the path; delayMs sleeps before answering, raw is a body sent verbatim. Kept until DELETE /mock/reply
POST /mqtt/publishputs a message on the MQTT broker: { "topic": ..., "payload": <JSON> }, or "text" for a payload sent exactly as given - a device on the bus, for the MQTT bridge tests
POST /bridge/publish{ "endpoint": ..., "payload": <JSON> } through a hosted bridge plugin's publish - the bridge with the alias dds, else the first loaded
POST /bridge/serviceReply{ "endpoint": ..., "payload": <JSON> }: what to answer when the broker calls that service
anything elseGET, POST, PATCH, PUT, DELETE on any path: kept for /dump, answered with --status (or a programmed reply)
OptionWhat it is
--port, -pdefault 7701
--status, -sthe status every kept request is answered with, 100-599, default 200
--delaymilliseconds to sleep before answering - for timeout tests
--discardrequests counted (GET /count), not kept - a benchmark's receiver
--traceLevelsdefault 0-255 (the functests read them); "" for none
--httpsKey, -k / --httpsCertificate, -cPEM files: serve HTTPS (both needed)
--mqttPort, --mqttTopic, --mqttUser, --mqttPassword, --mqttTlssubscribe to an MQTT broker (port 0: none; topic default #; TLS accepts a self-signed certificate); the messages are kept as requests are
--bridges, -br / --bridgeConfig, -brcbridge plugins to host, and the broker's own bridge configuration file
--foreground, -fgdefault on

Hosting a bridge plugin

With --bridges, corTestClient loads the same .so the broker loads - resolved under /opt/seamware/plugins/bridge ($SEAMWARE_PLUGIN_DIR), or a path - with the same ABI handshake, calls its init with the configuration file, and subscribes to every endpoint the file names. Its BridgeBroker fills in sampleIn, logFunction and sampleQualifiedIn: a sample is kept for /dump rather than stored. That is what lets a test put a value on a transport and read what the broker made of it, and answer a service the broker calls through the plugin's serverIface. The contract: Writing a bridge.

In coraine's functests

corTestFunctions.sh wraps it: ftClientStart [--port P] [--status S] ... starts one, with its pid, log (/tmp/corTestClient.<port>.log) and scheme kept per port, so several run at once; ftClientDump, ftClientCount and ftClientStop go with it. The binary is corLibs/bin/corTestClient - Writing a test.

corMongoDrop

corMongoDrop [--host H] [--port P] --db NAME                      # drop the database NAME
corMongoDrop [--host H] [--port P] --db NAME --collections a,b,c  # those collections of NAME
corMongoDrop [--host H] [--port P] --prefix P                     # every database named P, or P-...
corMongoDrop [--host H] [--port P] --prefix P --contains S        # ... whose name also contains S

The host defaults to localhost, the port to 27017; one of --db and --prefix is needed. Exit 0 when it could talk to the server - a database or collection that does not exist is a no-op, not an error - 1 when it could not, 2 for bad arguments. The functests drop with it before almost every test, and fall back to mongosh where it is not built; the cost of each is in Testing.

Building

A sibling of the Cor-Libs, like every repository of the stack (-I.., ../<lib>/lib<lib>.a). The corLibs umbrella builds it after every library and collects the tools into corLibs/bin, beside corTest:

make -C ../corLibs di                # the whole stack
make di                              # this repository alone, once the libraries are built:
                                     # bin/corRequest, bin/corTestClient, bin/corMongoDrop (where libmongoc is)
make COR_HTTP_SERVER=builtin di      # against a corRest built with the builtin HTTP server (corHttp)

It needs libmicrohttpd (or corHttp, with COR_HTTP_SERVER=builtin - it must be the server corRest was built with), OpenSSL and libmosquitto; corMongoDrop needs libmongoc (pkg-config mongoc2) and is skipped, with a line saying so, without it. The libraries are linked by path, whole-archived and exported (-rdynamic): a bridge plugin corTestClient loads calls into the libraries of its host. BUILD=debug (the default) compiles the traces in; EXTRA_CFLAGS adds flags without replacing the defaults. The tools land in bin/.
