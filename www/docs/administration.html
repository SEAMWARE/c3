Administration

Running a broker: its command-line options and their environment variables, the log, the admin API, the health probes, and the limits that keep it inside its memory. Installing one, and its databases' options: Installation.

Options

Every setting is a command-line option. coraine -u lists them with a description, coraine -U with each one's environment variable and type. The list depends on the plugins selected - a plugin brings its own (--dbHost comes with mongoc, --dbDir with corDB) - so ask with them: coraine --database corDB --troe timescale -u. On a running broker, GET /admin/config has every option with its value, its default and where the value came from.

Every option in full - its values, what it needs and refuses, an example: Command-line options.

Environment variables

Every option is also an environment variable: CORAINE_ + the long option in upper case, - becoming _ - --maxRequestSize is CORAINE_MAXREQUESTSIZE, --high-precision CORAINE_HIGH_PRECISION. A command-line argument overrides the variable. Two more variables move the installation's directories:

VariableDefault - what it does
SEAMWARE_PLUGIN_DIR/opt/seamware/plugins - where plugin short names resolve (read before the arguments are parsed)
SEAMWARE_ETC_DIR/opt/seamware/etc - where bridges.json and contextSourceExtras.json are looked for when their options are not given; a file missing there is not an error

Foreground or daemon, and where the log goes

By default the broker runs in the foreground and logs to stdout - what a container runtime (docker logs, kubectl logs), systemd (Type=simple, the journal) and a terminal take the log from. The package's service runs it that way.

--logTo stdout (default)--logTo file--logTo both
foreground (default)the log on stdout<logDir>/coraine.log onlyeach line in the file and on stdout
--daemonrefused<logDir>/coraine.logrefused

--daemon with --logTo stdout (the default) or both does not start - a daemon's stdout is /dev/null. Exit code 1, one line on stderr: coraine: --daemon with --logTo stdout: a daemon's stdout is /dev/null - use --logTo file. --daemon with -fg is refused as well.

  • The file is <logDir>/coraine.log - /var/log/coraine/coraine.log by default. The directory is not created; a file that cannot be opened stops the broker at start (Unable to open '...' for writing: ..., exit code 1). A coraine.log of an earlier start is renamed coraine.log.old. Created 0664 minus the umask.
  • Rotation: the broker does not reopen the file (no SIGHUP handler); it writes in append mode, so logrotate's copytruncate rotates it.
  • --daemon (-bg) detaches: fork (the command returns 0 at once), setsid, chdir /, stdin/stdout/stderr on /dev/null. Exit code 0 means detached, not serving: a start-up error after it is in the log file only. A relative path (--dbDir) is relative to / afterwards. There is no pid file - the log names the pid, with or without -v: I: ...: main: --daemon: detached, pid 236587. SIGTERM / SIGINT stop it in order, as in the foreground; SIGHUP is not handled and ends it without that.
  • systemd: the package's unit is Type=simple - do not set CORAINE_DAEMON=true there (a broker that detaches is a main process that exited, and systemd stops the service). A unit of your own with --daemon is Type=forking.
  • Environment: CORAINE_DAEMON=true (only true, any case, turns a boolean on), CORAINE_LOGTO, CORAINE_LOGDIR.
mkdir -p ~/coraine-log ~/coraine-db
coraine --daemon --logTo file --logDir ~/coraine-log --database corDB --dbDir ~/coraine-db --troe none
grep -- '--daemon: detached' ~/coraine-log/coraine.log      # the pid
kill "$(sed -n 's/^.*--daemon: detached, pid //p' ~/coraine-log/coraine.log)"

-fg / --foreground is deprecated: the foreground is the default, so it does nothing. Accepted through 0.7.x with one warning line at start, refused from 0.8.0: W: ...: main: -fg: the broker runs in the foreground by default now - the option is refused from 0.8.0

The log

The broker logs to its standard output by default - under systemd, the journal (journalctl -u coraine); in a container, docker logs; with --logTo file or both, <logDir>/coraine.log (above). Errors (E:) and warnings (W:) are always written; -v adds the rest.

E: 000010.339: adminIndexes.c[68]: storeHasIndexes: 501 Not Implemented: the store 'none' has no declared indexes

On a running broker the log and trace levels change through /admin/log - the way to look into a live instance, rather than restarting it with -t. A release broker that crashes writes what it takes to reproduce it - the request and its payload, the command line, the build id, the stack - to its log; the debug image of the same tag replays it.

Health port

With --healthPort <port> the broker answers probes on a port of its own, from a thread of its own - not the HTTP server, so a probe never queues behind requests. It opens before the store is loaded. How the probes are set up on a cluster: Kubernetes.

Request200503
GET /livethe broker makes progressa request in flight longer than --healthStallTimeout (30 s) with none finishing meanwhile. Never for memory or a database
GET /readythe broker servesthe store still loading; the current-state store not answering its ping; over the memory budget; stuck; stopping (from SIGTERM on)
anything elsealways-

Every answer has the same body, the report - kept current in the background, so a probe measures nothing:

  "memory": { "budget": 912680550, "used": 61435904, "resident": 75988992, "level": "ok", "refused": 0 },
  "requests": { "inFlight": 2, "total": 1288211, "lastFinishedAgoMs": 0 }

Member
statusstarting, ok, degraded (the history unreachable or not recording, or over 90 % of the memory budget), down (the store unreachable, or stuck), stopping
store, troemongoc and timescale are pinged once a second with a 1 s timeout: reachable is an answer within the last 5 s. corDB and none are in the process: reachable once loaded. troe.history (timescale): recording, notRecordingForMs, heldBytes, lostRows

/ready stays 200 while the TimescaleDB history is down: the broker still serves the current state, and every instance of a cluster writes to the one PostgreSQL - a 503 would take them all out at once.

Memory budget

In a container with a memory limit, a process over it is killed by the kernel - SIGKILL, exit 137, no warning - and with corDB in RAM everything it held goes with it. coraine keeps a budget below the limit and turns requests away before it gets there:

Memory usedWhat happens
below 90 % of the budgeteverything is served
90 % - 100 %writes that grow memory (POST, PUT, PATCH) are refused
over the budgeteverything is refused but what frees memory or reports: DELETE, batch delete, /version, /metrics, /admin/*
  • A refused request gets 503, Retry-After: 5, error type https://coraine.readthedocs.io/errors/MemoryBudgetExceeded.
  • The budget: --memoryLimit (MiB), or 85 % of the smallest cgroup memory limit the process lives under. No limit, no option: no budget, nothing checked.
  • Measured every 100 ms: RssAnon + RssShmem. File-backed pages - the executable, the libraries, corDB's memory-mapped log - are not counted.
  • Metrics: ngsild_memory_budget_bytes, ngsild_memory_used_bytes, ngsild_memory_resident_bytes, ngsild_requests_refused_memory_total.

Request size

The body is limited by --maxRequestSize (2 MiB; 413 above it). The line and headers must fit in --httpConnectionMemory (kB; 4 to 1024; libmicrohttpd only - the built-in server ignores it):

--httpConnectionMemoryheaders up toURL up to
87 kB6 kB
12 (the default)11 kB9 kB
1614 kB13 kB
32 (libmicrohttpd's own default)more than 20 kBmore than 18 kB

A request that does not fit is refused by the HTTP server before the broker sees it - 431 for its headers, 414 for its URL, with the server's short HTML body - and the log says so, at most once a second. A long query (hundreds of ids, a long q) fits in the body of POST /ngsi-ld/v1/entityOperations/query. A VCVerifier access token is 1.5-4 kB; 12 kB leaves room for one with every other header. The memory is cleared after every request: 12 kB instead of 32 kB is worth 2-3 % of a core on small requests.

Response size

--maxResponseSize is the byte budget of an entity query (GET /entities, POST /entityOperations/query, live or on a Snapshot), of the temporal queries and of what Context Sources answer to a forwarded query. The store counts each entity as it fetches it - mongoc its BSON length, corDB its JSON rendering - and stops before the one that would pass the budget, so a query's memory is bounded while it is fetched. Without the option it is 1/16 of the memory budget: 27 MiB in a 512 MiB pod, 108 MiB in a 2 GiB one.

CaseAnswer
the budget reached before limit200, a shorter page; Link rel="next" continues after it
the first entity alone larger than the budget403 TooManyResults
a query that needs every match at once (orderBy) and they are larger403 TooManyResults
one entity's history larger than the budget200 with the K instances per attribute that fit, and the temporal pagination Link

The end of a result set is the page without a rel="next" link - not a page shorter than limit.

Pagination

A query of more than limit entities is paged; its Link header points at the next page (rel="next") and, from the second on, the previous one (rel="prev") - each a complete request. A local query in the default order is paged by position (pageAfter / pageBefore, values the broker's links give, not for a client to build): a page deep in the result costs what the first costs, and an entity deleted on an earlier page moves nothing - none skipped, none repeated. A client's own offset pages as before; orderBy, georel=near, distributed queries, EntityMaps and Snapshots page by offset.

EntityMaps

An EntityMap freezes the set of entities a query matches (not their values) and serves the pages from it. A GET /ngsi-ld/v1/entities whose first page has more after it gets one unasked, as --autoEntityMaps says - by default a distributed query only, which without a map has no correct second page. ?entityMap=true asks for one. A map lives 5 minutes (an automatic one 5 more with each page); the maps together hold at most --entityMapMemory MiB, the expired and least recently used automatic ones giving way first.
