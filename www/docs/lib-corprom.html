corProm - Prometheus metrics

Counters, gauges and histograms for a server whose request path must not allocate, block or take a lock: an update is one atomic operation on a fixed-point int64_t (a histogram: one per bucket it falls in, and two more). Rendering happens only when the metrics are asked for - as the Prometheus text format, or as a corTree. Repository: SEAMWARE/corProm.

The three kinds

CorPromMetric* corPromCounterCreate(const char* name, const char* help);
CorPromMetric* corPromGaugeCreate(const char* name, const char* help);
CorPromMetric* corPromHistogramCreate(const char* name, const char* help, double* buckets, int bucketCount);
KindUpdated byKept as
countercorPromCounterInc(m), corPromCounterAdd(m, int64_t n)the value × 1000
gaugecorPromGaugeSet(m, double v), corPromGaugeAdd, corPromGaugeSubthe value × 1000, rounded to the nearest thousandth - a thousandth is the smallest step
histogramcorPromHistogramObserve(m, double v)a count per bucket, the number of observations, their sum in billionths (rounded) - 0.2 ms adds 200 000
  • A histogram's buckets are the upper bounds given, in ascending order; a +Inf bucket is added. They are cumulative, as Prometheus defines them: an observation counts in every bucket whose bound is at or above it. The array is copied.
  • An update of the wrong kind - corPromCounterInc on a gauge - or of NULL does nothing.
  • Every metric is global, in one list in the order created, kept for the life of the process: the name and help are copied, nothing is freed. corPromLookup(name) finds one by name. A metric has no labels.

Creating is thread-safe, a name is taken once. Any thread can create a metric at any time: creation takes a mutex, and a metric is linked into the list only once it is complete, so a render or a lookup running at the same time sees it whole or not at all. A name already created is refused - the create returns NULL (Prometheus refuses an exposition with a name twice), as it does when out of memory - and an update on that NULL does nothing. The updates themselves stay atomic and lock-free. coraine creates all of its metrics once, at start-up, and keeps the pointers.

Rendering

int corPromRenderSize(void);
int corPromRender(char* buf, int bufLen);

The Prometheus text exposition format - # HELP (when there is a help text), # TYPE, the value lines - for every metric, in the order created:

CorPromMetric* reqs = corPromCounterCreate("requests_total", "Requests served");
CorPromMetric* conn = corPromGaugeCreate("connections", "Open connections");
double         b[]  = { 0.001, 0.01, 0.1, 1 };
CorPromMetric* lat  = corPromHistogramCreate("latency_seconds", "Request latency", b, 4);

corPromCounterInc(reqs);  corPromCounterInc(reqs);  corPromCounterAdd(reqs, 5);
corPromGaugeAdd(conn, 3); corPromGaugeSub(conn, 0.5);
corPromHistogramObserve(lat, 0.004); corPromHistogramObserve(lat, 0.2); corPromHistogramObserve(lat, 7);

int   size = corPromRenderSize();
char* text = malloc(size + 1);
corPromRender(text, size + 1);
# HELP requests_total Requests served
# TYPE requests_total counter
requests_total 7
# HELP connections Open connections
# TYPE connections gauge
connections 2.5

# HELP latency_seconds Request latency
# TYPE latency_seconds histogram
latency_seconds_bucket{le="0.001"} 0
latency_seconds_bucket{le="0.01"} 1
latency_seconds_bucket{le="0.1"} 1
latency_seconds_bucket{le="1"} 2
latency_seconds_bucket{le="+Inf"} 3
latency_seconds_sum 7.204000000
latency_seconds_count 3

The buffer is corPromRenderSize() + 1, and so is bufLen. The size does not count the terminating zero, and corPromRender writes one. With a buffer of exactly the size, the last byte - the newline that ends the last metric - is lost, and the return value is the same as had it fitted. With a smaller one it returns the size it needed. It returns the bytes written, without the zero.

  • A counter and a gauge are written with their thousandths - a whole value without a fraction (7), else with up to three decimals, trailing zeros dropped: the gauge above is 2.5, a gauge of 1/3 0.333. A histogram's sum has 9 decimals, a bucket bound is %g.
  • Each value is read atomically, not all of them together: a render while observations are made may show a histogram whose buckets and count are a few observations apart. Rendering takes no lock. The size and the render are two passes, too - a metric created or a value grown in between can make the text longer, and corPromRender then returns the size it needed.

As a tree

CorNode* corPromMetrics(CorAlloc* kaP);

The same metrics as an array of objects, built in kaP (NULL: the tree heap, corTreeFree it) - each with name, type, help, and a value, or a histogram's buckets (le, count), sum and count. Here a counter's and a gauge's value is a float, with its thousandths:

[{"name":"requests_total","type":"counter","help":"Requests served","value":7},

  "buckets":[{"le":0.001,"count":0},{"le":0.01,"count":1},{"le":0.1,"count":1},{"le":1,"count":2},{"le":"+Inf","count":3}],
  "sum":7.204,"count":3}]

In coraine

The admin plugin serves the text format at GET /admin/metrics (Administration), text/plain; version=0.0.4: request counters per operation, 4xx and 5xx errors, notifications sent and failed, the cache sizes, the memory budget, SSE streams, distributed-operation forwards, the request latency and batch sizes as histograms. The gauges of tenants, caches, memory and SSE are counted and set just before each render. The declared indexes' series (ngsild_index_*) are written after corProm's text, by coraine itself: they carry labels, which corProm's metrics have not (Database indexes).
