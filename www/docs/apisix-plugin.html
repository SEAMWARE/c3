The NGSI-LD plugin for APISIX

ngsild-pep (corApisixNgsild) decides access to an NGSI-LD broker's API in the APISIX gateway: the access token checked and the ODRL policies decided as coraine's --auth fdsc decides them - by the same C code, fdsc.so's, compiled into a library the plugin calls once per request. Any NGSI-LD broker can sit behind it.

What it decides

For each request on a route that has the plugin, one call into the library makes the whole decision - the token (authenticate) and then the policies (authorize) - and the answer is one of four:

VerdictWhat the client gets
allowednothing from the plugin: the request goes on to the broker
401no token, or one that does not verify - with WWW-Authenticate
403a valid token, and no policy allows the request
503no keys or no policies yet, or the plugin could not start (the reason is in the detail)

A refusal is the broker's own answer, a ProblemDetails (type about:blank, title, status, detail), so a client sees the same body from the gateway as from coraine.

What the decision reads is what fdsc.so reads without --fdscNgsild: the method, the path, the query string, the Authorization header, the x-stripped-path header (only with --fdscStrippedPath) and the body (not for GET, HEAD, DELETE). Nothing is expanded: ngsi-ld:entityType is the type as the request carries it - the id's third : part, ?type=, the body's type. The token, the policy words and the combination rules are those of Authorization - --auth fdsc.

The same code as --auth fdsc

libngsildpep.so is fdsc.so compiled from coraine's sources (src/plugins/auth/fdsc/), unchanged, with two files of the plugin's own:

FileWhat it is
src/ngsildPep.cthe gateway adapter: ngsildPepInit (fdsc.so's options, as a list of strings) and ngsildPepDecide (one decision: an AuthRequest built from the gateway's request, then fdsc.so's authenticate and authorize)
src/fdscFetchFile.cfdsc.so's fetch, for files and mem:<name> only - nothing below the FFI line does network I/O, as a blocking call would stall every request of an nginx worker
lua/apisix/plugins/ngsild-pep.luathe plugin: reads the request, makes the one FFI call, lets the request through or answers; fetches the keys and policies over the network when told to

test/sameAsFdsc.sh sends coraine's test/fdscDiff cases (the connector's tokens, policy vocabulary and combination rules) to APISIX with ngsild-pep in front of a broker started without --auth, and to coraine with --auth fdsc - the same keys, the same policies - and compares the answers by class (401, 403, 503, let through): 64 cases, 0 differences - the cases, the fdsc.so sources and the broker of coraine 7239cf37 (2026-10-14), which the plugin's CI pins; coraine's main has more cases since. With --pap the keys come from a verifier's discovery document and the policies from an ODRL-PAP, fetched by the plugin and by coraine. The plugin's CI runs both, with one coraine commit for the library's fdsc.so sources, the cases and the broker (its image).

Building the library

The library has to match the gateway's system. build-in-docker.sh [<image>] builds it inside a container of that system - by default debian:12, the base of apache/apisix:3.17.0-debian - from the checkouts beside the repository (coraine and the Cor-Libs corJson, corTree, corAlloc, corLog, corBase, corArgs, corNgsild), read only: nothing of the clones' own build directories is touched.

git clone https://github.com/SEAMWARE/corApisixNgsild
for r in coraine corJson corTree corAlloc corLog corBase corArgs corNgsild; do
  git clone https://github.com/SEAMWARE/$r
done
cd corApisixNgsild
./build-in-docker.sh        # dist/debian-12/libngsildpep.so

On a machine that is the gateway's system, make builds it in place - the Cor-Libs built there in release (COR_LIBS: their parent directory, CORAINE: the coraine checkout). It needs OpenSSL's libcrypto. The Cor-Libs are linked in statically and their symbols hidden: the library exports only the plugin's four functions.

Installing it in APISIX

Three things go into the gateway: the plugin's Lua file, on APISIX's extra_lua_path; the library, and the keys and policies when they are files. With the APISIX image, as volumes:

services:
  apisix:
    image: apache/apisix:3.17.0-debian
    volumes:
      - ./config.yaml:/usr/local/apisix/conf/config.yaml:ro
      - ./corApisixNgsild/lua/apisix/plugins:/opts/custom_plugins/apisix/plugins:ro
      - ./ngsild:/opts/ngsild:ro          # libngsildpep.so, jwks.json, policies.json

APISIX runs as its own user in the container: the files must be readable by it.

Configuration

In config.yaml - one configuration per gateway:

apisix:
  extra_lua_path: "/opts/custom_plugins/?.lua"
plugins:
  - ngsild-pep
plugin_attr:
  ngsild-pep:
    lib: /opts/ngsild/libngsildpep.so
    log_level: WARN
    args: [ "--fdscJwks", "/opts/ngsild/jwks.json", "--fdscPolicies", "/opts/ngsild/policies.json",
            "--fdscIssuer", "http://verifier:3000", "--fdscOrganization", "did:web:provider" ]

and the plugin on a route - here every path, to a broker on port 1026:

routes:
  - uri: /*
    upstream:
      nodes:
        "broker:1026": 1
      type: roundrobin
    plugins:
      ngsild-pep: {}
MemberWhat it is
libthe library's path - required
argsfdsc.so's own options, as on coraine's command line (Authorization - Options) - required. A boolean option takes no value ("--fdscAnonymous"); an option fdsc.so does not have is refused
log_levelfdsc.so's own log lines, to the process's stdout (in a container, the container's log, beside nginx's): ERR, WARN (default), INFO, VERBOSE
fetchthe keys and the policies fetched by the plugin - below

The route's own configuration is empty: "ngsild-pep": {}. The plugin's priority is 2600, ahead of APISIX's openid-connect (2599) - it decides alone, and a route needs neither openid-connect nor opa.

A plugin that could not start answers 503 to every request - a wrong lib, a schema error in plugin_attr, an option fdsc.so refuses - with the reason in the response's detail and in the gateway's error log. Nothing is let through unchecked.

nginx writes a request body larger than its client_body_buffer_size to a temporary file, and the plugin then reads it from there - a cost on every such request. NGSI-LD batches are often larger than nginx's default; the plugin's test configuration sets client_body_buffer_size 1m (nginx_config.http_server_configuration_snippet).

Keys and policies from the network

The C side reads files only. To take the keys from the verifier and the policies from an ODRL-PAP, the plugin fetches them in Lua - with nginx's cosockets, which do not block - and hands them to fdsc.so by name, which reads them as mem:jwks and mem:policies:

plugin_attr:
  ngsild-pep:
    lib: /opts/ngsild/libngsildpep.so
    fetch:
      discovery: http://verifier:3000/services/data-service/.well-known/openid-configuration
      pap:       http://odrl-pap:8080
      interval:  30
    args: [ "--fdscJwks", "mem:jwks", "--fdscPolicies", "mem:policies", "--fdscIssuer", "http://verifier:3000",
            "--fdscOrganization", "did:web:provider", "--fdscRefresh", "2" ]
discoverythe verifier's OpenID discovery document: its jwks_uri is fetched for the keys. Or jwks: the JWK Set's URL itself
papthe PAP's base URL: every page of its /policy (?page=N&pageSize=100), as one array
intervalseconds between two fetches, in each worker - default 30; the first fetch is at start
--fdscRefreshhow often fdsc.so reads what was fetched

A fetch that fails keeps what is in use, and says so in the log. --fdscIssuer is required here: fdsc.so reads no discovery document of its own in the gateway. In args, a source is a file or mem:<name> - a URL (--fdscJwks http://..., and so --fdscDiscovery and --fdscPap) is an error, as the library does no network I/O.

What stays in the broker

--fdscNgsild is refused at start: the plugin answers 503 to every request, and the log says why. With it, fdsc.so decides on each entity a request reads or writes - its stored, expanded types, its attributes, its tenant, entity by entity in a batch or a query - which the broker has and a gateway does not. That is coraine's --auth fdsc --fdscNgsild, in the broker (Authorization - --fdscNgsild).
