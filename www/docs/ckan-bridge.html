The CKAN bridge

ckan.so, loaded with --bridges ckan, reads the DataStore resources of a CKAN portal - the open-data portal software behind many city and government data sites - and hands each row to the broker, where a DataChannel makes it into entities.

CKAN portal  --datastore_search-->  ckan.so  --(resource id, row, time)-->  broker  --DataChannel-->  entities

The bridge knows nothing about entities: it carries (endpoint, json, time) - the resource id, one row as a JSON object, the row's time. Which entities a row becomes - which column is the id, which are Properties, which two make a location, which one names another entity - is the DataChannel's mapping, in the broker.

Rows into entities: DataChannels

A Channel ties one endpoint to one attribute of one entity. A DataChannel ties one endpoint to the entities its records make: each record (a row - one JSON object, one member per column) becomes one or more entities, the id taken from a column. It names no entity and claims no attribute, and has its own listing, GET /ngsi-ld/v1/dataChannels (and /{id}, the id urn:ngsi-ld:DataChannel:ckan:<resource id>). DataChannels are the broker's feature COR_FEATURE_DATA_CHANNELS; without it, a dataChannels section is warned about and ignored and GET /dataChannels answers 501.

The CKAN bridge carries DataChannels only: a resource is read, and nothing is written to the portal. A channel handed over as a service or an action, or with any direction but inbound, is refused (BRIDGE_UNSUPPORTED) and stays dormant with the bridge's reason.

An example: Boston's bike stations

data.boston.gov publishes its Blue Bike stations as a DataStore resource (licence ODC PDDL). This file makes each row a BikeStation, with a Relationship to a District made from the same row:

{ "ckan": {
    "server": { "url": "https://data.boston.gov", "timeoutMs": 30000 },
    "ngsild": {
      "defaultEntity": false,
      "dataChannels": {
        "44c931aa-4577-4caa-a8f2-ed1e38263e70": {
          "channelInfo": [ { "key": "mode",     "value": "once" },
                           { "key": "pageSize", "value": "100"  } ],
          "entities": [
            { "type": "BikeStation", "id": "urn:ngsi-ld:BikeStation:{Number}",
              "attributes": {
                "name":       { "column": "Name" },
                "totalDocks": { "column": "Total_docks", "as": "number" },
                "public":     { "column": "Public_", "as": "boolean" },
                "location":   { "point": { "longitude": "Longitude", "latitude": "Latitude" } },
                "inDistrict": { "relationship": "urn:ngsi-ld:District:{District}" } } },
            { "type": "District", "id": "urn:ngsi-ld:District:{District}",
              "attributes": { "name": { "column": "District" } } } ] } } } } }
coraine --database corDB --bridges ckan --bridgeConfig bridges.json
curl 'http://localhost:1026/ngsi-ld/v1/entities?type=BikeStation&limit=1'
curl http://localhost:1026/ngsi-ld/v1/dataChannels

Read on 2026-10-09, the resource had 572 rows: 572 BikeStations and 13 Districts.

Mode once

When the broker has started and handed the bridge its DataChannels, each resource is read whole, on the bridge's own reader thread, in the order the DataChannels were added: page after page of /api/3/action/datastore_search?resource_id=<id>&limit=<pageSize>&offset=<n>&sort=_id, every row handed to the broker, until a page comes back shorter than pageSize or the offset reaches the answer's total. The resource is then done. A restart reads it again; the broker's write is an upsert, so the same rows leave the same entities. A row deleted at the source leaves its entities in the broker.

HTTP(S)the broker's own client (corRest, resolved from the running broker) - nothing is linked into the plugin
The portal at startnot contacted before the broker is up: a portal that is down does not keep the broker from starting
Failuresa portal that cannot be reached, a timeout or a 5xx is tried again after 1 s, then after 3 s; a 4xx is the answer. A resource that cannot be read leaves its DataChannel dormant, with the portal's reason as its statusReason - the portal answered 404 - Not Found Error: Not found: Resource "..." was not found.
The API keysent as the Authorization header, and nowhere else - not in a log line, not on GET /ngsi-ld/v1/dataChannels

poll (follow the dataset's activity stream, then read the new rows) and push (a webhook) are reserved mode names; a DataChannel naming one is refused with mode 'poll' is not built yet - 'once' is. Both are on the roadmap.

Configuration

One --bridgeConfig file serves every bridge, one member per alias. server is this plugin's; the ngsild section is the broker's, and its dataChannels make the DataChannels, one per resource.

server - the portal

MemberWhat it is
urlmandatory: the portal, https://... or http://...
apiKeya CKAN API token, sent as Authorization - for a private resource
apiKeyEnvthe name of an environment variable holding the token, instead of apiKey - one or the other, not both
timeoutMsone HTTP request, 100-600000, default 30000

A missing or wrong url, both key members, or a timeoutMs out of range fails the bridge's init, and the broker does not start. Another member is warned about and ignored.

channelInfo - how to read one resource

KeyWhat it is
modeonce - the default and the one built
pageSizerows per datastore_search call, 1-32000, default 100
timeColumnthe column holding each row's time, ISO 8601: 2026-10-09T12:00:00Z, 2026-10-09T12:00:00.250+02:00, 2026-10-09 12:00:00 (no zone: UTC), 2026-10-09 (midnight UTC)

The row's time becomes observedAt on every attribute the row writes. Without a timeColumn, or for a row whose value there is not a date-time, the row has no time and its attributes no observedAt (a value that is not a date-time is warned about once per read). An API key in channelInfo (apiKey, Authorization) is refused - channelInfo is shown on GET /ngsi-ld/v1/dataChannels - and so is any other key; the DataChannel is then dormant and says why.

dataChannels - the mapping

The member's name is the endpoint: the resource id, a UUID or a DataStore alias (letters, digits, ., _, -). entities lists what each row makes. The mapping is the broker's, the same for every bridge that carries DataChannels:

ida template: {Column} is the column's value. A row with no value in a column the id names makes no entity of that kind; the others it names are still made.
idEncodinghow a value goes into an id or a Relationship's object: merge (the default - each character outside [A-Za-z0-9._-] becomes _, South Boston → South_Boston, so values that differ only there name one entity) or percent (each such byte becomes %XX, South%20Boston: two values never name one entity)
{ "column": ... }a Property; "as" converts the value: number, integer, float, boolean (yes/true/y/1, no/false/n/0), string, datetime, json; "unitCode" beside it
{ "point": { "longitude", "latitude" } }a GeoProperty Point from two columns; { "geo": ... } one from a single column
{ "relationship": <template> }a Relationship
{ "value": <JSON> }a Property whose value is always that

An absent, null or empty column, or a value that does not convert, leaves that attribute out. All the entities of one row are written as one batch upsert with options=update: created when they are not there, their mapped attributes replaced, other attributes left alone - with the checks, notifications and temporal events of POST /entityOperations/upsert. A row that makes no entity is not taken (recordsRefused), and the read goes on. The full mapping - scope, otherColumns, the other attribute kinds - is in coraine's DataChannels.

What a DataChannel shows

GET /ngsi-ld/v1/dataChannels lists each one with its bridge, its endpoint, its channelInfo, the mapping as the file wrote it (recordEntities), status and statusReason, and the counters recordsIn (rows that wrote an entity), recordsRefused and entitiesWritten. The reason a resource is not read reaches statusReason through channelStatusIn (bridge ABI 12, the broker's COR_FEATURE_CHANNEL_STATUS_IN); with a broker or headers without it, only the log says why.

Building

The bridge is its own repository, corCkanBridge, built as every bridge from the template is. It needs no library of its own: -lpthread, and the Cor-Libs and corRest from the broker that loads it.

make                  # ckan.so, debug (traces compiled in)
make BUILD=release
make contract         # does src/ckanRegister.c still satisfy BridgeDriver.h?
make install          # to /opt/seamware/plugins/bridge (PLUGIN_DIR=...)

The corLibs umbrella clones it and does not build it; coraine-build --bridges ckan does. It needs a broker with DataChannels.

make test runs without the internet: test/funcTests/tools/ckanMock.py is the portal (port 19027), answering from test/funcTests/fixtures/ - three recorded pages of the bike stations (rows 1-50), the portal's answer for a resource it does not have, and edge-cases.json, written for the tests. The broker runs on port 19026 with ramDB; CKAN_BROKER, CKAN_PORT, CKAN_MOCK_PORT and CKAN_TEST_DIR override (as the template's).
