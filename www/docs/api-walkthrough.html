API walkthrough

An entity created, read, queried, changed, watched and deleted - six requests, on a broker that needs no other service.

coraine --database corDB --troe none --apiPlugins admin -pp 2

corDB keeps the entities in the broker's own memory, --troe none keeps no history, -pp 2 indents the JSON it answers with. The examples use port 1026 and curl; the API is under /ngsi-ld/v1.

1Create an entity

curl -X POST http://localhost:1026/ngsi-ld/v1/entities \
  -H 'Content-Type: application/json' \
  -d '{
        "id":       "urn:ngsi-ld:Vehicle:A100",
        "type":     "Vehicle",
        "brand":    { "type": "Property",     "value": "Mercedes" },
        "speed":    { "type": "Property",     "value": 80, "observedAt": "2026-08-20T10:00:00Z" },
        "isParked": { "type": "Relationship", "object": "urn:ngsi-ld:OffStreetParking:P1" }
      }'

201 Created, and a Location header naming the entity. With a Content-Type of application/json the @context is the one in the Link header - without one, the NGSI-LD core context.

2Retrieve it

curl http://localhost:1026/ngsi-ld/v1/entities/urn:ngsi-ld:Vehicle:A100

Three representations, chosen with ?format=:

formatAn attribute is
normalized (the default)its full object - { "type": "Property", "value": 80, "observedAt": ... }
concisethe same, without what can be inferred - "speed": 80 when nothing else is there
keyValuesits value only

3Query

# by type
curl 'http://localhost:1026/ngsi-ld/v1/entities?type=Vehicle'

# by the values of an attribute (q, § 4.9)
curl 'http://localhost:1026/ngsi-ld/v1/entities?type=Vehicle&q=speed>50'

# some of the attributes, and how many entities there are in all
curl 'http://localhost:1026/ngsi-ld/v1/entities?type=Vehicle&attrs=speed&count=true'

count=true puts the total in the NGSILD-Results-Count header of the response. A page is limit and offset; the Link headers point to the next and the previous one. A q on an attribute the deployment queries often wants an index - Database indexes.

4Update

# attributes added, or overwritten
curl -X POST http://localhost:1026/ngsi-ld/v1/entities/urn:ngsi-ld:Vehicle:A100/attrs \
  -H 'Content-Type: application/json' \
  -d '{ "colour": { "type": "Property", "value": "black" } }'

# the entity merge-patched (§ 5.6.16)
curl -X PATCH http://localhost:1026/ngsi-ld/v1/entities/urn:ngsi-ld:Vehicle:A100 \
  -H 'Content-Type: application/json' \
  -d '{ "speed": { "type": "Property", "value": 95 } }'

# one attribute
curl -X PATCH http://localhost:1026/ngsi-ld/v1/entities/urn:ngsi-ld:Vehicle:A100/attrs/speed \
  -H 'Content-Type: application/json' \
  -d '{ "type": "Property", "value": 100 }'

5Subscribe

A subscription asks for a notification each time a matching entity changes:

curl -X POST http://localhost:1026/ngsi-ld/v1/subscriptions \
  -H 'Content-Type: application/json' \
  -d '{
        "id":   "urn:ngsi-ld:Subscription:S1",
        "type": "Subscription",
        "entities": [ { "type": "Vehicle" } ],
        "watchedAttributes": [ "speed" ],
        "q": "speed>90",
        "notification": {
          "attributes": [ "speed", "brand" ],
          "format": "keyValues",
          "endpoint": { "uri": "http://localhost:9977/notify", "accept": "application/json" }
        }
      }'

Anything with an HTTP endpoint receives them. An MQTT endpoint (mqtt://host:port/topic, mqtts://...) works the same way with the MQTT bridge loaded - --bridges mqtt; without it such a subscription is refused. The subscription itself is read, patched and deleted at /ngsi-ld/v1/subscriptions/{id}.

6Delete

curl -X DELETE http://localhost:1026/ngsi-ld/v1/entities/urn:ngsi-ld:Vehicle:A100

Further

  • Distributed operations - another broker or Context Source registered as the source of some entities, and the broker forwards to it: --distributed, and /ngsi-ld/v1/csourceRegistrations (the Registry API works without the option).
  • The history - with a temporal plugin (--troe corDB inside the corDB store, --troe timescale in PostgreSQL) every attribute's history is queried under /ngsi-ld/v1/temporal/entities.
  • The whole API - coraine implements ETSI GS CIM 009 v1.9.1; the specification is the reference.

The history is written after the response. A temporal write is history, not state the caller waits for, so a request does not pay for it - and a 201 does not mean the history row can be read yet: an entity created and its temporal representation read at once may not show it. --troeSync gives read-your-writes: the history is handed over before the response (handed over, not committed - nothing waits for the database), and a temporal read waits for what was handed over before it. Writes pay 1-6 % for it.
