Kubernetes

What a coraine deployment on Kubernetes needs - the image, the memory settings, the probes, the stop and the metrics - and two manifests: mongoc as a Deployment, a persistent corDB as a StatefulSet.

The image

quay.io/seamware/coraine:<tag> - one immutable tag per merge to main: 0.5.0 for a release, 0.5.0-<date>-<commit> for a merge. There is no latest tag: name the tag you tested.

  • Multi-arch - linux/amd64 and linux/arm64 under the same tag; <tag>-amd64 and <tag>-arm64 pin one. The arm64 image is built without the DDS bridge.
  • The entry point runs coraine -fg with the container's arguments appended. args: in a manifest replaces the default arguments, --database mongoc --troe none --apiPlugins admin.
  • Every option is also an environment variable: CORAINE_ + the long option in upper case - --healthPort is CORAINE_HEALTHPORT.

Memory

SettingWhy
requests.memory = limits.memorywith CPU set the same way, the pod is in the Guaranteed QoS class - the last evicted when the node runs short of memory
no --memoryLimitthe broker reads the container's limit from its cgroup (memory.max) and sets its memory budget to 85 % of it
--memoryLimit <MiB>CORAINE_MEMORYLIMITa budget of its own, when 85 % is not the margin wanted. Above the container's limit the broker logs a warning: the kernel kills first
MALLOC_ARENA_MAX=2glibc's per-thread arenas keep freed memory resident. With corDB and libmicrohttpd (2026-10-01), 10 000 entities took 67 MiB instead of 89, 100 000 took 335 MiB instead of 376. Its cost in throughput with many threads is not measured, so it is not the image's default

Over the budget the broker refuses requests (503 and Retry-After) instead of growing until the kernel kills it: over 90 % of it writes, over all of it everything but deletes and monitoring. A kill with corDB takes the store's RAM with it, and a persistent store is then loaded again. What counts is the broker's anonymous and shared memory - not the corDB log, which is memory-mapped page cache the kernel reclaims.

The memory is sampled every 100 ms. Between two samples one query is held by a byte budget of its own: what it fetches - current state, temporal history, the answers of the Context Sources of a distributed query - stops at --maxResponseSize, by default 1/16 of the memory budget.

Sizing with corDB: about 3.5 KiB resident per entity of five attributes - 100 000 entities are about 355 MiB, a million about 3.5 GiB. With mongoc the entities are in MongoDB.

With a CPU limit, the broker's HTTP event loops and its worker pool follow the CPUs the container may use - its CPU affinity and its cgroup quota - not the node's core count.

Probes

Start the broker with --healthPort <port> and point the probes at that port:

livenessProbe:
  httpGet: { path: /live, port: health }
  periodSeconds: 10
  timeoutSeconds: 2
  failureThreshold: 3
readinessProbe:
  httpGet: { path: /ready, port: health }
  periodSeconds: 5
  timeoutSeconds: 2
  failureThreshold: 2

Not on 1026. A probe on the API port waits in the same queue as the requests, behind them. Under load it times out, the liveness probe fails, and Kubernetes restarts a broker that was only busy - in the middle of the load. The health port is a thread of its own, outside the HTTP server, answering from figures kept current in the background: nothing it answers waits for a request or a database.

Answers 503
/liveonly when a request has been in flight longer than --healthStallTimeout seconds (default 30) and no request finished in that time - the broker is stuck. Never for memory or a database: a restart cures neither, and empties the caches, drops every connection and, with corDB, loads the whole store again
/readywhile the store loads at start-up; while the current-state store does not answer its ping; over the hard memory budget; while stuck; from SIGTERM on. Kubernetes takes the pod out of the Service's endpoints until it passes
  • A PostgreSQL that does not answer leaves /ready at 200. Every pod shares the one temporal store, and a 503 for it would take all of them out at once: the broker serves the current state and its subscriptions, and holds the history, then loses it.
  • No startupProbe is needed. The health port opens before the store loads: /live answers 200 through a long load of a persistent corDB, and /ready turns 200 when it is done.
  • A tcpSocket probe on the health port works too, and tells only that the port is open.
  • Without --healthPort nothing listens; the image's Docker HEALTHCHECK asks GET /version on 1026, which is exempt from the memory budget.

Stopping

On SIGTERM the broker answers /ready with 503, stops taking requests, lets those in flight finish, and closes the store. A persistent corDB (--dbDir) then syncs every tenant's log - from then on every acknowledged write is on the disk - and writes a snapshot per tenant.

The snapshot only makes the next start faster: it loads instead of the log replay. A broker killed during its snapshots (terminationGracePeriodSeconds over, then SIGKILL) has lost nothing; it replays the log at its next start. Give it a grace period long enough for the snapshot of the store it holds when the start time matters.

Metrics

GET /metrics on 1026, in the Prometheus text format, served by the admin API plugin - without --apiPlugins admin it answers 404. It is exempt from the memory budget.

metadata:
  annotations:
    prometheus.io/scrape: "true"
    prometheus.io/port:   "1026"
    prometheus.io/path:   /metrics

Or, with the Prometheus Operator, a ServiceMonitor on the Service's api port and path /metrics. The memory budget is there as ngsild_memory_budget_bytes, ngsild_memory_used_bytes, ngsild_memory_resident_bytes and ngsild_requests_refused_memory_total.

mongoc - a Deployment

The store is MongoDB, outside the pod; the broker keeps no state of its own that a restart loses.

More than one replica needs --high-availability mongo and a MongoDB replica set: it keeps the instances' caches of subscriptions, registrations and @contexts in step. Without it, a subscription created through one instance is unknown to the others - High availability.

apiVersion: v1
kind: Secret
metadata:
  name: coraine-mongo
stringData:
  uri: "mongodb://coraine:CHANGE-ME@mongo-0.mongo,mongo-1.mongo,mongo-2.mongo/?replicaSet=rs0&authSource=admin"
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: coraine
spec:
  replicas: 1                       # more than one: --high-availability mongo
  selector:
    matchLabels: { app: coraine }
  template:
    metadata:
      labels: { app: coraine }
    spec:
      containers:
        - name: coraine
          image: quay.io/seamware/coraine:0.5.0
          args:
            - --database
            - mongoc
            - --dbURI
            - $(MONGO_URI)
            - --troe
            - none
            - --apiPlugins
            - admin
            - --healthPort
            - "8081"
          env:
            - name: MONGO_URI
              valueFrom:
                secretKeyRef: { name: coraine-mongo, key: uri }
            - name: MALLOC_ARENA_MAX
              value: "2"
          ports:
            - { name: api,    containerPort: 1026 }
            - { name: health, containerPort: 8081 }
          resources:
            requests: { cpu: "2", memory: 1Gi }
            limits:   { cpu: "2", memory: 1Gi }
          livenessProbe:
            httpGet: { path: /live, port: health }
            periodSeconds: 10
            timeoutSeconds: 2
            failureThreshold: 3
          readinessProbe:
            httpGet: { path: /ready, port: health }
            periodSeconds: 5
            timeoutSeconds: 2
            failureThreshold: 2
---
apiVersion: v1
kind: Service
metadata:
  name: coraine
spec:
  selector: { app: coraine }
  ports:
    - { name: api, port: 1026, targetPort: api }

The health port is not in the Service: the kubelet probes the pod directly.

corDB on disk - a StatefulSet

The store is in the broker's process, kept on a volume with --dbDir. One replica - a second would be a second, separate store. The volume is ReadWriteOnce: one node, one broker.

apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: coraine
spec:
  serviceName: coraine
  replicas: 1                       # the store is the process's: never more than one
  selector:
    matchLabels: { app: coraine }
  template:
    metadata:
      labels: { app: coraine }
    spec:
      terminationGracePeriodSeconds: 120
      containers:
        - name: coraine
          image: quay.io/seamware/coraine:0.5.0
          args:
            - --database
            - corDB
            - --dbDir
            - /data
            - --troe
            - none
            - --apiPlugins
            - admin
            - --healthPort
            - "8081"
          env:
            - name: MALLOC_ARENA_MAX
              value: "2"
          ports:
            - { name: api,    containerPort: 1026 }
            - { name: health, containerPort: 8081 }
          resources:
            requests: { cpu: "2", memory: 4Gi }
            limits:   { cpu: "2", memory: 4Gi }
          livenessProbe:
            httpGet: { path: /live, port: health }
            periodSeconds: 10
            timeoutSeconds: 2
            failureThreshold: 3
          readinessProbe:
            httpGet: { path: /ready, port: health }
            periodSeconds: 5
            timeoutSeconds: 2
            failureThreshold: 2
          volumeMounts:
            - { name: data, mountPath: /data }
  volumeClaimTemplates:
    - metadata:
        name: data
      spec:
        accessModes: [ ReadWriteOnce ]
        resources:
          requests: { storage: 20Gi }
---
apiVersion: v1
kind: Service
metadata:
  name: coraine
spec:
  selector: { app: coraine }
  ports:
    - { name: api, port: 1026, targetPort: api }

The disk holds the log segments (up to 1 GiB each, 64 MiB with --dbCompress) and the snapshots; 100 000 entities of four attributes are 38 MB as a log or as a snapshot. With --troe corDB the temporal history is on the same volume. The other corDB options - --dbSync, --dbSnapshotEvery, --dbCompress - are in Installation.

Importing a database first? A one-off Job on the same volume, with the StatefulSet at zero replicas - Migrating a database to coraine.
