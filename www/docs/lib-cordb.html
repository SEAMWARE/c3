corDB - the in-process store

corDB keeps a broker's entities, subscriptions and registrations in the broker's own memory - one tree per tenant, no database server - as a database plugin, corDB.so. With --dbDir it is durable (an append log and snapshots), and with --troe corDB the same store keeps the temporal history.

The plugins

One library, three shared objects, all built by its makefile:

PluginSelected withWhat it is
db/currentState/corDB.so--database corDBthe current-state store, in RAM or on disk; its own troeRegister is --troe corDB
db/currentState/ramDB.so--database ramDBthe same sources built with COR_DB_RAM_ONLY=1: no disk, so --dbDir and the other disk options are unknown options, and --troe corDB is refused. Its options: --dbLockPrefer, --dbValueIndexes
troe/temporal/ramDB.so--troe ramDBa ring of the broker's last 256 TRoE events in RAM, shown by /admin/troe/dump - for tests
coraine --database corDB                                  # in RAM: a restart starts empty
coraine --database corDB --dbDir /var/lib/coraine         # durable
coraine --database corDB --dbDir /var/lib/coraine --troe corDB   # durable, with history

A plugin is loaded as every DB plugin is (Plugin architecture): the broker checks the interface stamp, then calls dbRegister, which fills the DbDriver with corDB's functions - entities and batches, subscriptions, registrations, the document store, NGSI-LD Snapshots, the hosted @contexts, the declared indexes, tenant drop and release, and the geo-match callbacks. A slot left NULL is an operation the plugin does not have; a build without subscriptions or registrations (COR_FEATURE_SUBSCRIPTIONS=0, COR_FEATURE_REGISTRATIONS=0) leaves those slots NULL.

The store

A tenant's data is one CorDbStore (corDbStore.h), made on the tenant's first use and hung on Tenant.pluginData. Its tree is an object of three arrays:

{ "entities": [ ... ], "subscriptions": [ ... ], "registrations": [ ... ] }
  • Entities in creation order. The store's list is the default order of a query. A replace keeps the entity's place and its createdAt; a delete and a create put it at the end. A replayed log keeps the order: a put of an entity that exists replaces it in place.
  • One time per created entity. The store keeps the entity's createdAt, and below it only the times that differ - an attribute that was modified has its own modifiedAt, an added one its own createdAt and modifiedAt. A missing time is the entity's createdAt, put back on every copy that leaves the store (corDbSysTimes.h). Outside corDB every object has every time.
  • An attribute's type in the node. The "type" member of an attribute instance or sub-attribute is folded into the node (CorNode.kind) on the way in and given back, first, on every copy out - one node less per instance.
  • Copies out. A retrieve or a query clones what it returns under the read lock, into the request's allocator; the caller never holds a pointer into the store.

The built-in indexes

IndexWhat it is
entity ida hash table from the id to the entity's predecessor in the list (the array for the first), so a lookup and an unlink are O(1) (corDbIndex.h). Past 4 entities per slot it grows to a table eight times larger, moving 32 old slots at every link, unlink and replace - no write moves them all; a lookup tries the new table, then the old.
typeevery type's entities, in the store's order (corDbTypeIndex.h). A query by one type, or by one AND group of types ((A;B) - the member with the shortest list), walks that list; a query with no type or with types in OR walks the store. Built by the first query that can use it, under the read lock; not on disk. 48 bytes for each type of each entity. make COR_FEATURE_TYPE_INDEX=0 leaves it out.
declared value indexesbelow, Declared indexes

A debug build checks every indexed query against a walk of the whole store and aborts on a difference. Out of memory, an index is dropped and queries walk the store.

Locking

A tenant's store has one pthread_rwlock_t. Readers share it; a writer has it alone - CorNode is linked lists, and two writers relinking at once corrupt them. A request is on exactly one tenant, so no request takes two locks.

A function takes the lock for the rest of its scope with one line - COR_DB_READ(tenantP) or COR_DB_WRITE(tenantP) - and the compiler's cleanup attribute releases it on every return. The lock is not recursive: an entry point that is also called from inside a locked function is split into a locking shell and an unlocked ...Locked body. Work that needs no lock is done outside it - here, a delete frees the entity after the lock (corDbEntityDelete.c):

int corDbEntityDelete(Tenant* tenantP, const char* entityId)
{
  CorNode* goneP = NULL;

  {
    COR_DB_WRITE(tenantP);                           // released at the closing brace

    CorDbStore* storeP = corDbStoreOf(tenantP);
    CorNode*    eP     = corDbIndexLookup(storeP, entityId);

    if (eP != NULL)
    {
      corDbIndexUnlink(storeP, eP);
      corDbPersistAppendId(corDbLockedStore->persistP, CorDbLogEntityDelete, entityId);   // lock order is log order
      goneP = eP;
    }
  }

  if (goneP == NULL)
    return DB_NOT_FOUND;

  corTreeFree(goneP);                                // a whole entity's free()s, with no writer waiting
  return DB_OK;
}

Shortened from the source: the real function also prepares the entity's history record before the lock and walks the store for a store without its id index.

Option
--dbLockPreferreads | writeswhom the lock lets in first when readers and writers both wait. reads (the default) is glibc's read-write lock as it is; writes makes it writer-preferring (PTHREAD_RWLOCK_PREFER_WRITER_NONRECURSIVE_NP) - safe, as corDB never takes a store's read lock twice in one thread. Also a ramDB option.

Persistence - --dbDir

Without --dbDir the store is RAM only. With it, every write appends its effect to a log, under the write lock, before the response:

A record is an effect

A record says what the write did to the tree, never the request that did it: a replay applies "these attributes now are exactly this", with no NGSI-LD semantics, so two releases rebuild the same store from one log.

RecordBodyWritten by
ENTITY_PUTthe whole entitycreate, replace, attribute delete, batch create / update / upsert (one record per entity)
ATTRS_PUT{ "id", "attrs": { ... }, "deleted": [ ... ] } - each member the write named, whole, after it, and those it removedPATCH, merge, attribute append and update, batch merge - a one-attribute PATCH logs one attribute, not the entity
ENTITY_DELETEthe iddelete, batch delete
SUB_PUT / SUB_DELETE, REG_PUT / REG_DELETEthe subscription or registration / its idtheir writes

A record is a 28-byte header - magic and version, the body's length, a sequence number per tenant, the system time in nanoseconds, a CRC-32C - and a body in the cor binary format, the codec of cor://. Every record decodes on its own. A batch is not atomic in NGSI-LD, and is logged as one record per entity. The body of a record whose entity exists before the lock is encoded, and its CRC taken, before the lock; under it only the header is finished and the body copied.

The files

/var/lib/coraine/
├── _storageFormat          # the storage format, a number as text
├── _/                      # the default tenant
│   ├── snap-000041.cor     # the store as of sequence 41
│   ├── log-000041.cor      # every record since snapshot 41
│   └── hist-000001.cor     # with --troe corDB: the history
└── tenant1/
  • The open segment is mapped (mmap, MAP_SHARED, 1.25 GiB of address space) and the file allocated ahead of its records 4 MiB at a time with posix_fallocate - so a full disk is an error at the allocation, not a SIGBUS on a page of a sparse file. A segment rolls at 1 GiB (64 MiB with --dbCompress); a finished one is cut to its records.
  • A snapshot is taken on a thread of its own once a tenant has written --dbSnapshotEvery MiB of log and at least as much log as its last snapshot was big, and at a clean stop. It switches the log to a new segment under the write lock, then encodes the store in slices of 1000 entities, each under the read lock; between two slices it waits while writers wait, for at most three times as long as the slice took. Written as snap-N.tmp, synced, renamed; the files before it are then deleted. The snapshot is not the store at one instant: the log after it replays every write made while it was taken.
  • The storage format. _storageFormat is read before anything else under --dbDir. A lower format is brought up to this build's; a higher one - a store written by a newer release - stops the start and is left as it is.

Recovery

  1. The newest snap-N.cor (a .tmp is an interrupted snapshot, deleted). A snapshot that does not decode in full stops the broker.
  2. log-N.cor and every segment after it, record by record, until a record that is short or fails its CRC. Zeros from there on: the space allocated ahead, the end. Anything else is a torn tail - in the newest segment it is cut and writing continues there; anywhere else it stops the broker. A sequence that does not follow the last one is a gap (pages written out of order before a machine died): the log ends before it, and a later segment is renamed <segment>.torn - kept, not replayed.
  3. With --troe corDB, the hist-N.cor segments, in order.
  4. The indexes, rebuilt from the tree.

What a stop, a crash and a power cut lose

EventLost
a clean stop (SIGTERM, SIGINT)nothing: requests finish, every segment is synced and cut, every tenant snapshotted
kill -9, a crash, an OOM killnothing acknowledged: the record was in the page cache before the response
the machine dies--dbSync interval: at most the last --dbSyncInterval; --dbSync request: nothing acknowledged; --dbSync none: whatever was not written back

With --dbSync request a write's response waits for its record's fdatasync, after the write lock is released; the writers that arrive during one sync share the next (group commit).

A log that cannot be written - the pause

With any --dbSync, a log that cannot be written pauses the store: a segment that cannot be allocated ahead (a full disk, a file-size limit), a record that cannot be put in the log, a failed fdatasync. The pause is broker-wide and every write function checks it first, one atomic load (corDbStoreWriteRefused). The driver's paused function tells the broker, which refuses every write before it is parsed - 503 PersistenceUnavailable, Retry-After: 5, detail writes are refused until the broker can write its log again (paused for <N> s): <why> - answers /ready with 503 and counts the refusals (Administration). A write that passed the broker's check and reaches the store as the pause begins is refused by the store, with the same answer. Reads are served.

  • The reserve. The flusher keeps 8 MiB of the open segment allocated ahead of its records, off the write path - a segment that would pass its roll size with it rolls early - so a full disk pauses the store before a write needs the room, unless more than 8 MiB is written between two of its runs.
  • A write already applied when the log failed is answered 503 too: its record not in the log, or a failed sync - every write after it, as a load stops at the first record it cannot read, and with --dbSync request the writes the sync was for. The answer is raised as the write lock is released, after the operation has returned, as corRest's late problem (corRestProblemLate), which replaces the operation's answer.
  • The repair. The snapshotter writes a snapshot of each tenant whose log failed, from memory, once a second backing off to once every 16 s; a snapshot rolls the log and drops the files before it. When it has succeeded for every such tenant the pause ends, and the writes answered 503 after they were applied are in that snapshot. --dbSync request waiters whose sync failed wait up to 10 s for it.
  • The history's repair (--troe corDB). The history is not in a snapshot: a tenant whose history log lost a record or a sync has its history written anew from memory - every entity's instances and lifecycle events, as new segments after the open one, their records numbered from 1 again. Each is synced and renamed from .tmp, the last first, the directory synced, and only then the older segments deleted; the appends go on in the last new segment. While it is written the tenant's history mutex is held: no history is drained, and temporal reads and writes wait. The pause ends when the repair is done for every such tenant. Recovery takes a history segment whose first record is number 1, after others, as the start of the history and deletes the ones before it; a death before the first new segment was renamed leaves the new ones after a gap, set aside as .torn - the history is then the old segments.

--dbCompress

Snapshots and finished log and history segments are compressed with zstd, level 3, in frames of at most 64 MiB, on the snapshot thread - never the open segment. A file's first four bytes tell a compressed one from a plain one, so a start reads a store with the option or without it, and a start with it compresses the finished segments a run without it left. libzstd (libzstd.so.1) is loaded with dlopen only then, never linked; missing, the start is refused. A compressed file that does not decode to its end is damage, not a torn tail.

The history - --troe corDB

--troe corDB is corDB.so's own troeRegister - the same store, the same lock, the same directory - so it needs --database corDB. The history is captured where current state changes, at corDB's write sites, not from the broker's TRoE events: current state overwrites, history appends.

  • Every write that reaches an attribute appends an instance: create, replace, merge, PATCH, the batches. A PATCH with an unchanged value appends one too - it changes modifiedAt. A replace records only what it wrote.
  • A deleted attribute instance appends a tombstone (the value urn:ngsi-ld:null and deletedAt); the Scope is recorded as a Property; entity events - created, replaced, deleted - are records of their own, and a deleted entity's history stays.
  • Under the write lock a write only queues its history; whoever releases the lock drains the queue under the tenant's history mutex - the index in RAM and hist-N.cor - before the response. A temporal read drains first.
  • In RAM: entity id, attribute, instances in the order written - each its encoded record and the four times a filter reads without decoding it, in a per-tenant arena of 1 MiB chunks. On disk with --dbDir; snapshots never remove history segments.

The temporal API reads it - GET /temporal/entities/{id}, GET /temporal/entities, POST /temporal/entityOperations/query, with timeproperty, timerel, lastN / firstN / offsetN, q and the geo-query - and writes it (POST /temporal/entities, attribute and instance deletes, an instance's PATCH). aggrMethods are computed by the broker from the instances. History imported with coraine-import (Migration) comes in through TroeDriver.historyImport, with the times it had in the source.

Option
--troeInstanceCap-troeCap · 1-1000000the most instances per attribute a temporal retrieve or query returns without lastN or firstN, oldest first (default 1000000). More there: a 200 with the first page and a Link: <...?offsetN=<cap>>; rel="intervalafter" header. Present only with --troe corDB.

Timepoint - an entity as it was

The same history answers the timepoint resources: TroeDriver.entityAtRetrieve and entityAtQuery are corDbTimepointRetrieve and corDbTimepointQuery. An entity at T is rebuilt in the store's own model from the instances the history keeps - so the broker projects, renders, matches q and geo and pages it as any store entity - and a query rebuilds each entity at T and runs the store's own query over them (corDbEntityQueryList).

  • The entity existed at T when its last lifecycle event at or before T is a create or a replace (system time); instances from before the create that started that life are left out.
  • Per attribute and datasetId: the instance of that life with the latest time at or before T - on modifiedAt, or on observedAt (modifiedAt for an instance without one), by the axis the broker asks for. A tombstone at or before T leaves the attribute out.
  • Its types are its current ones: the history keeps no change of types.

Declared indexes

An attribute whose q value terms an index serves is declared - for every tenant, or narrowed to one tenant, to one entity type: at start with --dbValueIndexes, on a running broker with /admin/indexes (kept as documents of the default tenant's dbIndexes collection, and back at the next start). Database indexes has both stores' indexes.

coraine --database corDB --dbValueIndexes https://example.org/ontology/speed
coraine --database corDB --dbValueIndexes '[{"attribute": "https://example.org/ontology/speed", "type": "https://example.org/ontology/Vehicle"}]'
  • What it is. In the store of every tenant a declaration covers, a skip list of the attribute's values - every instance's, an array's elements; booleans, numbers, strings - each with its entity (corDbValueIndex.h).
  • What it serves. A term on the attribute with ==, a range, a list, <, <=, >, >=: the candidates are the values the term can match, in the store's order, each then matched as before - the answer is the walk's. An AND takes its term with the fewest candidates; an OR is served when all its members are. Not served: !=, ~=, !~=, existence, a sub-attribute, a [member] path.
  • When it walks instead. A query by type whose type list is shorter than the candidates walks that list. A page (offset + limit) whose candidates exceed sqrt(page × entities), at least 64, walks the store - the walk stops at the page, while the index gathers and sorts every candidate. A count, or a query that wants every match, takes the index.
  • Built by the first query that can use it, under the read lock - and at once in every store when the admin API declares one. Not on disk. A change of the declarations rebuilds every store's index; the store's writes wait for it.
  • Kept by the functions that link, unlink and swap an entity, and by corDbIndexChanged where an entity changes in place; only the entities with a value of a declared attribute are in it.
  • Counted per declaration and store: accesses (the q terms served) and updates (the writes that changed it), in GET /admin/indexes.

At most 64 declarations; a short name (not an IRI) stops the start. make COR_FEATURE_DB_INDEXES=0 leaves the declared indexes out of the build, and the option with them. What a declared index gains and costs per request: Extreme performance.

Building it

A Cor-Lib checkout beside its siblings and beside ../coraine, whose plugin interface (src/lib/db/DbDriver.h, src/lib/troe/TroeDriver.h) it is compiled against; the corLibs umbrella builds it with the rest. It links only libgeos_c (geo-queries) and libm: the Cor-Lib and NGSI-LD functions it calls are resolved from the broker at dlopen.

make                         # debug (traces in), into obj/debug
make BUILD=release
make BUILD=coverage
make install                 # corDB.so, ramDB.so to /opt/seamware/plugins/db/currentState, troe/ramDB.so to .../troe/temporal
make COR_FEATURE_SUBSCRIPTIONS=0 COR_FEATURE_REGISTRATIONS=0   # as a broker built without them
make COR_WITH_GEOQ=0         # no geo-queries, no libgeos_c

Every make runs coraine's tools/dbAbiStamp.sh and compiles the stamp into each plugin as dbPluginAbi - the broker refuses a plugin built against other headers, and the plugin a broker (The interface stamp). A plugin is built with its broker's feature switches. It is tested through the broker: coraine's functional suite with -db corDB (and -troeDb corDB), locally and in CI.
