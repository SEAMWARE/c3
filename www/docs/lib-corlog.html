corLog

corLog is the log of an executable: error, warning, info, verbose and FIXME lines, and 3200 numbered trace levels, written one line at a time to a file, to stdout or to both. coraine logs with it, and every library of the stack reaches it through corBase's library log.

The macros

One header, corLog/corLog.h, declares everything. A line is written by a macro that captures the file, the line and the function, and takes a printf format:

MacroWrites
COR_E(fmt, ...)an E line - always
COR_W(fmt, ...)a W line - always
COR_I(fmt, ...)an I line, when corLogInfo is true
COR_V(fmt, ...)a V line, when corLogVerbose is true
COR_F(fmt, ...)an F (FIXME) line, when corLogFixme is true
COR_T(level, fmt, ...)a T line, when trace level level is on - in a debug build only (below)
COR_X(code, fmt, ...)an X line, then exit(code)
COR_RE(ret, fmt, ...)an E line, then return ret;
COR_RVE(fmt, ...)an E line, then return; (a void function)

COR_E, COR_W, COR_X, COR_I, COR_V, COR_F and COR_T are expressions; COR_RE and COR_RVE are statements (do { ... } while (0)). COR_I, COR_V, COR_F and COR_T test their switch inline and call corLogOut only for a line that is written: a line that is off costs a load and a branch, and its arguments are not evaluated.

#include "corLog/corLog.h"

static int configRead(const char* path)
{
  int fd = open(path, O_RDONLY);

  if (fd == -1)
    COR_RE(-1, "open(%s): %s", path, strerror(errno));

  COR_V("reading %s", path);
  COR_T(400, "fd %d", fd);

  return fd;
}

Starting the log

int corLogInit(const char* progName, const char* logDir, bool logToScreen, const char* logLevel,
               const char* traceLevels, bool verbose, bool fixme);
ArgumentWhat it does
logDirnon-empty: the log is the file <logDir>/<progName>.log; a file of that name is renamed <progName>.log.old first. The file is opened O_APPEND, so a file truncated under the process (logrotate's copytruncate) is written from its new start. NULL or "": the log is stdout
logToScreenwith a file, every line goes to stdout as well
logLevel"ERR", "WARN", "INFO", "VERBOSE", "TRACE" - a ladder: INFO and above turn corLogInfo on, VERBOSE and above corLogVerbose. Any other string: an error on stderr, and -1. NULL: neither
traceLevelsthe trace levels to turn on, "5,10,15-20". A non-NULL value - an empty string too - also sets the ladder to TRACE, so corLogInfo and corLogVerbose are both turned on
verbosetrue turns corLogVerbose on, whatever the level
fixmecorLogFixme - the F lines

It returns 0, or -1 when the file cannot be opened (said on stderr) or the level is not one of the five. The switches are plain globals (corLogInfo, corLogVerbose, corLogFixme) and can be set after it. coraine passes logLevel NULL and then sets corLogInfo and corLogVerbose both to its --verbose, so that a trace level turns on the trace lines and nothing else (src/lib/startup/startupLog.c):

if (corLogInit(progName, logDir, logToStdout, NULL, traceLevels, corArgsBuiltinVerbose, false) != 0)
  exit(1);

corBaseInit(corLogOut);                                            // the libraries' lines into this log
corBaseTraceLevelsSet(corLogTraceLevels, sizeof(corLogTraceLevels) / sizeof(corLogTraceLevels[0]));

corLogInfo    = corArgsBuiltinVerbose;
corLogVerbose = corArgsBuiltinVerbose;

Before corLogInit nothing is written - not even an E or a W: corLogOut returns. The one exception is COR_X: its message goes to stderr as X: <message> and the process exits with its code. A library line before the log is up is handled by corBase instead, which writes errors and warnings to stderr (corBase - the library log).

A log line

<type>: <seconds>.<ms>: <file>[<line>]: <function>: <message>
I: 000000.020: coraine.c[2280]: main: coraine running on port 1026
T: 000000.000: seCoreTerms.c[72]: seCoreTermsAdd: 27 Service Execution terms added to the core context (T-403)
  • the time is since corLogInit, seconds (six digits) and milliseconds, from CLOCK_REALTIME
  • the file is the source file's name without its directory
  • a trace line ends with its level, (T-403)
  • a message longer than 1023 bytes is formatted again into a buffer of its size; if that allocation fails, the line is the first 1023 bytes

Trace levels

A trace level is a number from 0 to 3199: a bitmask of 100 32-bit words, corLogTraceLevels. A level outside it is never on, and setting it does nothing.

FunctionWhat it does
corLogTraceLevelSet(s, replace)turns on the levels of s - a comma-separated list of levels and ranges, "220-226,403". replace true clears every level first; false adds
corLogTraceLevelReset(s)turns off the levels of s
corLogTraceLevelSetOne(n)
corLogTraceLevelResetOne(n)		one level on, off
corLogTraceLevelCheck(n)is level n on
corLogTraceLevelGet()the levels that are on, as ranges - "1-2,5-8". A static buffer: not to be freed, overwritten by the next call

A list is read up to 511 bytes; a longer one is cut after its last complete item. Each item is read with atoi: a range is from-to, both ends included.

How the numbers are shared

The trace levels are the executable's one number space: a library's COR_LIB_T lines are tested against the same bitmask (corBase's corBaseTraceLevelsSet). So each part of the stack takes its own range, and names its levels in a header of its own:

LevelsCodeDefined in
50-66corJson (50-54, 56-63), corTree (55, 64-66)corJsonTraceLevels.h, corTreeTraceLevels.h
100-116corRestcorRestTraceLevels.h
150-156corJsonldcorLdTraceLevels.h
200-240corNgsild - validation 200-210, forwarding 220-226, registration matching 227, notifications 230-235, transient entities 240ldTraceLevels.h
300-303corAllocCorAllocTraceLevel.h
400-404coraine itselfsrc/app/coraine/coraineTraceLevels.h

A new library picks a range nobody uses and defines its levels as an enum or #defines starting there.

Switching them on

In coraine, at start, with --traceLevels (-t) - Options:

coraine -db corDB -t 220-226,403

On a running broker, with the admin API plugin (--apiPlugins admin), through /admin/log. The parameters are traceLevels, verbose and info (on/off, true/false, 1/0):

RequesttraceLevels
PUT /admin/logreplaces the levels that are on
POST / PATCH /admin/logadds to them
DELETE /admin/logturns them off
curl -X POST 'http://localhost:1026/admin/log?traceLevels=1,2,5-8&verbose=on'
{
  "info": false,
  "traceLevels": "1-2,5-8",
  "traces": true,
  "verbose": true
}

Every request answers with the state after it. traces says whether this build has traces compiled in.

Threads

Each line is formatted on the caller's stack and written with one writev under one mutex (corLogMutex) - to the file, and to stdout with logToScreen - so lines of different threads never interleave. The switches and the trace-level bitmask are read without a lock: a change made at run time (/admin/log) is seen by the next line tested. The functions that change them take no lock either.

What a release build keeps

COR_T exists in a build compiled with -DCOR_T_ON, and nowhere else. Without it a trace is compiled away - no code, no format string, no test - but it stays an expression whose arguments are type-checked and count as used, so a variable only a trace reads still compiles under -Werror, and a broken trace fails the release build too. corBase's COR_LIB_T works the same way. COR_E, COR_W, COR_X, COR_I, COR_V and COR_F are in every build.

  • corLog's makefile builds BUILD=debug by default, which adds -DCOR_T_ON; make BUILD=release builds without it.
  • Every object compiled with COR_T_ON carries the string COR_T_ON:traces-compiled-in; coraine's makefile fails a release link whose broker or plugins hold it.
  • A release coraine accepts --traceLevels, turns nothing on, and says so at start with a W line (this broker is a release build, its traces are compiled out). Building lists which builds have traces.
