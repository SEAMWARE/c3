DDS and ROS 2

coraine speaks DDS, and so ROS 2, through its DDS bridge: topics, services and actions become entity attributes. A robot's pose is an NGSI-LD attribute, and writing an attribute publishes a sample, calls a service or sends a goal.

What it does

DDSIn the broker
TopicsBoth ways. A sample becomes the value of an attribute; writing the attribute publishes a sample. The configuration says which topic is which entity's attribute.
ServicesWriting the service's attribute calls the service. The reply lands in the same attribute (reply), beside the request it answers (request). The write waits a moment for it (?ddsSync=true), or answers at once and the reply arrives later.
ActionsWriting the action's attribute sends a goal. Each goal is an instance of the attribute of its own, and its feedback, status and result appear there as they come. A goal can carry an endpoint that is notified of its progress, and it can be cancelled.
DiscoveryTopics, services and actions that no configuration names are shown on one catch-all entity, urn:ngsi-ld:dds:default - "what is on this bus?" answers itself. A discovered service is callable, too.
  • Pre-population. Every configured attribute exists from start-up - its entity is created if it is not there yet - with the value "uninitialized" until the first sample.
  • History. A DDS update goes into the temporal history like any other write.
  • Short names. A default user @context (--defaultUserContext - a URL, or a file such as the dds-context.jsonld the mapping tool writes) expands the configuration's entity types and attribute names. A client that uses the same short names without an @context of its own reads and writes the same attributes.

The entity mirrors the wire

A value DDS never saw is not stored, and a slow robot does not make the broker slow:

WhenThe broker
A value does not fit the topic's DDS typerefuses it - 400, nothing stored
An attribute is writtensends it to DDS first, and stores it only if DDS took it
A service is slow to answerwaits briefly, if asked to, then answers 202; the reply lands when it comes
One write, several attributes, DDS refuses onewrites the others; the 207 names the refused one
An action's last goal is overkeeps the attribute - its default instance, without the goals
A ROS name has a /robot1/navigate becomes the attribute robot1_navigate

Configuration

One file, shared by the plugin and the broker: the DDS Enabler reads dds.ddsmodule, the broker reads dds.ngsild.

{
  "dds": {
    "ddsmodule": { "dds": { "domain": 0 } },
    "ngsild": {
      "topics": {
        "rt/pose": { "entityId": "urn:ngsi-ld:Robot:1", "entityType": "Robot", "attribute": "pose" }
      }
    }
  }
}
coraine --bridges dds --bridgeConfig /path/to/that.json

Services and actions are entries of dds.ngsild.services and dds.ngsild.actions, with the same entityId, entityType and attribute. A service's DDS types are requestType and replyType - by default its name with _Request and _Response; they are configured because a service, unlike a topic, cannot be learned by listening. An action names its ROS 2 action type once, in type; its DDS types follow from it.

OptionWhat it does
--bridges ddsCORAINE_BRIDGESloads the DDS bridge, dds.so
--bridgeConfig <file>CORAINE_BRIDGECONFIGthe configuration file above
--defaultUserContext <url|file>CORAINE_DEFAULTUSERCONTEXTthe default user @context; the broker also serves it, as /ngsi-ld/v1/jsonldContexts/defaultUserContext
--ddsSyncCORAINE_DDSSYNCa PATCH of a service attribute waits for the reply by default; ?ddsSync=false opts out. Default: it does not wait
--ddsSyncTimeout <ms>CORAINE_DDSSYNCTIMEOUThow long a waiting PATCH gives a service before answering 202. 0 (default): the configuration's syncTimeoutMs, else 200
--ddsSyncWaitMax <n>CORAINE_DDSSYNCWAITMAXat most this many requests wait for a service at once (default 8); the rest send without waiting (202), so a slow DDS network cannot take every worker

Building the plugin

The bridge is its own repository, corDdsBridge, and is part of no umbrella build: the DDS stack it links is 21.4 MiB across nine libraries (libfastdds alone 16 MiB), about five times the whole broker. Only a deployment that wants DDS clones and builds it.

make            # build
make install    # dds.so into /opt/seamware/plugins/bridge/
make contract   # does it still satisfy BridgeDriver.h? needs no DDS at all
  • Needs the DDS Enabler and Fast DDS in /usr/local, and nlohmann-json3-dev.
  • C++, behind a C contract. The DDS Enabler's API is C++ only. The plugin is a C++ shared object that exports one C symbol, bridgeRegister; the broker stays C. libstdc++ enters the broker's process when the plugin is loaded.
  • What it fills of the contract (BridgeDriver.h in corBridge): topics - samples in (sampleIn and its qualified / meta forms), publish out; services - a request sent with serviceInvoke / serviceInvokeTracked, its reply back as replyIn; actions - goals sent with actionGoalSend, cancelled with actionGoalCancel, their feedback and result back as goal events. Services and actions the DDS network announces go to the broker as discovered endpoints (endpointDiscoveredIn). Each slot is filled only when the broker's bridge ABI has it (ddsRegister.cpp).
  • Whether it builds is COR_BRIDGE_DDS: auto (the default - where the Enabler is installed, and it says which), ON (a missing dependency is an error), OFF.

nlohmann-json3-dev is needed although nothing in the plugin uses it. The Enabler's own public header ddsenabler_participants/Writer.hpp includes <nlohmann/json.hpp>, so its absence shows as an error in a file of the Enabler's. make checks for it by name.

Tests

Close to forty functional tests cover the DDS side, eight of them against real ROS 2 nodes: talker and listener, a Fibonacci action server, service servers, a geometry_msgs/Twist topic. They run on both of coraine's databases.

Not yet

  • A service or a fast action answering within the time a write already spends forwarding to other brokers, its answer going straight into the response.
  • Bridges and channels created and changed at runtime - today they come from the configuration file.

Other bridges: MQTT, Modbus; devices in general: Speaking to devices directly.
