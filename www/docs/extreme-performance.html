Extreme performance

The published broker is built to be fast for everybody. A deployment that knows what it does can be much faster. Two things decide most of it, and in this order: indexes on the attributes you query, and a broker built for your workload.

1Index the attributes you query

Without an index, a q on an attribute reads every entity of the type and keeps the ones that match: fine at a thousand entities, the whole answer time at a million. With one, it reads the entities that match. An attribute with an index is declared - the broker creates the index in every tenant it covers, a tenant created later included.

What it gains, and what it costs

100 000 entities, one attribute declared; corDB on disk, MongoDB 8.2 local, PostgreSQL 16 with TimescaleDB 2.29 (2.9 million rows of history); the release build, 2026-10-22.

The gain is where a q is selective - few entities match. The cost is on every write of the attribute. Which weighs more is the workload's: how often the attribute is queried, how often it is written. The broker counts both - GET /admin/indexes and /admin/metrics (ngsild_index_accesses_total, ngsild_index_updates_total) - so the answer can be read off a running deployment.

Declaring them

coraine --dbValueIndexes https://example.org/ontology/speed ...       # the current state - corDB, MongoDB
coraine --dbValueIndexes '[{"attribute": "https://example.org/ontology/speed",
                           "type": "https://example.org/ontology/Vehicle"}]'   # narrowed to a type, or a tenant
coraine --troe timescale --troeValueIndexes https://example.org/ontology/speed ...  # the history

The names are expanded - the IRIs your clients' @context gives them. The option has no @context to expand a short name with, so speed alone is an error, and the broker does not start (it names the core @context's IRI, https://uri.etsi.org/ngsi-ld/default-context/speed, the one to use when the clients send no @context). The admin API expands with the request's own @context. The terms an index serves: a value of the attribute with ==, a range, a list, <, <=, >, >= (MongoDB also ~=). != matches by a value an entity does not have, and reads every entity.

Declare them at start. The admin API (POST /admin/indexes, /admin/troeIndexes) changes them on a running broker, and every change builds indexes over the whole store while it runs: at 1 000 000 entities, 0.87 s on corDB - every declaration's index built again, the writes waiting - and 1.1-2.1 s on MongoDB. Choose them when you deploy.

The history also finds an index made by hand in psql - a partial index on v_number or v_text of one attribute - and uses it within a minute. The Database indexes guide has what each store keeps, and how to see what a query uses.

2A broker built for your workload

The published image is one build, tuned on a general mix of requests. make tune builds one for yours: it trains the compiler on a description of the workload, measures the settings that depend on it, and builds the result - a binary or an image.

out of the boxmake tune
compiler optimisation-O2, profile-guided (PGO), trained on every kind of work - none of it in your proportionsthe profile trained on your workload: the hot paths together, the branches the right way round
memory allocatorglibc's mallocglibc, jemalloc or tcmalloc - measured, the fastest kept (LD_PRELOAD, no rebuild)
corDB's store lockreaders first (--dbLockPrefer reads)readers or writers first - measured

The HTTP server's pool and corDB's durability (--dbSync) are the deployment's, not the workload's: they stay options you set. Indexes are the workload's too, and make tune does not choose them - section 1.

The workload file

JSON, every member with a default. Make the entity look like yours - how many attributes, how many observed or with sub-attributes - and the load like yours:

{
  "store": { "database": "corDB", "persistent": true, "history": "none" },

  "entities": {
    "count": 10000,
    "types": [
      { "type": "Vehicle", "share": 0.8,
        "attributes": [
          { "name": "speed",    "type": "Property", "value": 42, "observedAt": true, "subAttributes": 1 },
          { "name": "location", "type": "GeoProperty" },
          { "name": "isParked", "type": "Relationship" }
        ] },
      { "type": "Parking", "share": 0.2,
        "attributes": [ { "name": "free", "type": "Property", "value": 10 } ] }
    ]
  },

  "subscriptions": [
    { "count": 100, "select": "perEntity", "watchedAttributes": ["speed"] },
    { "count": 5,   "select": "byType", "type": "Parking", "q": "free<3" }
  ],

  "load": {
    "concurrency": 50,
    "mix": { "patch": 0.80, "query": 0.10, "retrieve": 0.05, "create": 0.05 },
    "patch": { "attributes": ["speed"] },
    "query": { "type": "Vehicle", "q": "speed>50", "limit": 20 }
  },

  "duration": "30s"
}
storedatabase: corDB or mongoc; persistent: corDB on disk; history: none, corDB, timescale
entitiescount in all, split over the types by share. An attribute: type (Property, GeoProperty, Relationship, LanguageProperty, VocabProperty, ListProperty, JsonProperty), value (a number varies per entity), observedAt, subAttributes
subscriptionsgroups of count. select decides the fan-out - how many notifications one write sends: perEntity (one entity each), byType (every entity of type); watchedAttributes, q as in NGSI-LD
loadconcurrency (connections), the mix of patch, query, retrieve, create; what a patch updates, what a query asks
durationeach measured run, after a 5 s warm-up

3Building it

From a source build: the cor-libs as siblings (corLibs/bootstrap.sh clones and builds them), then the broker. make tune also needs wrk and python3, corTestClient (from corLibs/bin, it counts the notifications), and the allocators it compares: apt-get install libjemalloc2 libtcmalloc-minimal4.

cd coraine
make tune WORKLOAD=my-workload.json     # ~15 min: the instrumented build, the training, the comparison
make install_pgo                        # the tuned build -> /usr/local/bin, /opt/seamware

It ends with one line, and writes tune-result.json - the best combination, and every one, each with its p99 beside its rate:

tune: best --dbLockPrefer writes LD_PRELOAD=/usr/lib/x86_64-linux-gnu/libtcmalloc_minimal.so.4 - 173721 requests/s, +11.1 % against the out-of-the-box settings - tune-result.json

Then run the broker with what it says:

LD_PRELOAD=/usr/lib/x86_64-linux-gnu/libtcmalloc_minimal.so.4 coraine -fg --database corDB --dbDir /var/lib/coraine --dbLockPrefer writes ...

From c³

The Compile page trains a broker the same way, with coraine-build (the coraine-dev package, which installs the source). Under Optimisation:

  • Profile-guided - built instrumented, trained on the standard request shapes, rebuilt with the profile: the published image's build, made on this machine.
  • Tuned for a workload - trained on your workload file (its absolute path on this machine), and the allocator and the lock policy measured on it.

Both need curl, wrk and python3. apt-get install coraine-dev brings them, with the toolchain and the source; on a build from source, the button is greyed out, with what is missing, until they are installed. A trained build uses libmicrohttpd: the built-in HTTP server cannot be trained yet. The build's log shows each step live - build, train, install, check.

A tuned build keeps the settings that won in <build>/install/etc/tune.env (TUNE_DBLOCKPREFER, TUNE_ALLOCATOR). Operate applies them when it starts that build's broker, as the image does: the lock preference as the default of --dbLockPrefer (an option set in Operate still wins), the allocator preloaded. The broker's log names what was applied; an allocator that is not installed is left out, and the log says so.

As a Docker image

cp my-workload.json coraine/tune/
docker build -f docker/Dockerfile --build-arg WORKLOAD=tune/my-workload.json -t my-coraine .

The profile is built in, only the allocator that won is installed, and the entry point applies the settings that won (/opt/seamware/etc/tune.env). docker run -e overrides them: -e CORAINE_DBLOCKPREFER=reads, -e LD_PRELOAD= for glibc's allocator.

Measure on a quiet machine, of the kind the broker runs on. The comparison runs the workload on the build machine: a browser, a build or a video call beside it is measured too, and which allocator wins can depend on the CPU. make tune warns when a browser is up. c³ itself runs in one: for the numbers you will run on, train from the command line, with the browser closed.

4What tuning is worth

Two workloads, each three ways: out of the box (the published image's build), the tuned profile (make tune's build with the default settings - the profile alone), and tuned (with the settings it chose). corDB on disk, release builds, AMD Ryzen 9 8940HX, 2026-10-07; requests/s, the mean of three runs, every run within 2 % of its mean, no request failed.

A deployment that subscribes

10 000 Vehicles and Parkings, 105 subscriptions, 80 % PATCH, 10 % queries, 5 % retrieves, 5 % creates

Writers first and tcmalloc. Every query reads 8 000 Vehicles under the store's read lock; with readers first the PATCHes queue behind them. Writers first lets them in - more throughput, half the tail.

  • The profile alone adds little on these two (+2.3 %, -0.1 %): the general training already runs these paths. What a workload changes is the settings.
  • Which settings win differs. On the ingest: tcmalloc +11.1 %, glibc +7.1 %, jemalloc +5.7 % with writers first - and jemalloc -6.0 % with readers first.
  • Next to an index, these are small: +12.5 % and +46.9 % here, against ×17.6 to ×919 for a selective q on an attribute with an index.
