High availability

Several coraine instances behind a load balancer, sharing one MongoDB - what it takes, how the instances stay in step, and what to check when they disagree.

The setup

Three parts, all three needed:

  1. Two or more coraine instances - pods, containers, hosts.
  2. A load balancer in front of them. A request may land on any instance; no session affinity is needed.
  3. MongoDB as a replica set, shared by every instance, through the mongoc plugin.

Why the instances must be kept in step

Each instance keeps its subscriptions, registrations and @contexts in RAM, pre-compiled, so that matching an update or forwarding a request never costs a database round trip. One created through an instance lands in that instance's caches.

Without --high-availability mongo the failures look intermittent. The other instances never learn of the new subscription or registration, and the load balancer spreads the requests: notifications sent by some instances and not others, a forwarded request that works on one instance and is a 404 on the next.

With it, every instance watches the shared database with a MongoDB change stream and is pushed each change as it is written - no polling, no interval to tune, no peer list, no extra port.

Requirements

Database pluginmongoc. An in-memory store is nobody else's: the broker refuses --high-availability mongo with one
MongoDBa replica set, 4.0 or later (a change stream over the whole deployment). One node runs the mechanism (mongod --replSet rs0, then rs.initiate() once); real availability needs redundancy in the database too
MongoDB privilegesfind and changeStream on all databases - below
Temporal history--troe timescale (one PostgreSQL shared by every instance) or --troe none. A history inside the process (ramDB, corDB) would hold, in each instance, only the writes it served; the broker refuses it with --high-availability mongo
corainethe same version on every instance

The replica set, the credentials and the auth database go in the connection URI:

--dbURI "mongodb://<user>:<password>@<host1>,<host2>,<host3>/?replicaSet=rs0&authSource=admin"

MongoDB privileges

With authentication on, readWrite on coraine's own databases is not enough. Each instance watches the whole deployment with one change stream - a tenant is a database of its own, and new tenants appear at any time - and MongoDB allows that only to a user with find and changeStream on every database. A role with exactly that:

use admin
db.createRole({
  role:       "coraineHaWatch",
  privileges: [ { resource: { db: "", collection: "" }, actions: [ "find", "changeStream" ] } ],
  roles:      []
})
db.grantRolesToUser("<the coraine user>", [ { role: "coraineHaWatch", db: "admin" } ])

The built-in readAnyDatabase role covers it too, and grants more than is needed.

Enabling it

Off by default. On every instance, as the option or as its environment variable:

OptionWhat it does
--high-availability mongoCORAINE_HIGH_AVAILABILITY=mongokeeps the caches in step through a change stream on the shared MongoDB; short form -ha

An instance started with it refuses to start - it does not fall back to running out of step - when the database is not a replica set, or the change stream cannot be opened, typically for the privileges:

E: ... mongocHaWatchStart: --ha mongo: unable to open the change stream (not authorized on admin to execute command { aggregate: 1, pipeline: [ { $changeStream: { allChangesForCluster: true } } ] ... }). The stream watches the whole deployment ...
X: ... main: unable to start the HA channel 'mongo'

On Kubernetes: pods in a crash loop with that message. Grant the role and they start.

How it works

  • One change stream per instance covers every tenant, in one thread. It is opened at start-up, before the caches are loaded, and nothing is applied until the load is done - nothing written by another instance in between is missed.
  • Each event names the item and the operation - insert, update, delete; the instance reads that one item again and updates its cache. An instance also receives its own changes; applying them again is harmless.
  • Adding or removing an instance needs nothing anywhere: a new one loads the caches at start-up and then watches.
  • A dropped connection (a brief network loss, a primary failover): the MongoDB driver resumes the stream by itself. If it cannot, the error is logged and the stream reopened 5 seconds later, from that moment - the instance serving meanwhile: 
    E: ... HA: change stream error (...) - restarting the stream in 5 seconds

Changes between the break and the reopen are not applied until the instance restarts.

Eventual, but pushed. A change reaches the other instances typically milliseconds after it is committed - not at once: a client that creates a subscription and at once sends an update through the load balancer may have the update handled by an instance that has not applied the subscription yet.

The temporal history

With --troe timescale every instance writes the history of the requests it serves into the one shared PostgreSQL, and any instance answers a temporal query with all of it. Nothing of the history is synchronised, so nothing is written twice and nothing is lost when an instance goes:

  • Schema migrations at start-up hold a PostgreSQL advisory lock - instances starting together upgrade the schema once.
  • A tenant's database created by two instances at once is created once; the second CREATE DATABASE is taken as done.
  • Instance ids are UUIDs, unique whichever instance creates them.

What is each instance's own:

The clockan instance stamps the history it writes (modifiedAt, createdAt) with its own clock, and the stamps order an attribute's instances and give the Entity its modifiedAt. Keep the clocks synchronised (NTP): a skew between two instances is a skew in the order of the writes they served
When the history is writtenan instance queues a request's history right after the response, and a writer commits it with the others queued meanwhile, in one transaction. An instance that dies between the response and that commit leaves the write in the current state and not in the history - with --troeSync too, which queues it before the response but does not wait for the commit
The shared PostgreSQL downevery instance keeps serving the current state; each holds the history of the writes it serves, up to 8 MiB, and loses what does not fit; /ready stays 200. --troeDownExit makes an instance exit instead

Instances that disagree

The symptom: MongoDB holds everything, but each instance knows only what was created on it. Clients that list subscriptions to reconcile them see different answers depending on which instance replies, and create duplicates.

  1. Is --high-availability mongo set on every instance? Without it there is no synchronisation at all, and this is what that looks like.
  2. Is the change stream working? Look in every instance's log for HA: change stream error. not authorized ... $changeStream ... allChangesForCluster there means the privileges are missing.
  3. Grant the privileges, then restart the instances - a rolling restart is fine. A running instance retries the stream every 5 seconds and receives changes once the privileges are in place, but changes made before that are not replayed; a restart loads the complete state from MongoDB.
  4. Check: create a subscription through the load balancer, then ask each instance directly for GET /ngsi-ld/v1/subscriptions/<id>. Every one must answer 200.
  5. Clean up the duplicates made while the instances disagreed - they are real subscriptions, and synchronising does not remove them. GET /ngsi-ld/v1/subscriptions answers from the instance's cache: to see what is stored, look in MongoDB (the subscriptions collection of the tenant's database) or ask each instance after its restart, and DELETE the extras.

Not synchronised: Snapshots

Each instance loads the Snapshots (NGSI-LD § 5.16) at start-up, but changes to them are not synchronised: a Snapshot created through one instance is known to the others only after they restart.
