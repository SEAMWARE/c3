corPlugin - loading plugins

SEAMWARE/corPlugin - a small loader over dlopen and dlsym: it turns a plugin's short name into the path of a .so under a base directory, opens it, finds its register symbol, refuses one built against another tree-node layout, and closes every handle at shutdown. coraine loads its database, history, API, transport, auth and bridge plugins through it; the library itself knows none of those kinds.

The base directory

const char* corPluginSetBaseDir(const char* defaultDir, const char* envVarName);
const char* corPluginBaseDir(void);

Called once, at start-up, before the other functions: the base directory is the environment variable's value when it is set, else defaultDir. Neither string is copied. coraine and coraine-import:

corPluginSetBaseDir("/opt/seamware/plugins", "SEAMWARE_PLUGIN_DIR");

coraine -u ends with the directory it uses (Plugins are loaded from /opt/seamware/plugins), and GET /build reports it.

From a name to a path

void corPluginResolve(const char* baseDir, const char* category, const char* subcategory,
                      const char* name, char* pathOut, int pathSize);
CallPath
corPluginResolve(base, "db", "currentState", "mongoc", ...)<base>/db/currentState/mongoc.so
corPluginResolve(base, "bridge", NULL, "mqtt", ...)<base>/bridge/mqtt.so
a name with a / in it - ../corDB/obj/debug/corDB.sothe name itself: the base directory is skipped

It only builds the string - nothing is looked up. The path form is how a freshly built plugin is loaded straight from its build tree:

coraine --database ../corDB/obj/debug/corDB.so

The directories coraine uses, kind by kind, are in Plugin architecture.

Opening a plugin

void* corPluginOpen(const char* path, const char* symbolName, char* errorBuf, int errorBufSize);
  1. A path that does not exist: NULL, not found.
  2. dlopen(path, RTLD_NOW) - every undefined symbol of the .so is resolved now, against its own libraries and the host's exported symbols; one that is missing fails here, with the dlerror() text, not at the first call.
  3. dlsym of symbolName - missing: the handle is closed, NULL.
  4. The layout check (below) - refused: the handle is closed, NULL, and corPluginRefused() is true from then on.
  5. The symbol is returned. The caller casts it and calls it - corPlugin never calls into a plugin.

On every failure errorBuf (which may be NULL) holds the reason. This is coraine's DB plugin, from src/lib/plugin/pluginLoader.c:

#include "corPlugin/corPlugin.h"

char path[512];
corPluginResolve(corPluginBaseDir(), "db", "currentState", shortName, path, sizeof(path));

char openErr[512];
DbRegisterFunc registerFunc = (DbRegisterFunc) corPluginOpen(path, "dbRegister", openErr, sizeof(openErr));
if (registerFunc == NULL)
{
  snprintf(errorBuf, errorBufSize, "DB plugin '%s' (%s): %s", shortName, path, openErr);
  return -1;
}

registerFunc(&db);                 // the plugin fills the driver struct

A DB or TRoE plugin has a second check of coraine's own between the open and the register call, its interface stamp (Plugin architecture). The kinds, their register symbols and their driver structs are coraine's, not this library's.

Closing

corPluginCloseAll() dlcloses every handle corPluginOpen returned a symbol for - coraine calls it at shutdown, after the DB plugin's close. Every plugin opened is tracked, however many there are (the list grows); a failed open closes its handle at once and is not tracked.

The layout check

A plugin reads and builds the host's tree nodes by their fields - every kind does. Built against another CorNode layout, it would read every node at the wrong offsets. Every object compiled with corTree's CorNode.h (SEAMWARE/corTree) carries the layout's number, corNodeLayout (2), as an exported weak symbol - a plugin built with -fvisibility=hidden too. After the dlsym, corPluginOpen looks up corNodeLayout in the handle and compares it with the host's own:

The pluginResult
carries the host's numberopened
carries another numberrefused - plugin: CorNode layout <n>
carries none - built before the number existedrefused - plugin: CorNode layout 1, or older - it has no corNodeLayout
its corNodeLayout is found only in one of its dependenciesrefused as carrying none: the number counted is the one in the same object as the register symbol (dladdr), not one a library it links brings along
bridge plugin 'mqtt' (/opt/seamware/plugins/bridge/mqtt.so): refused - built against another tree-node layout than this broker (plugin: CorNode layout 1, or older - it has no corNodeLayout; broker: CorNode layout 2). It would read every node at the wrong offsets and crash the broker. Rebuild the plugin against this broker's Cor-Libs

The other direction - a plugin built against layout 2 in a host from before it - never reaches this check: every object built with CorNode.h references corNodeLayout2, which only a corTree with that layout defines, so the dlopen fails, undefined symbol: corNodeLayout2.

  • The plugin has been opened when it is refused: its initialisers (constructors) have run. Its register function has not.
  • corPluginRefused() lets the host stop on the refusal itself. coraine exits 1 right after loading the plugins - before parsing the command line, which without the refused plugin's options would report one of them as unknown, and the refusal would not be the last thing said.
  • The check is always compiled in; it has no switch.

What a plugin resolves from the host

A plugin that calls the host's libraries does not link them. The host is linked to export its symbols (-rdynamic, CMake ENABLE_EXPORTS) with those libraries linked whole (--whole-archive), so none is dropped; RTLD_NOW binds the plugin to them at the open. coraine is linked that way, and its plugins call corLog, corAlloc, corTree, corJson, corNgsild, ... from the running broker.

Such a plugin depends on the host's build, not only on the struct it fills. A symbol the host lacks fails the open. A function whose signature, or a type whose layout, differs between the headers the plugin was built against and the host's is not detected - except the tree node's, above. So a plugin is built against the same sources as the host that loads it; a contract version a host defines for its own structs (coraine's BRIDGE_ABI_VERSION, TRANSPORT_ABI_VERSION) covers those structs only (Built for this broker).

Listing what is installed

const char* corPluginScanNames(const char* dirPath, char sep, char* buf, int bufSize);
void        corPluginArgUpdate(const char* argLongName, const char* subDir);

corPluginScanNames lists the *.so of a directory, the suffix stripped, sorted, joined by sep - "corDB|mongoc|ramDB"; NULL when the directory is missing or holds none. At most 32 names of under 64 characters are taken. Sorted, so two identical installations print the same usage.

corPluginArgUpdate makes such a list the description of a corArgs option - the names under <base>/<subDir>, after corArgsInit. coraine does it for --database (db/currentState), --troe, --apiPlugins, --bridges and --auth, so coraine -u shows what can be loaded. At most 8 options; a directory with no plugin leaves the description as it was.
