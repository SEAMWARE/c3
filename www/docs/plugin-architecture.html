Plugin architecture

The broker binary holds the NGSI-LD logic, the REST layer, the JSON-LD engine and the subscription matcher - and no storage code and no temporal code. Storage, history, extra endpoints, transports, bridges and authorization are shared objects, chosen at start-up. A new one is written without touching the core.

Several are comma-separated where more than one may be active. HTTP and cor:// are not plugins - they are built into corRest.

--troe corDB is not a file of its own. The history inside corDB is the corDB current-state plugin's own troeRegister - the same store, the same lock, the same log - so it needs --database corDB; with another store the broker stops: TRoE 'corDB' keeps the history inside the corDB store - it needs --database corDB. Another store's history goes to an external server (timescale).

A transport is not a bridge. A transport - like HTTP and cor:// - is how a client reaches the broker's API. A bridge is how the broker reaches a wire that is not NGSI-LD: a DDS topic, an MQTT broker, an OPC UA server. A bridge never answers a request.

Where plugins are loaded from

The base directory is /opt/seamware/plugins, or the environment variable SEAMWARE_PLUGIN_DIR; make install copies the bundled plugins into it. coraine -u ends with the directory it uses.

/opt/seamware/plugins/
├── db/currentState/    mongoc.so  corDB.so  ramDB.so
├── troe/temporal/      none.so  ramDB.so  timescale.so      # --troe corDB is corDB.so above
├── api/                admin.so
├── transport/          ws.so
├── auth/               fdsc.so  oidc.so
└── bridge/             loopback.so  mqtt.so  modbus.so  dds.so  ckan.so  opcua.so

A name with a / in it is a path, and skips the base directory - a freshly built .so straight from a build tree:

coraine --database ../corDB/obj/debug/corDB.so

How a plugin is loaded

  1. The path is built from the base directory, the kind and the name (unless the name is a path).
  2. dlopen with RTLD_NOW, and dlsym of the register symbol. A plugin built against another CorNode layout than the broker is refused here, whatever its kind.
  3. A DB or TRoE plugin's interface stamp is checked - before its register function is called.
  4. The register function is called with a zeroed driver struct, which it fills with its function pointers.

A plugin does not link the broker's libraries: the broker is linked -rdynamic, with its libraries and the Cor-Libs whole-archived, so a plugin resolves corLog, corAlloc, corTree, corJson, corNgsild, ... from the running broker at dlopen. A plugin's own CMakeLists.txt links only its backend - mongoc2, geos_c, ...

  • Its own options. A plugin may publish command-line options (driverP->args). The broker reads --database, --troe, --apiPlugins, --bridges and --auth before the main parse, loads the plugins and adds their options - so coraine --auth fdsc -u lists the --fdsc* options, and --help differs with the plugins chosen.
  • NULL means unsupported. A driver slot left NULL is an operation the plugin does not have: the service routine answers 501 Not Implemented, or does nothing where the specification allows it.
  • An auth plugin that cannot load or init stops the broker. No --auth lets every request in.

Built for this broker

A plugin that calls Cor-Lib functions must be built against the same lib sources as its broker - for a packaged broker, the coraine-dev source of the same version (Installation). A function the broker lacks fails the dlopen. A changed signature or struct layout is not detected - except the two checks below.

The CorNode layout - every plugin

Every kind of plugin reads and builds the broker's tree nodes by their fields; built against another layout it would read every node at the wrong offsets. The layout has a number, corNodeLayout in corTree's CorNode.h - 2 today - which every object built with that header carries, and every driver header includes.

PluginBrokerWhat happens

bridge plugin 'mqtt' (/opt/seamware/plugins/bridge/mqtt.so): refused - built against another tree-node layout than this broker (plugin: CorNode layout 1, or older - it has no corNodeLayout; broker: CorNode layout 2). It would read every node at the wrong offsets and crash the broker. Rebuild the plugin against this broker's Cor-Libs

The interface stamp - DB and TRoE plugins

A DB or TRoE plugin shares structs with the broker by layout - DbDriver, DbQueryFilter, Tenant, TroeDriver, ... A mismatch would corrupt memory, so it is refused both ways, and the program exits 1:

SideExportsChecks
the broker (coraine, coraine-import)coraineDbAbithe plugin's dbPluginAbi, after the dlopen, before the register function
the plugindbPluginAbithe broker's coraineDbAbi, first thing in dbRegister / troeRegister - so a broker older than the check is stopped too

The stamp is a hash (sha256, 16 hex digits) of the headers the two sides share structs through, comments stripped and whitespace collapsed - a comment edit leaves it as it was, any declaration change gives a new one, and nothing is bumped by hand (tools/dbAbiStamp.sh --list names the headers). A refusal names both stamps:

DB plugin '/opt/seamware/plugins/db/currentState/corDB.so' does not match this broker: it has no DB plugin interface stamp; a plugin built against another DB plugin interface corrupts memory
  plugin's interface stamp: none - built before the check
  broker's interface stamp: 8fa2e0424436a91e
  rebuild the plugin against this broker's source, or install matching versions of the broker and its plugins

Both checks are always compiled in - safety checks of the plugin interface, with no COR_FEATURE_* switch.

A contract version covers its structs and nothing else - the Cor-Lib functions a plugin calls are the "same sources" rule above. API, bridge and transport plugins carry no interface stamp.

What crosses a bridge

  • A bridge knows nothing about entities. It carries bytes to and from an endpoint; which attribute an endpoint is, is a Channel, kept in the broker. The seam is (endpoint, json, time) both ways - in through BridgeBroker::sampleIn, out through BridgeDriver::publish.
  • Everything crossing it is plain data - const char*, int64_t: no tree node, no allocator, no NGSI-LD type. A bridge need not be C - the DDS one is C++, which the broker dlopens without seeing a C++ token - and its calls arrive on threads the broker did not create.
  • No loop. An arriving value is stored through the DB driver and never enters a service routine, while the outbound hook is in the service routines: a value that came in from a transport cannot reach the code that sends values out.

A bridge may use the Cor-Libs directly - logging, corJson and corTree for its configuration, in an allocator of its own. The contract is its own library, corBridge; corBridgeTemplate is where a new bridge starts.

Writing a DB plugin

One .so exporting void dbRegister(DbDriver*) - as corDB's corDbRegister.c, a DB plugin in a repository of its own:

#include "db/DbDriver.h"

void dbRegister(DbDriver* driverP)
{
  driverP->alias          = "myStore";
  driverP->version        = "0.1.0";
  driverP->args           = myArgV;          // or NULL
  driverP->init           = myInit;          // after the options are parsed
  driverP->close          = myClose;
  driverP->entityCreate   = myEntityCreate;
  driverP->entityRetrieve = myEntityRetrieve;
  driverP->entityQuery    = myEntityQuery;
  driverP->entityDelete   = myEntityDelete;
  // ... what you support; the rest stays NULL (501)
  driverP->tenantSetup    = myTenantSetup;
  driverP->tenantRelease  = myTenantRelease; // frees what tenantSetup hung on Tenant.pluginData
}
  1. Compile src/plugins/shared/dbPluginAbi.c into it, with the generated dbAbiStamp.h on the include path, and call dbPluginAbiBrokerCheck("DB") first in dbRegister - without them the broker refuses it.
  2. Build it as a SHARED library, linking only its own backend; src/plugins/currentState/mongoc/CMakeLists.txt is the template.
  3. Drop myStore.so into <base>/db/currentState/ and run coraine --database myStore.

API and TRoE plugins follow the same pattern, with apiRegister and troeRegister.
