Database indexes

An index lets the database go straight to the documents a query asks for. Without one it reads every document and keeps the ones that match - a cost that grows with the store: fine at a thousand entities, the whole answer time at a million. Asking "which index does this query use, and how many documents did it read for the ones it returned" is the first question when a broker with MongoDB or PostgreSQL behind it is slow.

corDB

corDB keeps the entities in the broker's own memory, with its own indexes - the entity id, the entity type, and the default order. There is no database to connect to. An index on an attribute's values is declared: --dbValueIndexes <its IRI> at start, or POST /admin/indexes on a running broker - Extreme performance has what it gains and costs.

MongoDB - what coraine creates itself

The entities are in the collection entities of the broker's database (--dbName; a tenant has a database of its own). For every database, at start-up and when a tenant is first used:

IndexServes
_idthe entity id - retrieve, update and delete of one entity (MongoDB's own)
{type, createdAt, _id}a query by type, in the default order: it reads exactly the page asked for. A page of 20 of a type that is 1 % of 100 000 entities: 19.7× the requests/s of an index on type alone (MongoDB 8.2, 2026-10-08)
{createdAt, _id}the default order of a query without a type - otherwise a sort in memory, which MongoDB limits
2dsphere on each GeoPropertygeo-queries; created when the broker first sees the GeoProperty
cor_v_<id>, cor_d_<id>a q on a declared attribute (--dbValueIndexes, /admin/indexes): its default instance's value, and its datasetId mark. One that no declaration names is dropped

The broker also drops an index named type_1 at start-up - the index on type alone that older versions created, now a prefix of the second one. Don't give an index of your own that name.

MongoDB - how an entity is stored

One document per entity. Each attribute is a top-level field named by its expanded name, with every . written as ． (U+FF0E, fullwidth full stop - MongoDB reads a dot in a field name as a path); inside it one member per instance - @none for the default one, the datasetId for the others - and the value in value:

{
  "_id":  "urn:ngsi-ld:Vehicle:7",
  "type": "https://uri.etsi.org/ngsi-ld/default-context/Vehicle",
  "https://uri．etsi．org/ngsi-ld/default-context/speed": {
    "@none": { "value": 80, "observedAt": ... }
  },
  "createdAt": ..., "modifiedAt": ...
}

MongoDB - does a query use an index?

In mongosh, the query the broker sends for GET /ngsi-ld/v1/entities?type=Vehicle&limit=20:

use cor
db.entities.find({ type: "https://uri.etsi.org/ngsi-ld/default-context/Vehicle" })
  .sort({ createdAt: 1, _id: 1 }).limit(20)
  .explain("executionStats").executionStats

totalDocsExamined against nReturned: 20 against 20 is an index doing its job; 100 000 against 20 is every entity read for a page. explain() without executionStats names the plan - IXSCAN an index, COLLSCAN every document.

MongoDB - adding an index by hand

db.entities.createIndex({ "https://uri．etsi．org/ngsi-ld/default-context/speed.@none.value": 1 })
  • It lasts. An index is part of the database on disk: it survives a restart of MongoDB and of the broker. It is not in a tenant created later (a database of its own), nor in a database dropped and created again.
  • The name must be exact - the expanded name, the fullwidth dots. An index on a field that does not exist is created without complaint and used by nothing.
  • A comparison in q needs two indexes. A comparison matches any instance of the attribute (NGSI-LD: an instance with a datasetId counts too), each at a path of its own - speed.@none.value, speed.ds1.value. The broker asks MongoDB with an expression over all of them ($objectToArray), which no index answers, and puts two conditions in front of it that an index can answer: the term on the default instance (speed.@none.value), or the attribute marked as having a datasetId instance (speed.@datasetIds). With an index on each, a query reads the entities that match and the marked ones; with one of them, every entity of the type. Declare the attribute instead (--dbValueIndexes <its IRI>): the broker creates both, in every tenant, a tenant created later included. Served: == (a value, a range, a list), <, <=, >, >=, ~=; != and !~= read every entity of the type.
  • Every index costs every write that changes its field - one more structure to update.

PostgreSQL / TimescaleDB - the temporal history

With --troe timescale the history is in PostgreSQL - a database per tenant - and the Temporal API reads it. The broker creates the tables and the indexes its queries are built on (the table troe_schema_version records which schema version it has):

TableIndexes
troe_entities
one row per entity event		primary key (entity_id, modified_at, op); GIN on entity_type
troe_attrs
one row per attribute instance - a hypertable on modified_at when TimescaleDB is there		primary key (instance_id, modified_at); (entity_id, attr_name, observed_at); (entity_id, attr_name, modified_at); GIN on entity_type

Two more kinds are a choice:

  • For SQL sent to PostgreSQL directly - a dashboard, a report: --troeSqlIndexes attrObserved,geo,time, on (attr_name, observed_at), the GeoProperty values (GiST) and modified_at. The broker's own queries do not use them.
  • For a q on an attribute: --troeValueIndexes <its IRI>, two partial indexes of its values (v_number, v_text), in every tenant. A temporal query with a q term on it then takes its entities from the index.

An index made by hand in psql is found too: the broker reads pg_indexes, and uses CREATE INDEX ... ON troe_attrs (v_number) WHERE attr_name = '<attribute IRI>' (or v_text) for a q on that attribute within a minute. It lists it in GET /admin/troeIndexes, as made by "database".

Whether a query uses one: EXPLAIN (ANALYZE, BUFFERS) SELECT ... in psql - Index Scan or Bitmap Index Scan against Seq Scan, and the rows each step read. An index added by hand lasts, and is not in a tenant's database created later (a declared one is). On the hypertable CREATE INDEX CONCURRENTLY is not supported; TimescaleDB's CREATE INDEX ... WITH (timescaledb.transaction_per_chunk) builds it a chunk at a time, without holding the whole table.
