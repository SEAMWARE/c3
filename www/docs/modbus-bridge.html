The Modbus bridge

modbus.so carries values between the registers of a Modbus TCP device and entity attributes: registers polled in, attribute writes sent out. A PLC, an energy meter or a pump controller becomes an NGSI-LD entity - queryable, subscribable, with history.

Built: Modbus TCP; the address in the endpoint and how to read it in channelInfo; change-only reporting with a deadband; queued writes; modbusStatus on a device that stops answering. Not yet: contiguous registers read in one request, Modbus RTU (serial), a value read on demand through a registration, and a way back into the broker for a write's outcome - today it is logged only.

Modbus in short

  • A master polls, a slave answers. Nothing is pushed: a value changes inside the device and nobody knows until someone asks.
  • No names, no types. A device exposes four numbered tables. What a register means - "30001-30002 are the grid frequency, a 32-bit float, word order CDAB, in 0.01 Hz" - is only in the device's manual.
  • Modbus TCP listens on port 502. One TCP gateway often fronts many serial devices, told apart by the unit id.
  • Errors are exception responses (illegal function, illegal address, device busy), or silence - a timeout.

A server, a value, an attribute

One bridge is one Modbus server - host:port, a default unit, a poll interval. One channel is one value in it, tied to one attribute. The channel's endpoint is the value's address, and nothing else:

[unit/<n>/]coil|discrete|holding|input/<address>

holding/40001        unit/3/holding/40001        coil/12        input/30010

The address is 0-based, or the 1-based 1xxxx / 3xxxx / 4xxxx form of the device manuals, recognised by its range. How to read the value is the channel's channelInfo - key-value pairs, as NGSI-LD's receiverInfo; changing a scale factor does not make another channel:

KeyMeaningDefault
typebool, int16, uint16, int32, uint32, float32, float64bool for bits, uint16 for registers
orderword and byte order of a multi-register value: ABCD, CDAB, BADC, DCBAABCD
scale, offsetvalue = raw × scale + offset (inverted on a write)1, 0
pollthe poll period, msthe bridge's
deadbandreport only a change larger than this0 - any change

A mistake is not a default. Keys and values are strings. An unknown key, or a value that does not fit (a float32 coil), refuses the channel: it shows as dormant in GET /ngsi-ld/v1/channels, with the reason.

Configuration

The bridge's member of the --bridgeConfig file; ngsild.topics ties each endpoint to an attribute, as for every bridge:

{ "modbus": {
    "server": { "host": "10.0.0.5", "port": 502, "unit": 1, "pollMs": 1000, "timeoutMs": 500 },
    "ngsild": { "topics": {
      "holding/0": { "entityId": "urn:Meter:1", "entityType": "Meter", "attribute": "power",
                     "channelInfo": [ { "key": "type",  "value": "float32" },
                                      { "key": "order", "value": "CDAB" },
                                      { "key": "scale", "value": "0.1" } ] },
      "coil/3":    { "entityId": "urn:Meter:1", "entityType": "Meter", "attribute": "relay" }
    } } } }

How values move

In - pollingModbus pushes nothing, so the plugin polls: one thread per bridge, one request at a time. A value's time is the time its read completed - Modbus has no timestamps.
Change onlyA value is reported only when it differs from the last one reported, beyond its deadband. A poll that returns the same 21.5 every second for hours is no write at all - each report is an attribute write, subscription matching, notifications and a history row.
Out - writesA write of the attribute is encoded (inverse scale, type, order) and queued; the bridge's thread sends it, never the request that changed the attribute - a Modbus write is a network round trip. A coil takes true / false, a register a number; anything else is refused.
The device is goneOn a timeout or an exception the attribute keeps its last value - the last known one - and gets, once, when the state changes: "modbusStatus": { "type": "Property", "value": "timeout" } (or "illegalAddress", ...). Back to "ok" when a read succeeds again.

Building the plugin

The bridge is its own repository, corModbusBridge; the corLibs umbrella clones and builds it with the rest. It needs nothing beyond libc: Modbus TCP is a socket and a seven-byte header, and the client is the plugin's own.

make                  # modbus.so, debug (traces compiled in)
make BUILD=release
make install          # to /opt/seamware/plugins/bridge (PLUGIN_DIR)
make contract         # does it still satisfy BridgeDriver.h?

Tests and a demo

The functional test is in coraine, bridge_modbus.test, against a Modbus TCP simulator whose registers are set and read over HTTP (test/funcTests/tools/ftModbus.py): polling, change-only reporting, writes, exceptions and timeouts, deterministic.

A demo - an OpenPLC water tank on Modbus and an MQTT temperature sensor, one NGSI-LD entity, read and controlled over NGSI-LD - is DEMO.md in the bridge's repository.
