c³ - the coraine Control Center

c³ is one application for everything around a coraine broker: build it for a deployment, start and watch it, explore its entities as a graph and on a map, and read its documentation. A small backend in C serves the pages on this machine and does the work; the browser window is the interface.

The parts

The bar at the top has a page for each part:

  • Compilea broker built by coraine-build: the features compiled in or out, the optimisation, the HTTP server - its output followed live, the builds kept
  • Operatebrokers started and stopped, natively or in a container, with MongoDB, PostgreSQL/TimescaleDB and Mosquitto; their logs, configuration, metrics and log levels
  • Explorea live connection to a broker: entities as boxes, Relationships as arrows, the entities on a map - online or offline - and their values as they change
  • Dashboarddashboards built by the user from what the brokers hold: WireCloud, in containers c³ starts, shown in the page and logged in by c³
  • Documentationthese guides - searchable, offline - and every component, with its guide and its repository

The DDS, OPC UA and AAS mappings are in Operate's broker form. The AI Assist button in the header says what is planned; nothing of it is built.

Starting it

c³ builds against the Cor-Libs as coraine does - sibling checkouts, each built with make in it (COR_LIBS=<dir> for checkouts elsewhere). It needs gcc, make, OpenSSL (libssl-dev) and zlib (zlib1g-dev, for the map files), and a browser.

mkdir seamware && cd seamware
for r in corBase corLog corAlloc corArgs corTree corJson corHttp corRest c3; do
  git clone https://github.com/SEAMWARE/$r
done
for r in corBase corLog corAlloc corArgs corTree corJson corHttp corRest; do make -C $r; done
cd c3
make                  # ./c3
./c3                  # opens the application; Ctrl-C stops it

make install (PREFIX=/usr/local, DESTDIR for packaging) installs bin/c3 and share/c3/www; make run ARGS="--port 7901 --no-browser" builds and runs from the checkout.

A c³ started while one runs on its port opens that one in the browser and ends. When the running one is an earlier build of the same file - it was started from bin/c3, and an install replaced the file since - the new one stops it (SIGTERM, the port free within 10 s) and starts in its place, as a stop by hand would: the brokers and services it started keep running and the new one attaches to them, a build that runs is cancelled.

The window

  • Chrome or Chromium in $PATH (google-chrome, google-chrome-stable, chromium, chromium-browser; on macOS also in /Applications): an application window of its own, full-screen, with a profile of its own in $XDG_STATE_HOME/c3/chrome (~/.local/state/c3/chrome). Full-screen, its leave-full-screen (as F11), minimise and close buttons are in c³'s header; closing the window leaves c³ running.
  • Otherwise the default browser: xdg-open, open on macOS.
  • No screen (Linux, no $DISPLAY and no $WAYLAND_DISPLAY): the URL is printed, with the ssh -L line to reach it from another machine.

The backend answers this machine only: a connection from another address is a 403, and so is a request whose Host is not localhost, 127.0.0.1 or [::1]. From another machine: ssh -L 7900:localhost:7900 <host>. A second c3 on a port where one runs opens the running one and exits; any other program on the port is an error.

Every request c³ sends - to a broker, an OpenID provider, a verifier - goes through the environment's proxies (https_proxy, http_proxy, no_proxy); a broker on this machine wants no_proxy=127.0.0.1,localhost. A private CA's certificate: SSL_CERT_FILE.

Compile - a broker built for a deployment

A front-end to coraine-build: c³ builds nothing itself. Every build is the command the page shows, run by the backend - the same build as on the command line (Building from source).

  • Source - what coraine-build builds from: the coraine-dev package (the source of the release it installs) or Git clones, a directory holding coraine, c3 and the libraries side by side (~/git) - typed, or chosen with the folder button beside it: a browser of this machine's folders, the git clones marked, saying whether coraine is in the one open. For the clones, the repositories a build needs are listed - coraine's docker/vendor-libs.sh --list names them; of the bridges' repositories only those of the bridges switched on. Each has a Branch pull-down - what of it goes in: main (origin/main), the default, as last fetched; a branch of the clone; a branch at origin; or HEAD, what is checked out - its last commit, committed work only (the column's ? says so). The build passes them to coraine-build as --ref <repo>=<ref>, and the feature list is read at the same refs. Refresh, on the line above the list, fetches every clone from origin (git fetch --prune, in parallel) and lists the branches again - branches made since c³ started. Listed are the ones to look at - missing, another branch than main, a branch the clone does not have (Build waits), uncommitted changes on the branch taken, a clone elsewhere; Show all (+, the last icon) lists every one, Hide (−) in the same place goes back. A missing repository has Clone (into the directory - Clone the N missing for all), the git clone command to copy, and It is elsewhere for a clone at another path (it must hold .git; Forget this path undoes it). Build waits while one is missing, and says so. A bridge whose repository is not cloned can be switched on - Source then lists it. This card works when the rest of Compile is greyed: with no coraine clone, coraine is what it offers to clone first.
  • Features - from coraine-build --list-features --json, never a copy: each switch with its default and description; one changed from its default is marked, one whose requirements are off is greyed with what it needs. MONGOC and CORDB are the mongoc and corDB ticks under Server and databases.
  • Bridges - from coraine-build --list-bridges, each its own repository, its size beside it; dds is off by default (about 13 MiB, eProsima's Fast DDS and DDS Enabler). With dds on, Map DDS topics, services and actions asks, then opens Operate with the dds bridge ticked in its broker form and the DDS mapper open (below); its ← Back to Compile, or the Compile tab, comes back, the choice as it was. With opcua on, Map an OPC UA server does the same for the OPC UA mapper. With aas on, Map an AAS server opens Operate with the aas bridge ticked and the form's AAS part open, the cursor in the server's URL - its Discover the server picks the shells and submodels.
  • Optimisation - Release, Profile-guided (--pgo), Tuned for a workload (--tune <file>, the workload by its absolute path), Debug (traces compiled in) (Extreme performance).
  • Server and databases - three columns of tick boxes, each with what ticking it adds to the build and its ?. HTTP server: libmicrohttpd (the default), corHttp (--http-server builtin), or both (--http-server both: the broker carries both and chooses one at start with --httpServer, libmicrohttpd unless told) - both when coraine-build --list-http-servers --json lists it, otherwise ticking one unticks the other; one stays ticked; the training modes take libmicrohttpd alone. Current-state databases: corDB (the CORDB switch; always built by a source without it) and mongoc (the MONGOC switch), one of them at least - corDB's own history and the training modes need corDB. Temporal history: corDB and TimescaleDB - either, both, or none.
  • Executable - the broker's file name (--name, default coraine); Operate starts it by that name.
  • Output - the card under Source: Binary, or Binary and Docker image (--image; with docker or podman): the build on this distribution's base image (ubuntu:26.04 on Ubuntu 26.04), the packages of the libraries it links (the ones built from source copied), laid out as the published image - /usr/local/bin, /opt/seamware, its entry point and healthcheck. Docker image name names it, default localhost/<executable>:<build>. The image is kept in Docker on this machine, not as a file: docker images lists it, docker run <name> starts it, and a registry in front of the name (quay.io/...) is for docker push. 67 MiB with the default bridges (22 Nov 2026); a phase image after check. The result shows the image, its size and a docker run line. Save as a file (--image-file; from a source whose coraine-build has it) writes the image as image.tar.gz in the build's directory too (docker save, gzip; 66 MiB with the default bridges, 24 Nov 2026), a phase image-file - for a machine without a registry: docker load -i image.tar.gz there. The result shows the file, its size and that line.
  • The command - the exact argv for the choice, one option a line; only the switches that differ from their defaults are passed. Build starts it.
  • Following a build - its output line by line, and a bar over the phases coraine-build announces (build, install, bridges, check, done; tools and train for the training modes). Under the phases: the current one, how long it has run, the last line of output and what the phase does; nothing printed for 15 s says so, and the bar turns striped (still working) when the phase outruns its estimate. train holds the instrumented build, the training and the rebuild with the profile - 13 minutes on a laptop, a line per scenario. Build scrolls to the panel; while a build runs, a line under Build names it, its phase and its time, and brings the panel back into view. Cancel: SIGTERM to the build's process group, SIGKILL 5 s later. One build at a time; no make, gcc or training broker outlives a build, nor c³.
  • The result - the size of install/ and of the broker, its --version with the features as the built broker reports them, the directory, the whole log. Run it opens Operate with that build. A build followed on the page ends with a popup, done or failed; its Start it opens Operate with the build chosen - its image when it made one.
  • Builds kept (newest first, a click opens one, Delete removes it) and presets - a choice saved under a name. Both cards are closed when c³ starts, their number on the header; a click on it opens one.

Operate - brokers and their services

The page shows one thing at a time:

  • Set up a broker, a tile at the top, and under it Running - the brokers c³ started that run, start, stop or failed, the one Explore is connected to first (also one c³ did not start, while it answers), and a service still running that no broker uses; No broker runs when there is none. The list follows the brokers: one just started is in it, one stopped leaves it. Each running broker's row has Stop and Explore; a click elsewhere on a row opens its card. Explore and a broker's URL open it in Explore once it answers its probe. A broker stopped by hand is not listed: its settings are under Set up a broker, Earlier settings.
  • A broker's card - its state, what it runs from, where its data is, its health; Stop, Explore, Options (its options in the form, where its OPC UA server is browsed); the services it uses, each one's Log opening that service's card; Configuration and build, Metrics, Log and trace levels; its log. ← goes back.
  • Set up a broker, step 1, what runs: Earlier settings (a broker started before - its options fill the form; Forget), Compile's Builds (the newest first, the latest marked), the Installed coraine, the Docker images (those here, then the newest published; + lists them all; another tag typed). Step 2: the form, and beside it the services the start brings up, the command and Start; Change goes back to step 1. Started, the broker's card opens.

The current state DB - corDB (on disk: a directory chosen with a folder picker, or c³'s own; a container's volume), ramDB (in memory only) or mongoc; Forget and delete data never deletes a directory chosen - the history DB (--troe none, corDB or timescale), the port and health port, the grace period (seconds from SIGTERM to SIGKILL), the WebSocket transport, the admin API, distributed operations, -v.
  • Bridges - every bridge c³ knows, those the broker lacks greyed with the reason; CKAN, OPC UA, AAS and the mappers' buttons show only with their bridge ticked. Without a bridge configuration file of one's own, c³ writes it: c³'s Mosquitto for mqtt, the DDS domain and mapping, the CKAN datasets ticked, an OPC UA server and its channels, an AAS server and its AssetChannels.
  • Map DDS topics, services and actions (the DDS mapper), Map an OPC UA server (the OPC UA mapper) and Map an AAS server, each with its bridge ticked. A container broker with the dds bridge runs on the host's network and IPC namespace (--network host --ipc host) - DDS discovery is UDP multicast, which the network c3 keeps to its own containers - so its port is the host's and, like a native broker's, open on every interface.
  • Options - every other option of the broker, read from its own usage (-u, -U) with the databases chosen: a tick, a choice or a value (the default greyed), and a ? in coraine's words. Those c³ sets itself show what it sets; those that are c³'s (--daemon, --logTo, --logDir) are not offered.
  • More options - anything else, as typed.
  • The form offers what the broker has, from its own --version, run as a start runs it (its own plugin directory): what is compiled out (features:) and what its plugin directory lacks (plugins: db=... troe=... api=... auth=... bridges=... transports=...) is greyed with the reason - a store, a history, the WebSocket transport, the admin API; the bridges are that list's (loopback, the test bridge, never), and the CKAN, OPC UA and AAS parts and the mappers show only with their bridge. An image's --version is read once per image (docker run --rm --entrypoint coraine <image> --version); one not here is known after its start pulls it. The start refuses what the form leaves out, too.
  • Beside the form: the services it starts first, and the command, exactly as it will run.

Services are containers of c³'s own, one of each kind shared by every broker c³ starts (c3-mongoc-timescale-mongo, c3-mongoc-timescale-timescale, c3-mqtt-mosquitto), each with a volume, on the network c3, published on 127.0.0.1 on the service's port + 10000 (MongoDB 37017, PostgreSQL 15432, Mosquitto 11883 - the next free one when that is taken). Each broker has its own database in them (--dbName c3_<name>, --troeName c3_<name>_h). They start before the broker that needs them, waited for until they answer, and stop when nothing c³ started uses them; their volume stays until Delete data - beside the service in Set up a broker's step 2, while it does not run. c³ creates only c3-* containers and volumes and the network c3, all labelled c3=run, and touches nothing else.

Starting and stopping. A started broker joins Explore's list (http://localhost:<port>). A native broker runs in a session of its own, its output appended to its log; it does not need c³ - when c³ stops, the brokers keep running, and the next c³ attaches to them (by pid and the process's start time). Stop sends SIGTERM - corDB syncs its log and writes its snapshots - and SIGKILL when the grace period is over; a container: docker stop -t <grace>, then docker rm.

What a running broker shows, every 2 s its status (GET /ready on its health port, else GET /version) and, with the admin API:

  • The log, live (server-sent events), the run before kept as broker.log.1.
  • Configuration and build - what it is built with (GET /build) and every option it runs with, where each came from (GET /admin/config), a secret masked by the broker.
  • Metrics - /admin/metrics as charts over the last 10 minutes, read every 5 s: requests per second, errors, latency (mean and 95th percentile), notifications, subscriptions, memory; the busiest operations (Administration).
  • Log and trace levels - verbose and info, and a tick box per trace level, grouped by library, its tooltip what it traces - set live through /admin/log. Traces exist in debug builds only; on a release build the tick boxes are greyed.

The DDS mapper

Operate's page, given to the mapping of a DDS domain to NGSI-LD: each topic, service or action mapped is one attribute of an entity. Mapping once is the usual case: what was written is read back when c³ opens, and the mapper opens on it.

  • How c³ reaches your DDS system - domain (ROS 2: ROS_DOMAIN_ID), transport (shared memory and UDP - DDS's default; UDP only; shared memory only) and interfaces - the IPv4 addresses of this host's interfaces UDP is kept to, comma-separated; empty: all of them; none with shared memory only. Written into the bridge configuration as dds.ddsmodule.dds domain, transport and whitelist-interfaces; Discover's broker and the broker Done starts use them alike. DDS discovery reaches this host and its network segment, not across a router, a VPN or a NAT; shared memory reaches this host alone, and a container only when it shares the host's /dev/shm. A ROS 2 Discovery Server, unicast peers and Fast DDS XML profiles cannot be given: the DDS Enabler's participant reads none of them. Where c³ does not reach the system, Import inventory.json.
  • A vocabulary - the namespace of the terms (each entity type and attribute <vocabulary><term>); empty: the default context's. proposals' type - the entity type the proposals give (Robot).
  • Discover asks the DDS system what it announces: c³ joins its domain from the machine it runs on, so it must reach it - DDS discovery is multicast, on that host or its network. It starts a broker of c³'s own on the domain, transport and interfaces (the form's: the installed one, a build or the image, the dds bridge alone, in memory), asks its bridge once what was announced - it answers when discovery has been quiet for 3 s, at most 10 s - and stops it: a few seconds. Import inventory.json reads the list a DDS discovery tool wrote. show ROS 2 housekeeping - its discovery and log topics, every node's parameter services - hidden otherwise.
  • Three lines - N DDS Topics, N DDS Services, N DDS Actions, each with ▸ to open it and the number mapped. Open, a line an endpoint: its name, its type, and, mapped, its attribute and entity. An endpoint mapped and not in the last discovery is listed too.
  • The proposals - an endpoint not mapped shows, greyed, its proposal: the name's last segment camelCased the attribute, the segments before it the entity (rt/turtle1/pose: pose of urn:ngsi-ld:Robot:turtle1; no segment: urn:ngsi-ld:Robot:robot1), the proposals' type the entity's - once, an entity with a type keeps it. The green ✓ accepts it, into the fields still empty; ✓ all (N) on a group accepts those of every endpoint shown and not mapped. Each name stays editable.
  • An endpoint opened - Attribute name, Entity ID, Entity type (optional), the ids and types already used offered as you type. The first field typed in names the attribute from the endpoint (its last segment camelCased: rt/turtle1/cmd_vel, cmdVel). the topic's payload (a service's request and reply, an action's goal, feedback and result) shows a sample of its DDS type - the value of the attribute it is mapped to; not mapped takes the endpoint out.
  • An entity's type, once - an entity is created with its type, so every entity id needs one, on at least one of its endpoints; the others take it. Under an endpoint, what Done refuses: no attribute or entity id, an id that is not a URI, an entity with no type anywhere, two types for one entity, a name with a character NGSI-LD forbids (space < > " ' = ; ( )), id, type or another member of every entity as an attribute, two endpoints on one attribute of an entity.
  • Done writes the DDS configuration (POST /api/run/dds/files) into ~/.local/share/c3/dds/ ($XDG_DATA_HOME/c3/dds/): dds-bridge.json, the bridge configuration (--bridgeConfig), and dds-context.jsonld, the @context (--defaultUserContext); with them dds-mapping.json, the mapping as the mapper reads it back, and dds-types/, the bridge's type files.
  • The files screen - the two files' full paths, each with Copy; Set up a broker with it: the broker of Set up a broker's form with the dds bridge and the two files, the command shown, More options added as typed. Start the broker starts it and closes the mapper; Put it in the broker form fills the form only, to change more before Start. Edit the mapping goes back to it.
  • Escape, × or Close closes the mapper, the brokers in view again.

The OPC UA mapper

Operate's page, given to the mapping of an OPC UA server to NGSI-LD - the DDS mapper's layout and ways, a tree of the server's nodes in place of three lists. A Variable mapped is one attribute of an entity (a Channel); an Object mapped is a model (an AssetChannel): the Object and every Object in it entities. What was written is read back when c³ opens, and the mapper opens on it.

  • How c³ reaches your OPC UA server - its URL (opc.tcp://host:port), the security mode and, secured, the policy, the client's certificate, private key and application URI, the server certificates to trust or "trust any"; a username and password, empty: anonymous. The first time, the broker form's server fills them. The password is sent once: c³ keeps it in its data directory (mode 600) and the bridge configuration names that file; it is in no file you share. Discover's broker and the broker Done starts use them alike.
  • A vocabulary and proposals' type - as the DDS mapper's; the proposals' type is given an Object whose TypeDefinition says nothing (BaseObjectType).
  • Discover reads the server's address space: a broker of c³'s own - native, the image has no opcua bridge - with the opcua bridge alone connects to the server, c³ reads its bridge's inventory five levels at a time until it has it all (namespace 0 left out, at most 20 000 nodes) and stops it: a few seconds. Import inventory.json reads the same tree from a file - c³'s, or the inventory a broker's bridge answers (/admin/bridges/opcua/inventory?depth=5). show the server's own nodes - namespace 0: the Server object, its diagnostics, aliases, locations - hidden otherwise.
  • The tree - the Objects folder's content: ▸ opens a node, its name opens its fields. A Variable shows its DataType, unit and whether it can be written; an Object its TypeDefinition.
  • A Variable - its proposal greyed: the entity the nearest Object above it, named as an AssetChannel on its Objects would name it (urn:ngsi-ld:PressType:Press17), the attribute its path from that Object camelCased (hydraulicsPressure; a leading acronym lowered whole: ioDataStatus), so that both write the same entity. ✓ accepts it; opened: Attribute name, Entity ID, Entity type (once per entity), its value as discovered, not mapped. A write of the attribute writes the Variable when the server lets it be written.
  • An Object - ✓ maps it as a model; the line says how many entities and attributes it makes. Opened: Containers - what a folder becomes in the entity above it: an attribute per Variable, one attribute with sub-attributes, or one JsonProperty; Direction - values in, or both; what it makes - the entities and the attribute names; ✓ its Variables (N) - each Variable in it a Channel as proposed, instead of the model. A node inside a model says so.
  • A method - shown, not mapped: a method is a service of its entity, a Service Registration with the endpoint opcua://<Object NodeId>/<method NodeId>.
  • Done - refused, the node saying why, for what the DDS mapper refuses, and for a server without its URL, a security mode without its files, a user without a password. It writes opcua-bridge.json (--bridgeConfig), opcua-context.jsonld (--defaultUserContext) and opcua-mapping.json, the mapping the mapper reads back, into ~/.local/share/c3/opcua/ ($XDG_DATA_HOME/c3/opcua/).
  • The files screen - as the DDS mapper's: Start the broker or Put it in the broker form - a native broker with the opcua bridge and the two files; the form's own OPC UA server and Channels are emptied, the server is in the file.

AAS - an Asset Administration Shell server

The broker form's AAS: the aas bridge (corAasBridge, a prototype - coraine-build --bridges aas; native brokers, the image has no aas bridge) reads an AAS server's shells and submodels over the AAS HTTP API (IDTA Part 2, V3) and the broker makes each one picked a graph of entities - an AssetChannel (coraine's AAS and AssetChannels).

  • The server - its URL (http[s]://host:port[/base path], /api/v3.0 on some servers); the Authorization header (Bearer ...), sent once: c³ keeps it in the broker's directory (mode 600) and hands it to the broker in its environment (C3_AAS_AUTHORIZATION, the bridge's authorizationEnv) - never in c3.json or the bridge configuration; the CAs the server's certificate is verified against (a PEM file; none: the system's), or do not verify.
  • Discover the server - a broker of c³'s own, the aas bridge alone, reads the server: its shells, its submodels and each one's model, whole (/admin/bridges/aas/inventory, then ?from=<id> per shell and per submodel no shell refers to - at most 200), and stops: a few seconds. The Authorization typed, else the one c³ keeps for the broker, goes with it.
  • The list - each shell (and each submodel of no shell) with what it makes: the entities an AssetChannel on it makes, their types and ids - the shell's and a submodel's own id (an IRI), else urn:ngsi-ld:<type>:<the names from the shell>. ▸ opens its model as the bridge hands it to the broker: submodels, collections, Properties with their values, semanticIds, Operations with their inputs. + AssetChannel adds it to the broker form.
  • An AssetChannel - the shell's or submodel's id, and:
    • entities - the shell and each submodel ("natural": the shell an entity of type Shell, each submodel one of its idShort, the shell's submodels Relationships), or by rules: a node kind (shell, submodel, collection), a semanticId it must have (none: any) and the entity type; the first rule a node matches names its type, a node no rule matches goes into the entity above it. Switched to rules, the rules start as what natural makes: the shell, each submodel by its semanticId, a catch-all for the others. + entity rule on a submodel or collection of the model adds one for it, before its kind's catch-all - a collection without a semanticId makes every collection an entity, as the button says.
    • a collection that is no entity - an attribute per element (attributes), one attribute with its elements as sub-attributes (subAttributes), or one JSON attribute (value).
    • direction - read from the server, or also a client's write to the server first (channelDirection both: PATCH .../$value; refused, the broker stores nothing).
    • read every - the poll interval, an ISO 8601 duration (PT2S); none: 10 s.
  • Start - c³ writes the aas member of the broker's bridges.json: the server, and an assetChannels entry per AssetChannel. GET /ngsi-ld/v1/assetChannels of the broker says how each one does - dormant with why (a 401: the Authorization) or available, the entities written.
  • Not yet: an Operation is a service of its entity only through a Service Registration of one's own (endpoint aas+http://.../submodels/<id>/submodel-elements/<path>, corAasBridge's README); c³ makes none.

Explore - the graph and the map

A broker's URL and Connect. The next start connects to the last broker by itself, with the types picked last time. The examples in c³'s repository fill a broker to try it on:

coraine -db corDB -p 1090 --transports ws &            # a broker in RAM, with its WebSocket transport
examples/factory.sh http://localhost:1090              # 25 entities: Relationships, locations, areas, routes

Connecting

  • The tenant - the field beside the URL (NGSILD-Tenant; empty, the default one), kept per broker, offered again with those used before and, from coraine with its admin API, GET /admin/tenants.
  • Local only - every query with local=true: the broker's own entities, without those of its Context Source Registrations.
  • The access token (Token) - sent as Authorization: Bearer on every request, over HTTP and in each message on the broker's WebSocket. In this order: a login to the broker's OpenID provider (the authorization code flow with PKCE, a public client that allows http://<c³>/api/oidc/callback); a credential login for a Data Space Connector - a Verifiable Credential obtained from the consumer's Keycloak (OID4VCI), presented to the verifier, its access token sent; a token typed in (with Remember it on this machine); --token-file; $C3_TOKEN. Tokens stay in the backend - never in the page, never in c3.json; a login's tokens are in memory only and renewed before they expire. A 401 shows the broker's reason, and Log in… when the broker says where its tokens come from (coraine's /.well-known/oauth-protected-resource) (Authorization).
  • Headers of its own (Token, below the token) - up to 16 per broker, each a name, a value and secret: an API key, a Basic Authorization, what a gateway in front of the broker asks for. Sent as they are with every request to that broker - the proxy's reads and writes, the live values' HTTP requests, the WebSocket's upgrade request and each message's metadata. An Authorization among them takes the place of the token. In memory, and with Remember them on this machine in secrets.json; a secret header's value never reaches the page (its last four characters, or its length, do), and saved with its field empty it keeps its value. The headers c³ sets itself are refused (Host, Content-Type, Accept, NGSILD-Tenant, X-C3-Broker, the WebSocket's, ...).
  • Discovery - before any entity is loaded: GET /types?details=true, GET /types/{type} per type (its count and its attributes' kinds), GET /attributes?details=true. The panel lists the types with their counts, each one's attributes, and the Relationships between types.
  • Choosing what to see - Load loads the types ticked (GET /entities?type=A,B, every page, up to 2000 entities; past that a notice says how many there are). A broker of 300 entities or fewer is loaded whole on a first connect.

The browser never talks to a broker: the backend proxies each request, so the broker needs no CORS. The proxy forwards the NGSI-LD API, /version, /build and coraine's admin reads; its writes are the entities and PUT /admin/log only, and only from c³'s own page.

The graph

  • An entity is a box (its type, the end of its id, its first two Properties); a Relationship to another loaded entity is an arrow. A type's colour comes from its place in the broker's sorted list of types - the same broker, the same colours.
  • The layout is deterministic: the same entities and Relationships give the same picture, whatever order the broker sent them in. Every arrow points up; entities with no Relationship go in a grid below.
  • The wheel zooms, a drag moves the view or a box; Fit and 0 show everything.
  • A click shows an entity's attributes - kinds, values, unitCode, observedAt, datasetId, sub-attributes - and its JSON; a Relationship's target is a link.
  • An entity's menu (right-click, or Shift+F10): With linked entities (join=inline&joinLevel=1, 2, 3: one box holding the entities its Relationships point to), Neighbourhood (the entities one Relationship away, out or in), Follow, Hide type, Copy id, Show JSON, Edit…, Replace… (PUT), Delete entity….
  • The editor - the entity as rows, an input per attribute kind (a value with its JSON type, a Relationship's target - or pick in graph -, a Point's coordinates - or pick on map -, a LanguageProperty's languages, ...), sub-attributes, instances by datasetId. Save as says how an edit is sent: a merge (PATCH /entities/{id}, the default, "urn:ngsi-ld:null" for what was deleted), update attributes (PATCH /entities/{id}/attrs, each new or changed instance whole, a deletion as "urn:ngsi-ld:null"), append attributes (POST /entities/{id}/attrs, with or without ?options=noOverwrite - no deletions: they are left out, and counted) or a partial attribute update (PATCH /entities/{id}/attrs/{attrId}, one per changed instance - its changed members, a deleted sub-attribute as "urn:ngsi-ld:null"; a new or deleted attribute or instance left out). The request at the bottom shows what Save sends. A right-click where there is no entity creates one (POST /entities). The broker's errors - a 401, a 403, a 400's detail, a 207's attributes not updated - show in the editor.

The map

Graph / Map switches the view, kept per broker. On the map, every loaded entity with a GeoProperty (location first, then any other): a Point as a marker, a LineString as a line, a Polygon as an area, in the type's colour; Relationships as lines with an arrowhead at the target - all, or the selected entity's only.

  • Colour by type, or a Relationship (inDistrict →): each target and the entities pointing at it in one colour, with a legend.
  • Icons for the kinds c³ knows by their type's name - a bus, a stop, a streetlight, an air quality or weather station, a traffic sensor, a person - coloured by state (a broken status red, an airQualityLevel on its scale, a powerState); any other type a dot.
  • Movement - a Point a live change moves glides to its new place, its lines following (not with prefers-reduced-motion).
  • A right-click opens the entity's menu, with Show in the graph; Create entity here… where there is none.

The base map is OpenStreetMap data drawn with MapLibre GL JS in c³'s dark style: online, OpenFreeMap's vector tiles; offline, the areas downloaded.

Offline map areas

Download this area, on the map's bar:

  1. The size first - the area in view, the level of detail (10, 12, 13, 14 or 15; each level adds about four times the tiles) and its size, exact before anything is downloaded: the backend reads the planet's directories for the tiles of that box. An area of more than 1 000 000 tiles is refused.
  2. The extract - the backend extracts the tiles from the newest Protomaps planet build (read with HTTP Range requests, never downloaded whole) into one PMTiles file, $XDG_DATA_HOME/c3/maps/<id>.pmtiles; the first time, the label fonts too. Progress and Cancel; one download at a time.
  3. Drawn from the file - inside the area, down to its level, also with no network.
  4. The list - each area's name, size, level, date and planet build, Show and Delete.

Offline means the downloaded areas: outside them the map is empty. Making an area needs the network once.

Live values

When an attribute of a loaded entity changes in the broker, its box and its marker change, the rows that changed marked; an entity created appears, one deleted disappears; nothing is reloaded. Live · WebSocket or Live · HTTP says how the changes arrive:

  • The broker's WebSocket transport (coraine --transports ws, WebSocket) - tried first: the backend opens /ngsi-ld/v1/ws, creates one subscription over it, and the notifications come back on the same socket. The broker deletes the subscription when the socket closes, also when c³ is killed.
  • An HTTP subscription notifying the backend (http://127.0.0.1:<port>/api/notify/<session>) - any NGSI-LD broker that can reach it. A subscription left by a c³ that was killed is deleted by the next start on that port.

The subscription (named c3-live:<port>) watches the types loaded, every attribute and every kind of change; it is replaced when the picks change and deleted when the page closes. The changes are applied every 250 ms; when the broker goes away, the page watches again until it is back.

  • Alarms - alert rules per broker: a title, a severity, an entity type and a q, each a subscription of its own. A match raises an alarm - a toast, a row, the entity ringed on the map until acknowledged - cleared when the live values no longer match (for the simple forms of q; otherwise by hand).
  • History - each numeric Property of the selected entity over the last 10 minutes as a sparkline, from the temporal API (GET /temporal/entities/{id}?timerel=after...), then grown from the live values. A broker without history shows the live values from the moment the entity was selected.
  • Named demos - a name instead of a URL (CDMAD, built in; others under demos in c3.json): c³ fetches the demo's descriptor - its broker, tenant, view, the types to load, its alert rules - and connects.

They are on the network c3 and labelled c3=run, as Operate's services, and Operate lists them too, where their logs are and where a stopped one's data is deleted.

The first start - when c³ cannot log in to WireCloud as admin - also runs, in WireCloud's container:

python -m manage populateinstalls WireCloud's own widgets and operators

Every start runs python -m manage rebuildsearchindexes when Elasticsearch has no workspaces index - populate does not make the search indexes, and without them WireCloud's search answers 500.

Logged in by c³ - once WireCloud runs, the page asks c³ to log in (POST /api/run/dashboard/login): c³ logs in to WireCloud as admin and sets WireCloud's session cookies (token, csrf_token, token_expiration) on its own answer. A browser keeps a cookie per host, not per port, so the cookies reach WireCloud on its port of the same host, and the page shows WireCloud in a frame, logged in. The frame is on the host the page was loaded from: localhost and 127.0.0.1 are two sites, and a cookie of one does not go to the other. Open in a tab opens WireCloud on its own, Reload logs in again.

Its secrets - the password of admin and WireCloud's WIRECLOUD_JWT_KEY and WIRECLOUD_SECRET_KEY - are made by c³ at the first start and kept in secrets.json (dashboard). The keys go to WireCloud's container through an env file (mode 600) removed once the container is made. None of them is sent to the page.

c³'s widgets

c³ comes with WireCloud widgets of its own (www/widgets/, vendor Seamware). Every start installs each one WireCloud does not have at its version: c³ zips the widget's directory into a .wgt and uploads it as admin. In WireCloud, add them to a workspace from Add widget and connect them in Wiring.

Source → table → value: the table lists the entities, the value shows the one clicked, and follows its value as the source reads again. Source → chart draws all of them over time; table (or map) → chart draws the one clicked - the selection carries the source's broker and tenant, so the chart reads its history there. The chart's history needs a broker that keeps it (TRoE); without one it draws what it receives from then on.

The map is c³'s own (the same base map as Explore): c³ packs maplibre and its base map into the widget (the widget's file c3-include names them), and the widget reads the areas downloaded in c³, and their fonts, from c³.

Through c³ - the widgets reach the brokers through c³'s proxy, as Explore does: c³ adds each broker's token, headers and tenant, so only the brokers c³ knows. c³ answers CORS for WireCloud's origin only (http://localhost:<port> or http://127.0.0.1:<port> while WireCloud runs), on the NGSI-LD API through the proxy, the list of brokers and the downloaded map areas (their list, the .pmtiles by Range, the fonts) for GET; and for POST, PATCH and DELETE on the entities (/ngsi-ld/v1/entities and below) only, while the switch Widgets may write in the Dashboard's bar is on - it is by default. Anything else - a subscription, /admin, a write with the switch off - is refused (403). Every write a widget makes is a line in the Dashboard's log. The widgets find c³'s port in the cookie c3_port, set with WireCloud's when c³ logs in.

In c³'s language - WireCloud and the widgets show the language chosen in c³, whatever the browser's: c³ opens WireCloud with ?lang= and sets the cookie lang, which WireCloud reads on every request.

When c³ cannot log in to WireCloud - WireCloud's user admin has a password that c³ made and keeps. If the Dashboard's data was made by another c³, or the password was changed by hand, c³'s login fails and the start stops with that message. Reset admin's password, beside the message, gives admin c³'s password again; the workspaces and everything else are kept, and the Dashboard starts again.

In c³'s colours - WireCloud runs with c³'s own theme (www/wirecloud/c3theme, built on WireCloud's default theme), and the widgets use c³'s colours too. To change the look, edit the theme's static/css/_variables.scss (c³'s palette on WireCloud's variables) or static/css/c3.scss (rules of its own), compile them with tools/wirecloud-theme.sh (it uses WireCloud's own build: a WireCloud checkout with its npm packages), and Stop and Start the Dashboard.

WireCloud's image

WireCloud 2 has no published image yet (Ficodes/WireCloud#7); c³ uses wirecloud-fastapi:latest, the name WireCloud's docker/docker-compose.yml builds:

git clone https://github.com/Ficodes/WireCloud
cd WireCloud
docker compose -f docker/docker-compose.yml build --build-arg WIRECLOUD_INSTALL_MCP=true wirecloud

The build-arg adds WireCloud's MCP server: c³ then starts WireCloud with it, and with one OAuth client of its own (c3-assist: acting as admin, to read, change workspaces and install widgets - it deletes nothing), its secret made by c³ and kept beside the Dashboard's other secrets. Built without it, WireCloud runs the same, without the MCP server. A WireCloud started before the image had it: Stop, then Start.

At v2.0.0 the build needs the Elasticsearch client pinned to the server's major version (elasticsearch>=8,<9 in requirements.txt and pyproject.toml, #5) and createsuperuser fixed (#6). Without the image, Start says so and starts nothing.

How it is built

The backend is one C binary, c3, on coraine's own libraries: corHttp (the HTTP server - the pages, the API, the page's WebSocket, files and server-sent event streams), corRest (the HTTP client of the proxy and the map downloads), corJson and corTree (the configuration and the API's bodies), corArgs (the command line), and corAlloc, corBase, corLog under them; zlib and OpenSSL. A proxied request leaves the event loop and is sent on a thread of its own: a slow or absent broker holds up nothing else (timeout 15 s, the largest answer 64 MiB).

The frontend is plain JavaScript modules, HTML and CSS - no build step, no framework, nothing from a CDN. The map's libraries (MapLibre GL JS, pmtiles, @protomaps/basemaps) are copied as published into www/vendor/, each with its licence.
