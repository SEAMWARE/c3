c³ - the coraine Control Center

One application for everything around a coraine broker: build it for a deployment, start and watch it, explore its entities as a graph and on a map, and read its documentation. A small backend in C serves the pages on this machine and does the work; the browser window is the interface.

The parts

The bar at the top has a page for each part:

  • Compilea broker built by coraine-build: the features compiled in or out, the optimisation, the HTTP server - its output followed live, the builds kept
  • Operatebrokers started and stopped, natively or in a container, with MongoDB, PostgreSQL/TimescaleDB and Mosquitto; their logs, configuration, metrics and log levels
  • Explorea live connection to a broker: entities as boxes, Relationships as arrows, the entities on a map - online or offline - and their values as they change
  • Documentationthese guides - searchable, offline - and every component, with its guide and its repository

The DDS and OPC UA mappings are in Operate's broker form. The AI Assist button in the header says what is planned; nothing of it is built.

Starting it

c³ builds against the Cor-Libs as coraine does - sibling checkouts, each built with make in it (COR_LIBS=<dir> for checkouts elsewhere). It needs gcc, make, OpenSSL (libssl-dev) and zlib (zlib1g-dev, for the map files), and a browser.

mkdir seamware && cd seamware
for r in corBase corLog corAlloc corArgs corTree corJson corHttp corRest c3; do
  git clone https://github.com/SEAMWARE/$r
done
for r in corBase corLog corAlloc corArgs corTree corJson corHttp corRest; do make -C $r; done
cd c3
make                  # ./c3
./c3                  # opens the application; Ctrl-C stops it

make install (PREFIX=/usr/local, DESTDIR for packaging) installs bin/c3 and share/c3/www; make run ARGS="--port 7901 --no-browser" builds and runs from the checkout.

The window

  • Chrome or Chromium in $PATH (google-chrome, google-chrome-stable, chromium, chromium-browser; on macOS also in /Applications): an application window of its own, full-screen, with a profile of its own in $XDG_STATE_HOME/c3/chrome (~/.local/state/c3/chrome). Its minimise and close buttons are in c³'s header; closing the window leaves c³ running.
  • Otherwise the default browser: xdg-open, open on macOS.
  • No screen (Linux, no $DISPLAY and no $WAYLAND_DISPLAY): the URL is printed, with the ssh -L line to reach it from another machine.

The backend answers this machine only: a connection from another address is a 403, and so is a request whose Host is not localhost, 127.0.0.1 or [::1]. From another machine: ssh -L 7900:localhost:7900 <host>. A second c3 on a port where one runs opens the running one and exits; any other program on the port is an error.

Every request c³ sends - to a broker, an OpenID provider, a verifier - goes through the environment's proxies (https_proxy, http_proxy, no_proxy); a broker on this machine wants no_proxy=127.0.0.1,localhost. A private CA's certificate: SSL_CERT_FILE.

Compile - a broker built for a deployment

A front-end to coraine-build: c³ builds nothing itself. Every build is the command the page shows, run by the backend - the same build as on the command line (Building from source).

  • Features - from coraine-build --list-features --json, never a copy: each switch with its default and description; one changed from its default is marked, one whose requirements are off is greyed with what it needs. MONGOC is the Stores choice (corDB only, or corDB + mongoc).
  • Optimisation - Release, Profile-guided (--pgo), Tuned for a workload (--tune <file>, the workload by its absolute path), Debug (traces compiled in) (Extreme performance).
  • HTTP server - libmicrohttpd (the default) or coraine's own (--http-server builtin; not with the training modes).
  • Executable - the broker's file name (--name, default coraine); Operate starts it by that name.
  • Target - shown greyed: coraine-build builds for the host.
  • The command - the exact argv for the choice, one option a line; only the switches that differ from their defaults are passed. Build starts it.
  • Following a build - its output line by line, and a bar over the phases coraine-build announces (build, install, bridges, check, done; tools and train for the training modes). Cancel: SIGTERM to the build's process group, SIGKILL 5 s later. One build at a time; no make, gcc or training broker outlives a build, nor c³.
  • The result - the size of install/ and of the broker, its --version with the features as the built broker reports them, the directory, the whole log. Run it opens Operate with that build.
  • Builds kept (newest first, a click opens one, Delete removes it) and presets - a choice saved under a name.

Brokers started and stopped on this machine, from:

The form - one of three sets, then each option as wanted:

  • The store and its keep it on disk (--dbDir), the history (--troe none, corDB or timescale), the port and health port, the grace period (seconds from SIGTERM to SIGKILL), the WebSocket transport, the admin API, distributed operations, -v.
  • Bridges - those the broker has (the bridge/*.so of its plugin directory) and a bridge configuration file; without one, c³ writes it: the set's Mosquitto for mqtt, the DDS domain and mapping, the CKAN datasets ticked, an OPC UA server and its channels (native brokers).
  • DDS (the dds bridge ticked) - the domain, a vocabulary, and the mapping: a topic, a service or an action a row, one attribute of an entity, its whole sample the value. With a vocabulary, c³ writes dds-context.jsonld - each entity type and attribute a term in it - and starts the broker with --defaultUserContext. Discover starts a broker of c³'s own on the domain (the installed one, a build or the image, the dds bridge alone, in memory), asks its bridge once what was announced - it answers when discovery has been quiet for 3 s, at most 10 s - and stops it: a few seconds. The list hides ROS 2's housekeeping unless asked; each endpoint shows its type and its fields, and + map adds a row named from the endpoint, every name editable. Discovering again keeps the rows and marks those not seen. Import inventory.json reads the list a DDS discovery tool wrote. Open the DDS mapper gives the mapping the whole window, in three columns. Announced: the topics, services and actions, a filter by name, each one's type and fields, and beside each its entity - picked from the list (or a new one), or the endpoint dragged onto an entity. Map topics by their names maps every topic shown and not mapped the way + map does (rt/turtle1/pose: entity urn:ngsi-ld:<type>:turtle1, attribute pose). Entities: each entity's type and id, and its attributes, each name typed, each one moved to another entity or unmapped; + Entity makes one of the type typed beside it. Under an entity, what the broker would refuse or do otherwise: an id that is not a URI, two entities with one id, a name with a character NGSI-LD forbids, id or type as an attribute, two endpoints on one attribute. The third column: the entities as the broker makes them (a topic's attribute with a sample of its type), the @context c³ writes with a vocabulary, and the configuration's dds.ngsild. The form's rows, summary and command follow every change; Escape or Done closes the mapper. A container broker with the dds bridge runs on the host's network and IPC namespace (--network host --ipc host) - DDS discovery is UDP multicast, which the network c3 keeps to its own containers - so its port is the host's and, like a native broker's, open on every interface.
  • More options - anything else, as typed. What the broker is built without is greyed with the reason, from its --version.
  • The command, exactly as it will run, and the services it starts first.

Services are containers of c³'s own, c3-<set>-<service>, shared by the brokers of the set, each with a volume, on the network c3, published on 127.0.0.1 on the service's port + 10000 (MongoDB 37017, PostgreSQL 15432, Mosquitto 11883 - the next free one when that is taken). Each broker has its own database in them (--dbName c3_<name>, --troeName c3_<name>_h). They start before the broker that needs them, waited for until they answer, and stop when nothing c³ started uses them; their volume stays until Delete data. c³ creates only c3-* containers and volumes and the network c3, all labelled c3=run, and touches nothing else.

Starting and stopping. A started broker joins Explore's list (http://localhost:<port>). A native broker runs in a session of its own, its output appended to its log; it does not need c³ - when c³ stops, the brokers keep running, and the next c³ attaches to them (by pid and the process's start time). Stop sends SIGTERM - corDB syncs its log and writes its snapshots - and SIGKILL when the grace period is over; a container: docker stop -t <grace>, then docker rm.

What a running broker shows, every 2 s its status (GET /ready on its health port, else GET /version) and, with the admin API:

  • The log, live (server-sent events), the run before kept as broker.log.1.
  • Configuration and build - what it is built with (GET /build) and every option it runs with, where each came from (GET /admin/config), a secret masked by the broker.
  • Metrics - /admin/metrics as charts over the last 10 minutes, read every 5 s: requests per second, errors, latency (mean and 95th percentile), notifications, subscriptions, memory; the busiest operations (Administration).
  • Log and trace levels - verbose and info, and a tick box per trace level, grouped by library, its tooltip what it traces - set live through /admin/log. Traces exist in debug builds only; on a release build the tick boxes are greyed.

Explore - the graph and the map

A broker's URL and Connect. The next start connects to the last broker by itself, with the types picked last time. The examples in c³'s repository fill a broker to try it on:

coraine -db corDB -p 1090 --transports ws &            # a broker in RAM, with its WebSocket transport
examples/factory.sh http://localhost:1090              # 25 entities: Relationships, locations, areas, routes
examples/live.sh http://localhost:1090 &               # ... its robots at work: values change every 0.5 s
examples/ckan-bikes.sh http://localhost:1090           # open data: Boston's bike stations and districts

Connecting

  • The tenant - the field beside the URL (NGSILD-Tenant; empty, the default one), kept per broker, offered again with those used before and, from coraine with its admin API, GET /admin/tenants.
  • Local only - every query with local=true: the broker's own entities, without those of its Context Source Registrations.
  • The access token (Token) - sent as Authorization: Bearer on every request, over HTTP and in each message on the broker's WebSocket. In this order: a login to the broker's OpenID provider (the authorization code flow with PKCE, a public client that allows http://<c³>/api/oidc/callback); a credential login for a Data Space Connector - a Verifiable Credential obtained from the consumer's Keycloak (OID4VCI), presented to the verifier, its access token sent; a token typed in (with Remember it on this machine); --token-file; $C3_TOKEN. Tokens stay in the backend - never in the page, never in c3.json; a login's tokens are in memory only and renewed before they expire. A 401 shows the broker's reason, and Log in… when the broker says where its tokens come from (coraine's /.well-known/oauth-protected-resource) (Authorization).
  • Headers of its own (Token, below the token) - up to 16 per broker, each a name, a value and secret: an API key, a Basic Authorization, what a gateway in front of the broker asks for. Sent as they are with every request to that broker - the proxy's reads and writes, the live values' HTTP requests, the WebSocket's upgrade request and each message's metadata. An Authorization among them takes the place of the token. In memory, and with Remember them on this machine in secrets.json; a secret header's value never reaches the page (its last four characters, or its length, do), and saved with its field empty it keeps its value. The headers c³ sets itself are refused (Host, Content-Type, Accept, NGSILD-Tenant, X-C3-Broker, the WebSocket's, ...).
  • Discovery - before any entity is loaded: GET /types?details=true, GET /types/{type} per type (its count and its attributes' kinds), GET /attributes?details=true. The panel lists the types with their counts, each one's attributes, and the Relationships between types.
  • Choosing what to see - Load loads the types ticked (GET /entities?type=A,B, every page, up to 2000 entities; past that a notice says how many there are). A broker of 300 entities or fewer is loaded whole on a first connect.

The browser never talks to a broker: the backend proxies each request, so the broker needs no CORS. The proxy forwards the NGSI-LD API, /version, /build and coraine's admin reads; its writes are the entities and PUT /admin/log only, and only from c³'s own page.

The graph

  • An entity is a box (its type, the end of its id, its first two Properties); a Relationship to another loaded entity is an arrow. A type's colour comes from its place in the broker's sorted list of types - the same broker, the same colours.
  • The layout is deterministic: the same entities and Relationships give the same picture, whatever order the broker sent them in. Every arrow points up; entities with no Relationship go in a grid below.
  • The wheel zooms, a drag moves the view or a box; Fit and 0 show everything.
  • A click shows an entity's attributes - kinds, values, unitCode, observedAt, datasetId, sub-attributes - and its JSON; a Relationship's target is a link.
  • An entity's menu (right-click, or Shift+F10): With linked entities (join=inline&joinLevel=1, 2, 3: one box holding the entities its Relationships point to), Neighbourhood (the entities one Relationship away, out or in), Follow, Hide type, Copy id, Show JSON, Edit…, Replace… (PUT), Delete entity….
  • The editor - the entity as rows, an input per attribute kind (a value with its JSON type, a Relationship's target - or pick in graph -, a Point's coordinates - or pick on map -, a LanguageProperty's languages, ...), sub-attributes, instances by datasetId. Save as says how an edit is sent: a merge (PATCH /entities/{id}, the default, "urn:ngsi-ld:null" for what was deleted), update attributes (PATCH /entities/{id}/attrs, each new or changed instance whole, a deletion as "urn:ngsi-ld:null"), append attributes (POST /entities/{id}/attrs, with or without ?options=noOverwrite - no deletions: they are left out, and counted) or a partial attribute update (PATCH /entities/{id}/attrs/{attrId}, one per changed instance - its changed members, a deleted sub-attribute as "urn:ngsi-ld:null"; a new or deleted attribute or instance left out). The request at the bottom shows what Save sends. A right-click where there is no entity creates one (POST /entities). The broker's errors - a 401, a 403, a 400's detail, a 207's attributes not updated - show in the editor.

The map

Graph / Map switches the view, kept per broker. On the map, every loaded entity with a GeoProperty (location first, then any other): a Point as a marker, a LineString as a line, a Polygon as an area, in the type's colour; Relationships as lines with an arrowhead at the target - all, or the selected entity's only.

  • Colour by type, or a Relationship (inDistrict →): each target and the entities pointing at it in one colour, with a legend.
  • Icons for the kinds c³ knows by their type's name - a bus, a stop, a streetlight, an air quality or weather station, a traffic sensor, a person - coloured by state (a broken status red, an airQualityLevel on its scale, a powerState); any other type a dot.
  • Movement - a Point a live change moves glides to its new place, its lines following (not with prefers-reduced-motion).
  • A right-click opens the entity's menu, with Show in the graph; Create entity here… where there is none.

The base map is OpenStreetMap data drawn with MapLibre GL JS in c³'s dark style: online, OpenFreeMap's vector tiles; offline, the areas downloaded.

Offline map areas

Download this area, on the map's bar:

  1. The size first - the area in view, the level of detail (10, 12, 13, 14 or 15; each level adds about four times the tiles) and its size, exact before anything is downloaded: the backend reads the planet's directories for the tiles of that box. An area of more than 1 000 000 tiles is refused.
  2. The extract - the backend extracts the tiles from the newest Protomaps planet build (read with HTTP Range requests, never downloaded whole) into one PMTiles file, $XDG_DATA_HOME/c3/maps/<id>.pmtiles; the first time, the label fonts too. Progress and Cancel; one download at a time.
  3. Drawn from the file - inside the area, down to its level, also with no network.
  4. The list - each area's name, size, level, date and planet build, Show and Delete.

Offline means the downloaded areas: outside them the map is empty. Making an area needs the network once.

Live values

When an attribute of a loaded entity changes in the broker, its box and its marker change, the rows that changed marked; an entity created appears, one deleted disappears; nothing is reloaded. Live · WebSocket or Live · HTTP says how the changes arrive:

  • The broker's WebSocket transport (coraine --transports ws, WebSocket) - tried first: the backend opens /ngsi-ld/v1/ws, creates one subscription over it, and the notifications come back on the same socket. The broker deletes the subscription when the socket closes, also when c³ is killed.
  • An HTTP subscription notifying the backend (http://127.0.0.1:<port>/api/notify/<session>) - any NGSI-LD broker that can reach it. A subscription left by a c³ that was killed is deleted by the next start on that port.

The subscription (named c3-live:<port>) watches the types loaded, every attribute and every kind of change; it is replaced when the picks change and deleted when the page closes. The changes are applied every 250 ms; when the broker goes away, the page watches again until it is back.

  • Alarms - alert rules per broker: a title, a severity, an entity type and a q, each a subscription of its own. A match raises an alarm - a toast, a row, the entity ringed on the map until acknowledged - cleared when the live values no longer match (for the simple forms of q; otherwise by hand).
  • History - each numeric Property of the selected entity over the last 10 minutes as a sparkline, from the temporal API (GET /temporal/entities/{id}?timerel=after...), then grown from the live values. A broker without history shows the live values from the moment the entity was selected.
  • Named demos - a name instead of a URL (CDMAD, built in; others under demos in c3.json): c³ fetches the demo's descriptor - its broker, tenant, view, the types to load, its alert rules - and connects.

The Documentation page

These guides: the list (#docs), a guide (#docs/<guide>) and a section of it (#docs/<guide>/<section>), with On this page, the previous and next guide, and search across every guide's sections. The pages are part of c³ and served by its backend, so they work offline. Every component is listed too, one line each: its name opens its guide here - a Cor-Lib's, the bridge's, the tool's - with its API reference and its repository beside it; a component with no guide (corAasBridge, and the private ones) opens its repository on GitHub. With the gh command logged in, the private SEAMWARE repositories the user can read are added (gh repo list, asked as the user).

The same pages are the website seamware.github.io/docs (make site, in build/site); there a link to a page of c³ itself - Compile, Operate, Explore - is the page's name, marked as being in c³.

Where it keeps its state

The configuration file, c3.json ($XDG_CONFIG_HOME/c3/, else ~/.config/c3/, or --config) - written by the backend as the user works, never by the page:

MemberWhat it holds
brokersthe brokers connected to (the 50 most recent), each with Explore's choices: the tenant and those used, the types picked per tenant, graph or map, the map's view, colour by, the alert rules, the login's issuer, client id and scope
demosnamed demos and their descriptors' URLs
maps.areasthe map areas downloaded
compileCompile's current choice and the presets
run.brokersthe brokers Operate started, with their options
ui.lastPagethe page shown last

It is written whole to c3.json.tmp and renamed over c3.json (mode 600, the directory 700). Members this version does not know are kept; a file that is not a JSON object is moved to c3.json.broken; a file of a newer version is read and never written. No access token is in it, nor a broker's own headers: remembered, they are in secrets.json beside it (mode 600 - a file others can read is not used).

The data directory, $XDG_DATA_HOME/c3/ (else ~/.local/share/c3/) - here the directories are the truth, not the configuration:

builds/<name>/           coraine-build's directory: the source, the build tree, install/ (the result)
builds/<name>.json       the build's record: options, command, phases, exit status, sizes, --version
builds/<name>.log        everything coraine-build wrote
run/<name>/broker.log    a broker's output and c3's lines about it; broker.log.1 the run before
run/<name>/state.json   a native broker that runs: its pid and the process's start time
run/<name>/data/        --dbDir of a native corDB
run/<name>/bridges.json the bridge configuration c3 writes
run/services/<container>.log
maps/<id>.pmtiles       a downloaded map area
maps/fonts/             the label fonts

Chrome's profile for c³'s window is in $XDG_STATE_HOME/c3/chrome.

How it is built

The backend is one C binary, c3, on coraine's own libraries: corHttp (the HTTP server - the pages, the API, the page's WebSocket, files and server-sent event streams), corRest (the HTTP client of the proxy and the map downloads), corJson and corTree (the configuration and the API's bodies), corArgs (the command line), and corAlloc, corBase, corLog under them; zlib and OpenSSL. A proxied request leaves the event loop and is sent on a thread of its own: a slow or absent broker holds up nothing else (timeout 15 s, the largest answer 64 MiB).

The frontend is plain JavaScript modules, HTML and CSS - no build step, no framework, nothing from a CDN. The map's libraries (MapLibre GL JS, pmtiles, @protomaps/basemaps) are copied as published into www/vendor/, each with its licence.
