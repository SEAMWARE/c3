The cor format and cor://

cor is coraine's binary serialisation of a tree - a request, a response, an entity. cor:// is the broker's binary API: the same trees, framed for a long-lived TCP connection. A request that arrives over cor:// is already a tree, so it goes into the same service routines as an HTTP request, without a JSON parse, and its response goes back as a tree.

When to use it

  • Between brokers. A context source registration whose endpoint is cor://host:port makes forwarding to that source go over cor:// instead of HTTP - no JSON rendered or parsed on either side of the hop.
  • A client that speaks it. corTools' corRequest sends requests over cor://, one at a time or in its load mode.
  • Not for what only HTTP carries: a body that is not JSON, a text answer, HEAD.

cor:// is a communication protocol, not a bridge: it reaches the broker's API, as a client (forwarding) and as a server (the listener).

A broker built without it. make COR_WITH_COR_PROTOCOL=0 (or coraine-build --features COR_PROTOCOL=OFF) leaves out the cor:// server and client, --corPort and the cor:// forwarder: 24 640 bytes less (stripped, 2026-10-13). --version and GET /build say COR_PROTOCOL 0 / false. A registration with a cor:// endpoint is then accepted and not forwarded to: the answer carries NGSILD-Warning: 299 <host:port> "The registration endpoint's scheme is not supported by this broker". The cor format stays - corDB's log and history are written in it.

What it is

  • One format, three uses: cor://, and the bodies of the corDB log and snapshot records.
  • The codec knows nothing about NGSI-LD. It lives in corTree and serialises any tree; corNgsild tells it, through callbacks, which names are core terms and which objects are attributes.
  • Zero-copy on read - strings keep their NUL and point into the read buffer. Skippable - objects and arrays carry their byte length, so a reader steps over a subtree it does not want in one add. Little-endian - no byte swapping, on x86 or ARM.
  • Multiplexed - any number of requests in flight on one connection, answered in the order they finish, run on the event loops' coroutines.

The frame

Every message is a fixed 16-byte header, then one encoded tree.

Header fieldBytes
magic4C0 4F 52 01: 0xC0, O, R, format version 1
message type1HELLO, HELLO_ACK, REQUEST, RESPONSE, PUSH, CLOSE, ERROR, PING, PONG
flags1bit 0: compressed; bit 1: a fragment, more follows
reserved2zero
correlation id4a REQUEST's, copied into its RESPONSE; 0 for PUSH
length4the body's

The magic is what no text can begin with: 0xC0 never appears in valid UTF-8. An HTTP client on the cor:// port, or the reverse, shows in the first bytes - GET is not C0 4F 52 - and is refused at once with a clear error. After a framing error a reader can scan for the next magic.

The bodies are trees, not codes. A request is { op, tenant, path, params, body }, a response { status, headers, body }. A new operation is a new value of op, which an old peer answers with "not implemented" instead of failing to parse it. HELLO carries the format version and the lengths of the two fixed tables (core terms, namespaces); both are append-only, so two peers use the shorter of each.

On cor:// the tables live as long as the connection. A namespace or a name is sent once and reused by every message after it. Each side writes its own outgoing tables and mirrors the peer's; frames are encoded in the order they are sent and decoded in the order they arrive; a reconnect starts the tables empty again. A corDB snapshot or log block keeps tables of its own, so it can be read alone.

Multiplexing

  • The server reads every frame that comes on a connection and runs each request as it arrives - inline when it cannot wait, as a coroutine when it can - and writes each response as it finishes.
  • The client keeps one connection per peer per thread, shared by the requests of that thread. A distributed operation fanned out to several cor:// sources starts every request before it waits for any: they are all in flight at once.
  • With mongoc a request that waits cannot be a coroutine (its driver blocks): the connection moves to a thread of its own and is served one request at a time.

One broker, no forwarding - what the transport itself costs, a GET on corDB, 16 connections (release build, no PGO, 2026-10-01): cor:// and HTTP at parity on throughput, 145,300 against ~142,000 req/s; the p99 under load 209 µs against 4-9 ms.

On the wire: the generic codec gives 84 % of minimised JSON, with the NGSI-LD callbacks 71 %, over 660 JSON documents of the ETSI suite and coraine's tests - compact names and inline @context text, the least favourable case. Broker-to-broker traffic, with its expanded names, is still to be measured.
