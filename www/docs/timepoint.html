Timepoint - an entity as it was

The Core API's retrieve and query, evaluated at a point in time: the entities as they were at timeAt. The answer is an ordinary Entity, or an Entity array - not the temporal representation of /temporal/entities. NGSI-LD v2.1 (ETSI DATAINFRA(26)000027).

# the vehicle as the broker held it at 10:00
curl 'http://localhost:1026/ngsi-ld/v1/temporal/timepoint/entities/urn:ngsi-ld:Vehicle:A100?timeAt=2026-10-20T10:00:00Z'

# the vehicles faster than 50 then
curl 'http://localhost:1026/ngsi-ld/v1/temporal/timepoint/entities?type=Vehicle&q=speed>50&timeAt=2026-10-20T10:00:00Z'

timeAt

Mandatory: a missing or invalid timeAt is a 400 BadRequestData.

  • GET - the URL parameter timeAt.
  • POST - a member of the Query: { "type": "Query", ..., "timeAt": "..." }.

The Query's timeAt, not a temporalQ's. A temporalQ selects entities by their history (timerel, its own timeAt); the timepoint's timeAt picks the instance of each attribute an entity had then. A timepoint query with a temporalQ is a 400 - and so is a Core API POST query with a timeAt member: a Query there has none.

What "as it was" means

timeAt is on system time: the entity as the broker held it at timeAt - each attribute's last write at or before it.

The entity at timeAtThe answer
created after it, or deleted at itnot there - a retrieve is a 404
an attribute deleted before itthe entity without that attribute
deleted and created againthe life timeAt is in - an earlier life's attributes do not come back
its typesits current ones - a change of types is not kept in the history

Everything else is the Core API's

Its parameters, their meaning, its rendering and its errors - q, geoQ, scopeQ, type, ids, idPattern, pick, omit, attrs, datasetId, lang, options (concise, keyValues, sysAttrs), limit, offset, count, ... - evaluated on the entities as they were. A q on speed filters on the speed at timeAt; count counts the entities that matched then.

Not on the timepoint resourcesWhy
join, joinLevel (400, an unknown parameter)the linked entities would be read as they are now
entityMap (400, an unknown parameter)a map's pages read the entities as they are now
NGSILD-Snapshot (400)a timepoint request is not served from a Snapshot

A timepoint request creates no automatic EntityMap, and is local: no registration's source is asked.

Where the history comes from

From the TRoE inside corDB:

coraine --database corDB --troe corDB

Add --dbDir to keep it on disk. A TRoE without the timepoint reads - --troe none, --troe ramDB, and today --troe timescale - answers as it does for any temporal operation it lacks.

Build

COR_FEATURE_TIMEPOINT - on by default; off removes the resources, about 2.4 KB of the broker (Building).
