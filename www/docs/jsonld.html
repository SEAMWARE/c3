JSON-LD and @context

In NGSI-LD every name is an IRI. speed is a short name a client uses, and https://example.org/vocab/speed is the name the broker keeps. The client's @context maps one to the other. The broker expands the names of every request with it and compacts the names of every response with it, so two clients that use different short names for the same IRI see the same data. This guide says where the broker takes the @context from, what it does with it, and what it keeps.

Every example below was run against a coraine broker on localhost:1099, with --database corDB --httpEndpoint http://localhost:1099, and the outputs are as it answered. Only the Date headers are left out.

The JSON-LD processing - an @context parsed, the context cache, expansion and compaction - is corJsonld, a library of its own. The broker's NGSI-LD side, corNgsild, hosts the inline @contexts a response names (below).

1What an @context does

An @context is a JSON object of terms: a short name and the IRI it stands for. Here it is hosted on the broker itself (the endpoints):

curl -i localhost:1099/ngsi-ld/v1/jsonldContexts -H 'Content-Type: application/json' -d '{ "@context": {
  "Vehicle": "https://example.org/vocab/Vehicle",
  "speed":   "https://example.org/vocab/speed",
  "brand":   "https://schema.org/brand" } }'
HTTP/1.1 201 Created
Location: /ngsi-ld/v1/jsonldContexts/urn:ngsi-ld:Context:1-1793107074

An entity created with it, named in the Link header:

CTX='<http://localhost:1099/ngsi-ld/v1/jsonldContexts/urn:ngsi-ld:Context:1-1793107074>; rel="http://www.w3.org/ns/json-ld#context"; type="application/ld+json"'

curl -i localhost:1099/ngsi-ld/v1/entities -H 'Content-Type: application/json' -H "Link: $CTX" -d '{
  "id": "urn:ngsi-ld:Vehicle:1", "type": "Vehicle",
  "speed": { "type": "Property", "value": 42 },
  "brand": { "type": "Property", "value": "Mercedes" },
  "color": { "type": "Property", "value": "red" } }'
HTTP/1.1 201 Created
Location: /ngsi-ld/v1/entities/urn:ngsi-ld:Vehicle:1

Read back with the same @context, it looks the way it was written:

curl localhost:1099/ngsi-ld/v1/entities/urn:ngsi-ld:Vehicle:1 -H "Link: $CTX"
{"id":"urn:ngsi-ld:Vehicle:1","type":"Vehicle","speed":{"type":"Property","value":42},"brand":{"type":"Property","value":"Mercedes"},"color":{"type":"Property","value":"red"}}

Without it, the broker compacts with the core context alone. Each name the core does not know comes back as its IRI:

curl localhost:1099/ngsi-ld/v1/entities/urn:ngsi-ld:Vehicle:1
{"id":"urn:ngsi-ld:Vehicle:1","type":"https://example.org/vocab/Vehicle","https://example.org/vocab/speed":{"type":"Property","value":42},"https://schema.org/brand":{"type":"Property","value":"Mercedes"},"color":{"type":"Property","value":"red"}}

color is in no context. It was expanded with the core context's @vocab to https://uri.etsi.org/ngsi-ld/default-context/color, and compaction strips that prefix again, so it reads color with any context. The same goes for a query: type=Vehicle without the Link is https://uri.etsi.org/ngsi-ld/default-context/Vehicle, a different type, and it matches nothing:

curl 'localhost:1099/ngsi-ld/v1/entities?type=Vehicle'
[]
curl 'localhost:1099/ngsi-ld/v1/entities?type=Vehicle&options=keyValues' -H "Link: $CTX"
[{"id":"urn:ngsi-ld:Vehicle:1","type":"Vehicle","speed":42,"brand":"Mercedes","color":"red"}]

What expands: attribute and sub-attribute names, the values of type, a VocabProperty's vocab, the values of the other terms the core context types @vocab (watchedAttributes, propertyNames and so on), and the attribute names in URL parameters (attrs, q, orderBy). What does not expand: the id, a Property's value, the keys of a LanguageProperty's languageMap, and a JsonProperty's json. The rules, step by step, are in corJsonld.

curl localhost:1099/ngsi-ld/v1/entities -H 'Content-Type: application/ld+json' -d '{
  "id": "urn:ngsi-ld:Car:1", "type": "Car", "category": { "type": "VocabProperty", "vocab": "sedan" },
  "@context": { "sedan": "https://example.org/cat/sedan" } }'

curl localhost:1099/ngsi-ld/v1/entities/urn:ngsi-ld:Car:1
{"id":"urn:ngsi-ld:Car:1","type":"Car","category":{"type":"VocabProperty","vocab":"https://example.org/cat/sedan"}}

2Where a request's @context comes from

The requestIts @context
Content-Type: application/json, with a Link header (rel="http://www.w3.org/ns/json-ld#context")the one the Link names
Content-Type: application/ld+jsonthe @context member of the body, an object, a URL or an array of them. For an array body, each element has its own
GET, HEAD, DELETE - no bodythe Link header

The core context always comes last and wins, term by term (the core context). The combinations the spec does not allow are refused:

3The @context of a response

A response is compacted with the request's @context, and says which one it was. For Accept: application/json (the default) it is named in the Link header. For Accept: application/ld+json it is an @context member of the body, and there is no Link:

curl -i 'localhost:1099/ngsi-ld/v1/entities/urn:ngsi-ld:Vehicle:1?options=keyValues' -H "Link: $CTX" -H 'Accept: application/ld+json'
HTTP/1.1 200 OK
Content-Type: application/ld+json
Content-Length: 185

{"id":"urn:ngsi-ld:Vehicle:1","type":"Vehicle","speed":42,"brand":"Mercedes","color":"red","@context":"http://localhost:1099/ngsi-ld/v1/jsonldContexts/urn:ngsi-ld:Context:1-1793107074"}

A request with no @context gets the core context's URL, https://uri.etsi.org/ngsi-ld/v1/ngsi-ld-core-context-v1.9.jsonld, or the default user context's.

An @context that came inline, in an application/ld+json body, has no URL that a Link header could name. The broker hosts it for the purpose and names that (corNgsild's ldContextHost.c):

curl -i 'localhost:1099/ngsi-ld/v1/entityOperations/query?options=keyValues' -H 'Content-Type: application/ld+json' -d '{
  "type": "Query", "entities": [ { "type": "Vehicle" } ],
  "@context": { "Vehicle": "https://example.org/vocab/Vehicle", "speed": "https://example.org/vocab/speed" } }'
HTTP/1.1 200 OK
Content-Type: application/json
Link: <http://localhost:1099/ngsi-ld/v1/jsonldContexts/urn:ngsi-ld:Context:vb789f444eb5c2b54>; rel="http://www.w3.org/ns/json-ld#context"; type="application/ld+json"

[{"id":"urn:ngsi-ld:Vehicle:1","type":"Vehicle","speed":42,"https://schema.org/brand":"Mercedes","color":"red"},{"id":"urn:ngsi-ld:Vehicle:2","type":"Vehicle","speed":80}]

brand is not in this @context, so it comes back as its IRI.

Such a context
its idurn:ngsi-ld:Context:v<hash>, a hash of its body. The same inline @context on every request is one entry, whatever the request rate
its life3600 s after it was last used: each use starts the hour again. Unused for an hour, it is dropped (checked every second)
fetchedGET on its URL answers its body, with Cache-Control: no-store, because the URL can change once it is dropped and hosted again
listednever: GET /jsonldContexts leaves it out
storedin the cache only, never in the database

4The core context

The NGSI-LD core context v1.9 (https://uri.etsi.org/ngsi-ld/v1/ngsi-ld-core-context-v1.9.jsonld) is compiled into the broker and never downloaded. A request that names it, or an older core context (ngsi-ld-core-context.jsonld, -v1.N.jsonld), downloads nothing: the broker's own core is used. GET /jsonldContexts lists it as kind Cached - a local copy of the @context at its URL, compiled in instead of downloaded - so, as for every Cached one, its metadata is served (?details=true) and its body is not (422 OperationNotSupported). It cannot be deleted (400).

The core wins. A core term keeps its meaning whatever a user context says about that name: type, value, observedAt, location, status, name and the rest. This user context maps status to an IRI of its own:

{ "@context": { "ParkingSpot": "https://example.org/parking/ParkingSpot",
                "status":      "https://example.org/parking/status" } }

Yet an entity written with it has the core term status (ngsi-ld:status), and a reader with only the core context sees status, not https://example.org/parking/status:

curl 'localhost:1099/ngsi-ld/v1/entities?type=https://example.org/parking/ParkingSpot&options=keyValues'
[{"id":"urn:ngsi-ld:ParkingSpot:7","type":"https://example.org/parking/ParkingSpot","status":"occupied"}]

A vocabulary term with the same name as a core term is shadowed. The data model's IRI for it is never used, so a consumer that looks for that IRI does not find it. The core context's own list of terms says which names are taken.

Only the core context's @vocab is used. A name that no context defines becomes https://uri.etsi.org/ngsi-ld/default-context/ + the name. An @vocab in a user context is not used:

curl localhost:1099/ngsi-ld/v1/entities -H 'Content-Type: application/ld+json' -d '{
  "id": "urn:ngsi-ld:Thing:1", "type": "Thing", "weight": { "type": "Property", "value": 3 },
  "@context": { "@vocab": "https://example.org/mine/" } }'

curl 'localhost:1099/ngsi-ld/v1/entities?type=https://example.org/mine/Thing'
[]
curl 'localhost:1099/ngsi-ld/v1/entities?type=https://uri.etsi.org/ngsi-ld/default-context/Thing&options=keyValues'
[{"id":"urn:ngsi-ld:Thing:1","type":"Thing","weight":3}]

A name already an IRI (urn:, http://, https://) is kept as it is, and a prefix:suffix name is expanded with the prefixes of the user context first, then the core's (ngsi-ld:, geojson:).

5A default user context

--defaultUserContext (-duc) gives the broker the @context for every request that brings none: no Link header and, for application/ld+json, no @context in the body. The bridges' configuration and samples, and the auth plugin's policy terms, are expanded with it too. The core context still comes after it and wins.

Given as
a URLkept as given and downloaded the first time it is needed. A request that needs it while it cannot be downloaded gets 504 LdContextNotAvailable
a file, or file://<path>read and checked at start: it must be a JSON object with an @context member that is an object or an array, or the broker does not start. Then it is hosted, as <advertised endpoint>/ngsi-ld/v1/jsonldContexts/defaultUserContext, kind Hosted
coraine --database corDB --httpEndpoint http://localhost:1099 --defaultUserContext parking.jsonld

curl localhost:1099/ngsi-ld/v1/entities -H 'Content-Type: application/json' -d '{
  "id": "urn:ngsi-ld:ParkingSpot:7", "type": "ParkingSpot", "status": { "type": "Property", "value": "occupied" } }'

curl -i 'localhost:1099/ngsi-ld/v1/entities/urn:ngsi-ld:ParkingSpot:7?options=keyValues'
HTTP/1.1 200 OK
Content-Type: application/json
Link: <http://localhost:1099/ngsi-ld/v1/jsonldContexts/defaultUserContext>; rel="http://www.w3.org/ns/json-ld#context"; type="application/ld+json"

{"id":"urn:ngsi-ld:ParkingSpot:7","type":"ParkingSpot","status":"occupied"}

The option's reference: Command-line options. The DDS mapping tool writes such a file (DDS and ROS 2).

6Downloads and the cache

An @context URL is downloaded once and kept in the broker's context cache, kind Cached. Every later request that names it uses the cached copy. Downloading also follows an @context that is itself a URL, and every URL element of an array.

The cache
one per brokershared by every tenant and every request
size100 entries. Past that, the one used longest ago is dropped and downloaded again when next needed
a URL and its schemehttp://h/x and https://h/x are one entry: the first one seen
one download at a time per URLa second request for a URL that is downloading waits for it, up to 3 s, and fails with 504 if it has not landed. A coroutine that waits yields (Coroutines)
TLSverified against the system CA store. --insecureNotif turns that off for every outgoing request of the broker, downloads among them
a newer version of a contextnot noticed: an entry stays until it is dropped for room or deleted. DELETE /jsonldContexts/{id}?reload=true downloads it again

In the example below, the context server's log shows one GET /parking.jsonld for the create and none for the reads after it, then one more for the reload:

curl 'localhost:1099/ngsi-ld/v1/jsonldContexts?kind=Cached&details=true'
[{"URL":"http://127.0.0.1:8799/parking.jsonld","localId":"http://127.0.0.1:8799/parking.jsonld","kind":"Cached","createdAt":"2026-10-27T13:19:34.000Z","lastUsage":"2026-10-27T13:19:34.000Z"}, ...]

curl -i -X DELETE 'localhost:1099/ngsi-ld/v1/jsonldContexts/http%3A%2F%2F127.0.0.1%3A8799%2Fparking.jsonld?reload=true'
HTTP/1.1 204 No Content

7The @context endpoints

The JSON-LD context API (TS 104 175 clause 13), under /ngsi-ld/v1/jsonldContexts:

RequestWhat it does
POST /jsonldContexts{"@context": {...}} is hosted as given, kind Hosted, with a new id urn:ngsi-ld:Context:<n>-<seconds>. {"url": "..."} is downloaded and cached, kind Cached, and its id is the URL. 201 with the Location
GET /jsonldContextsthe URLs of the stored contexts. details=true gives objects instead (URL, localId, kind, createdAt, lastUsage). kind=Hosted|Cached|ImplicitlyCreated filters (anything else is 400), and limit, offset and count page it
GET /jsonldContexts/{id}a Hosted or ImplicitlyCreated context's body, as application/json. A Cached one answers 422 OperationNotSupported - its metadata only, with details=true
DELETE /jsonldContexts/{id}removed from the broker. reload=true downloads a Cached one again instead; on any other kind it is 400

The id in a path is URL-encoded when it is a URL. The Location of a Cached one is the URL itself:

curl -i localhost:1099/ngsi-ld/v1/jsonldContexts -H 'Content-Type: application/json' -d '{ "url": "http://127.0.0.1:8799/parking.jsonld" }'
HTTP/1.1 201 Created
Location: /ngsi-ld/v1/jsonldContexts/http://127.0.0.1:8799/parking.jsonld

The hosted contexts, the ones added by URL, and the ones a subscription creates are also written to the database, when its plugin stores contexts. A GET by id that misses the cache, after a restart for example, reads them there. A Link (or an @context URL in a body) that names one of the broker's own /jsonldContexts/{id} URLs - the advertised endpoint (--httpEndpoint, else the detected LAN address) + the path, as the listing and the Link headers give it - is that context, from the cache or the database: not a download, and no second, Cached entry. It makes no HTTP request to itself.

8What the database keeps

The store holds the expanded names: https://example.org/vocab/speed, not speed. A core term is kept by its short name (type, value, observedAt ...), so the structure of an entity costs no IRIs. So a query is answered the same whatever @context wrote the data, and an index is made on the IRI: Database indexes shows the paths. Each corDB record decodes on its own, so it carries its attributes' expanded names every time. In the fixture of Performance and footprint, that is most of a record's 744 bytes.
